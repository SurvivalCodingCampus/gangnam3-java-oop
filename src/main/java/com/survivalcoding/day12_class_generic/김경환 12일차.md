## 1. 오늘 내가 직접 손으로 치며 배운 점

### 제네릭은 사용할 때 저장할 타입을 정한다

`Pocket<E>`에서 `E`는 저장할 데이터의 타입을 나타낸다. 클래스를 만들 때 하나의 구체적인 타입으로 고정하지 않고, 객체를 생성할 때 `Pocket<Int>`처럼 사용할 타입을 정할 수 있다.

```kotlin
class Pocket<E> {
    private var _data: E? = null

    fun put(data: E) {
        _data = data
    }

    fun get(): E? = _data
}

fun main() {
    val pocket = Pocket<Int>()
    pocket.put(1_111)

    val data: Int? = pocket.get()
    println(data)
}
```

`Pocket<Int>`로 만든 객체에는 `Int` 값을 넣을 수 있다. 여기에 문자열을 넣으려고 하면 컴파일 오류가 발생한다. 꺼낸 값도 별도로 캐스팅하지 않고 `Int?`로 받을 수 있다. **넣을 때와 꺼낼 때의 타입을 연결해 주는 것**이 제네릭의 장점이라고 이해했다.

`E`와 `T`는 이 예제에서 사용하는 타입 매개변수 이름이다. `Pocket<E>`와 `StrongBox<T>` 모두 객체를 생성할 때 실제 사용할 타입을 정한다는 점은 같다.

### 값이 없을 수 있으면 반환 타입에도 표현한다

`Pocket`은 생성 직후에는 데이터가 없으므로 `_data`를 `E?`로 선언하고 `null`로 초기화한다. `get()`도 데이터가 없는 상태를 반환할 수 있으므로 반환 타입이 `E?`다.

`StrongBox<T>`에서도 저장된 값은 `T?`다. 금고가 잠겨 있거나 아직 내용물을 넣지 않았으면 `get()`은 `null`을 반환한다. 따라서 **`null`이 나왔다고 해서 잠겨 있다는 뜻으로만 해석할 수는 없다.** 열린 금고라도 내용물이 없으면 `null`이다.

### enum은 정해진 상태를 타입으로 표현한다

인증 상태는 임의의 문자열로 표현하는 대신 `AuthState`에 정해진 세 가지 값으로 나타냈다.

```kotlin
enum class AuthState {
    AUTHENTICATED, UNAUTHENTICATED, UNKNOWN
}

fun loginProcess(authState: AuthState) {
    when (authState) {
        AuthState.AUTHENTICATED -> println("인증잘됨.")
        AuthState.UNAUTHENTICATED -> println("인증안됨.")
        AuthState.UNKNOWN -> println("알수없음.")
    }
}
```

모든 enum 항목을 `when`에 명시하면 어떤 상태를 처리하는지 코드에 드러난다. 새 상태를 추가했을 때 빠진 분기를 컴파일 과정에서 확인할 수 있도록, 이 예제에서는 각 상태를 직접 적었다.

## 2. 가장 헷갈렸던 순간과 해결 과정

### val이면 객체의 내용도 바꿀 수 없는가?

`val`과 `var`는 **변수에 다른 값을 다시 대입해야 하는가**를 기준으로 선택한다.

- `val`: 초기화한 뒤 다른 값으로 재할당하지 않는다.
- `var`: 실행 중 다른 값으로 재할당할 수 있다.

`Word`는 생성할 때 받은 문자열을 읽어서 모음과 자음을 판별한다. 현재 기능에서는 문자열을 바꿀 필요가 없으므로 `class Word(val word: String)`으로 선언했다. 생성자의 `val word`는 객체가 보관하는 읽기 전용 프로퍼티가 된다.

`String` 자체는 불변이다. `word`를 `var`로 선언해도 기존 문자열의 글자를 직접 수정하는 것이 아니라, 다른 문자열을 다시 대입하는 것이다. `lowercase()`도 원본 문자열을 수정하지 않는다.

그렇다고 `val`이 모든 객체의 내부 상태까지 불변으로 만드는 것은 아니다.

```kotlin
val words = mutableListOf("Hello")
words.add("World")
```

`words`에 다른 리스트를 재할당할 수는 없지만, 현재 리스트에 원소를 추가할 수는 있다. **변수의 재할당과 객체 내부의 변경을 구분해야 한다.**

### 제네릭이면 항상 out이나 in을 붙여야 하는가?

`Pocket<E>`는 `put(data: E)`로 값을 받고, `get(): E?`로 값을 돌려준다. 타입 매개변수가 입력과 출력 양쪽에 쓰이므로 이 예제에서는 `out`이나 `in` 없이 일반 `<E>`를 사용한다.

단순히 값을 꺼내는 메서드가 있다고 `out`을 붙이거나, 넣는 메서드가 있다고 `in`을 붙이는 것이 아니다. **클래스 전체에서 해당 타입을 어떻게 사용하는지**를 보고 판단해야 한다.

### N번째에 열리는 것과 N번 지난 뒤에 열리는 것은 다르다

금고의 조건은 정해진 횟수에 도달하면 열리는 것이다. 그래서 현재 `get()` 호출을 시도 횟수에 먼저 포함하고, 그다음 잠금 해제 조건을 확인한다.

```kotlin
attemptCount = attemptCount.add(BigInteger.ONE)

if (!isUnlocked && attemptCount >= requiredAttempts) {
    isUnlocked = true
}

return if (isUnlocked) storedThing else null
```

예를 들어 `padlock`은 1,024번째 호출부터 저장한 값을 반환한다. 내용물을 넣어 둔 경우 1,023번째까지는 `null`이고, 1,024번째에 내용물이 나온다. 횟수를 늘리는 위치와 비교 조건이 동작의 경계를 결정한다.

## 3. 연습문제에 적용하면서 확인한 점

### Word는 영어 모음과 자음을 구분한다

`Word`는 지정한 위치의 글자를 소문자로 바꿔 비교한다. 대문자와 소문자를 같은 기준으로 판별하기 위한 처리다.

```kotlin
class Word(val word: String) {
    fun isVowel(i: Int): Boolean =
        word[i].lowercaseChar() in "aeiou"

    fun isConsonant(i: Int): Boolean {
        val ch = word[i].lowercaseChar()
        return ch in 'a'..'z' && ch !in "aeiou"
    }
}
```

자음은 단순히 모음이 아닌 모든 글자를 뜻하지 않는다. 먼저 영어 알파벳인지 확인하고, 그중 모음이 아닌 글자를 자음으로 판단한다. 따라서 숫자, 공백, 한글은 모음과 자음 판별 모두 `false`다.

인덱스 `i`는 0부터 시작하며 `word.length`보다 작아야 한다. 잘못된 인덱스로 접근하면 `IndexOutOfBoundsException`이 발생하므로, 전체 문자열을 순회할 때는 `word.indices`를 사용한다.

```kotlin
val word = Word("Hello")

for (i in word.word.indices) {
    val type = when {
        word.isVowel(i) -> "모음"
        word.isConsonant(i) -> "자음"
        else -> "영어 알파벳 아님"
    }
    println("${i + 1}번째 글자 '${word.word[i]}': $type")
}
```

코드의 인덱스는 0부터 시작하지만 출력에는 `i + 1`을 사용해서 사람이 읽는 첫 번째, 두 번째 글자로 표시한다. 함수 매개변수 `i`는 함수 안에서 재할당할 수 없고, `Int`는 글자의 위치, `Boolean`은 판별 결과를 나타낸다.

### StrongBox는 내용물과 잠금 상태를 따로 관리한다

`StrongBox<T>`는 같은 타입의 내용물 하나를 보관한다. `put()`을 다시 호출하면 마지막에 넣은 값으로 바뀌지만, 시도 횟수와 잠금 상태는 유지된다.

열쇠별 잠금 해제 횟수는 `KeyType`에서 관리한다.

| 열쇠 | 잠금 해제에 필요한 get() 호출 횟수 |
| --- | ---: |
| `padlock` | 1,024회 |
| `button` | 10,000회 |
| `dial` | 30,000회 |
| `finger` | 1,000,000회 |

`get()`은 내용물을 확인하는 동작이다. 한 번 반환했다고 저장한 인스턴스를 삭제하지 않는다. 또 한 번 잠금이 해제되면 계속 열린 상태를 유지하며, `put()`으로 내용물을 바꿔도 다시 잠그지 않는다.

`StrongBoxMain`에서는 `KeyType.entries`로 모든 열쇠를 순회한다. 각 시도마다 실제로 `get()`을 호출하되, 출력은 첫 시도, 해제 직전, 해제 시점만 보여 준다. **출력하는 횟수와 실제로 호출하는 횟수는 서로 다르다.**

## 4. 나만의 언어로 정리한 핵심 용어

- **제네릭**: 사용할 데이터 타입을 매개변수로 받아, 타입에 맞는 저장과 반환을 제공하는 방식.
- **타입 매개변수**: `E`, `T`처럼 실제 타입이 들어갈 자리를 나타내는 이름.
- **타입 안전성**: `Pocket<Int>`에 문자열을 넣는 것처럼 타입이 맞지 않는 사용을 컴파일 과정에서 확인하는 성질.
- **nullable 타입**: `Int?`, `T?`처럼 값과 함께 `null`도 가질 수 있는 타입.
- **enum**: 인증 상태나 열쇠 종류처럼 정해진 선택지를 하나의 타입으로 묶는 선언.
- **val과 var**: 변수나 프로퍼티의 재할당 가능 여부를 정하는 선언.
- **불변성**: 객체의 상태가 바뀌지 않는 성질. `val`로 선언했다는 사실만으로 객체 전체가 불변이 되는 것은 아니다.
- **BigInteger**: `Int`나 `Long`의 고정된 정수 범위를 넘어서는 큰 정수를 표현하는 타입.
- **indices**: 문자열 등의 유효한 인덱스 범위. 빈 문자열이면 순회할 위치가 없다.

## 5. 코드 구조와 상태 관리에서 배운 점

`Word`는 판별 기능을, `WordMain`은 문자열을 순회하고 결과를 출력하는 역할을 맡는다. 같은 패키지에 있으므로 실행 코드에서 `Word`를 사용할 수 있다. `StrongBox`와 `StrongBoxMain`도 금고의 동작과 실행 예제를 나누어 둔다.

금고 안에서는 저장한 내용물, 시도 횟수, 잠금 해제 여부를 각각 관리한다.

```kotlin
private var storedThing: T? = null
private var attemptCount: BigInteger = BigInteger.ZERO
private var isUnlocked: Boolean = false
```

내용물이 바뀌었다고 시도 횟수나 잠금 상태까지 초기화되는 것은 아니다. 각 값이 무엇을 의미하고, 어떤 메서드에서 바뀌는지를 따로 생각해야 했다.

시도 횟수에는 `BigInteger`를 사용한다. `Int`나 `Long`은 고정된 범위를 넘어 계속 증가시키면 오버플로가 발생할 수 있다. `BigInteger`는 이런 고정 폭 정수의 범위 초과를 피할 수 있다.

```kotlin
private val requiredAttempts: BigInteger =
    BigInteger.valueOf(keyType.requiredAttempts.toLong())
```

열쇠별 기준 횟수는 `KeyType`에 모으고, 금고에서는 비교할 `BigInteger` 값으로 생성 시 한 번 변환한다. 기준 횟수를 여러 곳에 직접 적는 대신, 열쇠 종류가 가진 값을 사용하도록 구성했다.

## 6. 오늘의 회고

오늘 예제에서 제네릭은 여러 타입을 받을 수 있게 하는 기능과 함께, **넣는 값과 꺼내는 값의 타입을 일관되게 연결하는 역할**을 한다는 점을 배웠다. `Pocket<Int>`로 정하면 입력도 `Int`를 따르고, 출력도 `Int?`로 받을 수 있다.

`val`과 `var`는 객체가 바뀌는지보다 변수를 재할당해야 하는지를 먼저 보고 선택해야 한다. 읽기만 하는 `Word.word`는 `val`로 두고, 금고의 내용물과 시도 횟수처럼 실행 중 바뀌는 상태는 `var`로 관리한다.

금고 문제에서는 N번째 호출을 횟수에 포함하는 순서, 열린 상태의 유지, 내용물을 바꿨을 때의 동작까지 정해야 했다. 메서드의 반환값만 보는 것보다 **호출 전후에 어떤 상태가 바뀌는지**를 함께 보는 것이 중요했다.

다음에는 이런 조건을 구현하기 전에 해제 직전과 해제 시점의 결과를 먼저 적어 보고, 내용물이 없는 경우와 한 번 열린 뒤의 동작도 함께 확인하려고 한다.
