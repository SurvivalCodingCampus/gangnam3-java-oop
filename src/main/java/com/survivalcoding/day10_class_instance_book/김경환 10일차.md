## 1. 오늘 배운 내용

### 주소가 같은지, 값이 같은지

오늘 가장 중요했던 것은 같은 객체를 가리키는지, 내용이 같은지를 구분하는 것이었다.
주소라고 생각하면 이해하기 쉽지만, 정확히는 객체를 가리키는 참조를 비교하는 것이다.

```java
Book a = new Book("Java 입문", LocalDate.of(2024, 1, 1), "설명 A");
Book b = new Book("Java 입문", LocalDate.of(2024, 1, 1), "설명 B");
```

`new`를 두 번 했으므로 a와 b는 서로 다른 Book 객체다. 출간일은 둘 다 2024-01-01이다.

```java
System.out.println(a == b); // false
```

`==`는 같은 객체를 가리키는지 비교한다. 필드의 내용이 같아도 따로 만든 객체면 false다.

기본 `Object.equals()`도 같은 객체인지 비교한다. 그래서 Book에서 equals를 재정의하지 않았다면 `a.equals(b)`도 false다.

이번 Book에서는 제목과 출간일이 같으면 같은 책이라고 판단하도록 equals를 재정의했다.

```java
System.out.println(a.equals(b)); // true
```

설명이 달라도 제목과 출간일이 같아서 true다. 어떤 필드를 비교할지는 문제에서 정한 기준에 따른다.
equals를 재정의해도 `==`의 비교 방식은 바뀌지 않는다.

### equals와 hashCode는 같이 생각하기

List에서 찾을 때는 equals가 사용된다. HashSet과 HashMap은 hashCode와 equals를 함께 사용한다.

해시값으로 찾을 후보를 좁히고, equals로 같은 객체인지 확인한다고 이해했다.
equals가 true인 객체는 hashCode도 같아야 한다. 반대로 해시값이 같다고 반드시 같은 객체는 아니다.

```java
@Override
public int hashCode() {
    // equals랑 같은 기준
    return Objects.hash(title, publishDate);
}
```

Book의 equals에서 제목과 출간일을 비교하므로 hashCode에서도 같은 기준을 사용했다.
설명은 두 메서드 모두에서 제외했다.

## 2. 가장 헷갈렸던 부분

### List, Set, Map의 차이보다 먼저 비교 기준 확인하기

처음 설명을 볼 때 내가 궁금했던 것은 주소 기반인지 값 기반인지였다.
컬렉션 이름만 보고 결과를 외우기보다 Book의 equals와 hashCode가 재정의되어 있는지부터 봐야 했다.

아래는 서로 다른 a와 b의 제목과 출간일이 같은 경우다.

| 상황 | 기본 참조 기준 | 제목·출간일 값 기준으로 equals와 hashCode 재정의 |
| --- | --- | --- |
| a만 있는 List에서 contains(b) | false | true |
| a만 있는 List에서 remove(b) | 삭제 실패 | a 삭제 |
| HashSet에 a와 b 추가 | 2개 | 1개 |
| HashMap에 a와 b를 각각 키로 추가 | 키 2개 | 키 1개, 기존 값 갱신 |

List는 중복을 허용하므로 a와 b를 둘 다 넣으면 어느 비교 기준이든 크기는 2다.
equals가 같다는 이유로 추가를 막는 것은 아니다.

```java
List<Book> books = new ArrayList<>();
books.add(a);
books.add(b);

books.remove(b);
```

현재 Book 기준에서는 앞에 있는 a가 먼저 삭제된다. remove는 앞에서부터 equals가 true인 첫 요소를 찾기 때문이다.
인수로 b를 전달했다고 반드시 b 인스턴스 자체를 지우는 것은 아니었다.

Map은 키를 기준으로 비교한다. 같은 키에 다시 put하면 값을 갱신한다. 서로 다른 키에 같은 값을 넣는 것은 가능하다.

### toString은 비교가 아니라 출력

기본 toString은 `클래스명@해시값` 형태다. 주소처럼 보이지만 실제 메모리 주소를 출력하는 것은 아니다.
재정의하면 제목, 출간일, 설명처럼 확인하고 싶은 내용을 보여 줄 수 있다.

```java
System.out.println(a);
```

출력할 때 toString이 사용된다. List나 Set을 출력할 때도 각 요소의 toString이 사용된다.

위의 a와 b는 equals가 true지만 설명이 달라서 toString 결과는 다르다.
출력 문자열이 같은지와 같은 책인지는 따로 생각해야 한다.

## 3. Book 연습문제에 적용한 내용

강의 자료 마지막 연습문제의 요구사항은 세 가지였다.

1. 제목과 출간일이 같으면 같은 책으로 판단하고 컬렉션에서도 같은 기준을 사용한다.
2. Collections.sort를 사용하면 최신 출간일 순으로 정렬한다.
3. clone 메서드로 깊은 복사를 한다.

필드는 title, publishDate, comment로 만들었다. 생성자와 getter/setter는 IntelliJ에서 `⌘N`으로 생성할 때와 같은 기본 형태로 정리했다.

### 출간일 비교

출간일 필드는 시간 정보가 없는 LocalDate로 작성했다. `2024-01-01`처럼 연, 월, 일만 저장하고, equals, hashCode, 정렬에서 이 값을 그대로 사용한다.

```java
private LocalDate publishDate;
```

테스트 날짜도 `LocalDate.parse("2024-01-01")`로 생성한다. Date로 변환하거나 시간대를 적용하는 코드는 제거했다.

### 최신순 정렬

Book에 `Comparable<Book>`을 구현하고 compareTo에 정렬 기준을 작성했다.

```java
Collections.sort(books);
```

compareTo 결과는 내가 먼저 오면 음수, 정렬 기준이 같으면 0, 뒤에 오면 양수다.
날짜에 reverseOrder를 적용해서 최신 출간일이 먼저 오게 했다.

같은 출간일이면 제목순으로 정렬하고, 출간일이 없으면 마지막에 두었다. 이 두 가지는 과제의 기본 요구사항에 추가한 규칙이다.

Comparator의 compare도 순서를 정하는 메서드다. Comparable의 compareTo는 객체 안에 기본 규칙을 두고, Comparator는 객체 밖에서 정렬 규칙을 지정할 때 사용한다.

List를 정렬해도 중복은 남아 있다. HashSet과 HashMap은 자동으로 최신순 정렬되지 않는다.
TreeSet과 TreeMap은 정렬 비교 결과가 0인 객체를 같은 요소나 키로 판단하므로 HashSet, HashMap과 구분해서 봐야 한다.

### 얕은 복사와 깊은 복사

```java
Book b = a;
```

이것은 복사가 아니다. 같은 객체의 참조를 다른 변수에도 넣은 것이다.

`super.clone()`은 새로운 Book을 만들고 필드의 참조를 복사한다. 변경 가능한 객체를 필드로 가진다면 그 객체도 별도로 복사해야 한다.

현재 Book의 String과 LocalDate는 모두 불변 타입이다. 내부 값을 바꿀 수 없어서 참조를 공유해도 서로 영향을 주지 않는다.

```java
// String과 LocalDate는 불변이라 참조를 공유해도 서로 영향 없음
return (Book) super.clone();
```

LocalDate의 plusDays 같은 메서드는 원래 날짜를 변경하지 않고 새 날짜를 반환한다. setter로 다른 날짜를 넣으면 해당 Book의 필드만 새 날짜를 가리킨다.

## 4. 테스트로 확인한 내용

테스트는 실제 Book 객체를 사용하는 JUnit 단위 테스트로 작성했다.
DB나 외부 API 의존성이 없어서 Mock은 사용하지 않았다.

```java
// given (준비)
// when (실행)
// then (검증)
```

기존 테스트처럼 준비, 실행, 검증을 구분했다.

- 제목과 출간일이 같을 때 equals와 hashCode가 같은지
- 제목 또는 출간일이 다르면 다른 책으로 판단하는지
- List의 검색·삭제, HashSet의 중복 처리, HashMap의 키 조회가 맞는지
- Collections.sort로 최신 출간일이 먼저 오는지
- 복사본의 출간일을 바꿔도 원본 날짜가 유지되는지
- 원본의 출간일을 바꿔도 복사본 날짜가 유지되는지

같은 출간일과 서로 다른 출간일을 넣어 결과를 확인했다. null은 별도 입력 사례로 검사했다.
시·분·초를 입력하거나 시각 차이를 검사하는 테스트는 제외하고, 날짜 기준으로 과제의 동작을 검증했다.

LocalDate는 내부 값을 직접 변경할 수 없다. 복사한 Book에 새 출간일을 설정하고 원본의 날짜가 유지되는지 확인했다.

```java
copy.setPublishDate(LocalDate.parse("2025-02-02"));
```

원본과 복사본이 서로 다른 Book 객체이고, 한쪽의 필드를 바꾸어도 다른 쪽이 유지되는지 검증했다. Book 테스트 22개가 통과했다.

## 5. 오늘 기억할 내용

- `==`: 같은 객체를 가리키는가?
- 기본 equals: 같은 객체를 가리키는가?
- 재정의한 equals: 내가 정한 필드의 값이 같은가?
- hashCode: equals와 같은 기준으로 계산하기
- compareTo, compare: 어떤 순서로 배치할 것인가?
- toString: 어떤 내용으로 출력할 것인가?
- 얕은 복사: 새 객체를 만들지만 내부 참조는 공유
- 깊은 복사: 변경 가능한 내부 객체도 따로 복사

HashSet의 요소나 HashMap의 키로 넣은 Book은 제목과 출간일을 바꾸지 않도록 주의해야 한다.
이 값들이 바뀌면 해시값도 바뀌어서 다시 검색할 때 찾지 못할 수 있다.

## 6. 오늘의 회고

List, Set, Map이 어떻게 동작하는지 보기 전에 비교 기준부터 확인하는 것이 중요했다.
같은 내용으로 두 번 new 했다는 것과 같은 객체를 가리킨다는 것은 다른 이야기였다.

equals, compareTo, toString도 모두 객체를 다루지만 각각 같은지 판단하기, 순서 정하기, 출력하기라는 역할이 있다.
퀴즈를 풀 때는 어떤 메서드가 호출되는지 먼저 보고, 그 메서드가 재정의되어 있는지 확인하려고 한다.

코드도 너무 긴 설명을 붙이기보다 내가 이해한 기준을 짧은 주석으로 남기는 편이 읽기 쉬웠다.
생성자와 getter/setter는 기본 형태로 두고, 제목과 출간일 비교나 불변 객체의 복사처럼 헷갈릴 수 있는 부분에 주석을 남겼다.
