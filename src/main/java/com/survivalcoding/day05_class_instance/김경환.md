## 1. 오늘 내가 직접 손으로 치며 배운 점

### 클래스형 변수와 참조

클래스형 변수에는 객체 자체가 아니라 **객체를 가리키는 참조값**이 들어간다. 메모리 주소처럼 생각하면 이해하기 쉽지만, Java에서 실제 주소를 직접 다루는 것은 아니다.

```java
private Wand wand;
```

마법사가 지팡이를 가진다는 것을 이렇게 표현할 수 있다. 여러 마법사에게 같은 지팡이 객체를 전달하면, 지팡이를 강화했을 때 그 객체를 사용하는 마법사 모두에게 영향을 준다.

### 캡슐화와 getter/setter

필드는 `private`으로 숨기고, 외부에서는 공개된 메서드를 통해 읽거나 변경하도록 만들었다.

```java
public void setMp(int mp) {
    validateMp(mp);
    this.mp = mp;
}
```

setter는 단순히 값을 넣는 메서드가 아니다. **값을 저장하기 전에 해당 객체의 규칙을 검사하는 입구**가 될 수 있다.

이번 과제에서는 다음 규칙을 적용했다.

- 마법사와 지팡이 이름은 `null`이 아니고 3글자 이상이어야 한다.
- 지팡이 마력은 0.5 이상 100.0 이하여야 한다.
- MP가 음수면 예외를 발생시킨다.
- HP가 음수면 예외 대신 0으로 보정한다.

이름 검사에서는 기존 코드의 추가 규칙으로 앞뒤 공백을 제외했다.

### 모든 필드에 setter가 필요한 것은 아니다

`Person`의 이름과 출생 연도는 생성할 때 정하고 이후에는 변경하지 못하도록 했다.

```java
private final String name;
private final int birthYear;
```

생성자로 값을 받고 getter만 제공했다. 나이는 별도 필드에 저장하지 않고 요청할 때 계산한다.

```java
public int getAge() {
    int currentYear = Year.now().getValue();
    return currentYear - birthYear;
}
```

2000년생이라면 2026년 기준 결과는 26이다. 생일을 따지는 만 나이 계산은 아니고, 이번 문제에서 요구한 연도 차이다.

## 2. 가장 헷갈렸던 순간과 해결 과정

### `올해 - 2000`이라는 표현

테스트 설명의 “나이는 올해 - 2000이다”를 보고 순간적으로 `-2000살`이라는 뜻인가 싶었다.

실제 의미는 **현재 연도에서 출생 연도를 뺀다**는 것이었다.

```java
2026 - 2000 = 26
```

이 일을 통해 테스트 이름도 작성한 사람만 이해하면 안 된다는 것을 느꼈다. 수식을 줄여 쓰는 것보다 문장으로 풀어 쓰는 편이 더 명확할 때가 있다.

### `(int)`는 반올림이 아니었다

회복량 계산에서 `(int)`와 `Math.round()`의 차이를 확인했다.

```java
int recovPoint = (int) (BASE_POINT * wand.getPower());
```

기본 회복량이 10이고 마력이 1.25라면 계산 결과는 12.5다.

- `(int) 12.5`는 소수 부분을 버려서 **12**
- `Math.round(12.5)`는 반올림해서 **13**

이번 과제는 교재대로 `(int)`를 사용했다. 정확히 말하면 `(int)`는 0 방향으로 소수 부분을 버린다.

### `this.wand.power`를 그대로 사용할 수 없는 이유

지팡이의 `power`를 `private`으로 바꾸면 `Wizard`에서 직접 읽을 수 없다.

```java
// 캡슐화 후에는 getter를 사용한다.
wand.getPower();
```

단순히 접근 지정자만 붙이면 끝나는 것이 아니라, **그 필드를 사용하는 코드도 함께 바꿔야 한다**는 것을 배웠다.

## 3. 테스트를 작성하면서 배운 점

### 정상 동작부터 확인하기

처음에는 “2000년생을 생성하는 테스트를 왜 해야 하지?”라는 생각이 들었다.

하지만 이 테스트는 생성자가 이름과 출생 연도를 제대로 저장하고, `getAge()`가 요구사항대로 계산하는지 확인한다. 값을 저장하는 코드를 빠뜨리거나 나이를 항상 0으로 반환하면 실패한다.

### given / when / then

테스트를 세 단계로 나누니 읽기 쉬워졌다.

```java
@Test
@DisplayName("[Wizard] HP에 -1을 설정하면 0으로 보정한다")
void clampNegativeHpToZero() {
    // given: 마법사와 음수 HP를 준비한다.
    Wizard wizard = new Wizard();
    int hp = -1;

    // when: HP를 설정한다.
    wizard.setHp(hp);

    // then: 음수 대신 0이 저장되는지 확인한다.
    Assertions.assertEquals(0, wizard.getHp());
}
```

- **given**: 객체와 입력값 준비
- **when**: 검사할 동작 실행
- **then**: 기대한 결과 확인

### 경계값 외에 사용 흐름도 테스트하기

AI를 통해서 테스트를 소프트웨어 공학적으로 조사했을때 다음과 같았다. 

소프트웨어 공학 관점의 테스트 분류

| 기법 | 적용 사례 | 찾으려는 문제 |
|---|---|---|
| 유스케이스 기반 테스트 | 연속 회복, 파티원 회복, 장비 교체·강화 | 각 메서드는 맞지만 함께 사용하면 틀리는 동작 |
| 상태 전이 테스트 | 지팡이 없음 → 실패 → 장착 → 성공, HP 감소 → 0 → 재설정 | 이전 상태에 따라 결과가 잘못 달라지는 문제 |
| 객체 간 통합 테스트 | Wizard → Wand의 마력 읽기 → Hero의 HP 변경 | 회복 대상이나 참조 연결 오류 |
| 실패 시 상태 보존 | null 장착 실패, 이름 변경 실패, HP 오버플로 | 예외 전에 일부 필드만 변경되는 문제 |
| 실패 후 복구 | 잘못된 등록·강화·회복 이후 정상 재시도 | 한 번의 실패로 이후 동작까지 망가지는 문제 |
| 객체 독립성과 참조 공유 | 같은 이름의 별개 객체, 동일 Wand 공유 | static 오용, 복사와 참조의 혼동 |
| 멱등성 | 같은 HP·MP·마력 값을 다시 설정 | 대입해야 할 값을 누적하는 문제 |
| 관계 기반 검증 | 같은 해의 두 사람 나이 차와 출생 연도 차 비교 | 구체적인 현재 연도에만 맞는 구현 |
| 부수 효과 검증 | 이름 변경 시 마력 유지, 회복 시 시전자 HP·MP 유지 | 관련 없는 필드를 실수로 변경하는 문제 |
| 현재 동작 기록 | HP 0 시전, HP 200 초과 회복, 미설정 마력 | 향후 게임 규칙 변경 시 영향이 드러나도록 기록 |

숫자의 경계만 검사하는 것으로는 부족했다. 게임에서 실제로 이어질 만한 행동도 검사했다.

- 같은 용사를 여러 번 회복하면 회복량이 누적되는가?
- 지팡이를 교체하면 다음 회복부터 새 마력이 적용되는가?
- 같은 지팡이를 공유하면 강화 결과도 공유되는가?
- 잘못된 지팡이 설정에 실패해도 기존 장비는 유지되는가?
- 한 마법사의 상태를 바꿔도 다른 마법사는 그대로인가?
- 실패한 뒤 올바른 입력으로 다시 시도하면 성공하는가?

기존 테스트를 포함해 총 122개가 통과했다. 다만 테스트가 많다고 모든 버그가 없다는 뜻은 아니다. 각 테스트가 어떤 요구사항과 실패 상황을 확인하는지 설명할 수 있어야 한다. **결론: 어렵다**

### 테스트 이름도 코드의 일부다

`rejectName1`, `rejectName2`처럼 번호만 붙이면 나중에 차이를 알기 어렵다.

```java
rejectNullName()
rejectEmptyName()
rejectTwoCharacterName()
```

메서드 이름과 `DisplayName`에 입력 조건과 예상 결과를 적어야 실패했을 때 원인을 빨리 찾을 수 있다.
DisplayName을 **사람냄새나게** 적을 필요가 있어보였다.

## 4. 나만의 언어로 정리한 핵심 용어

- 접근 제어자: 필드나 메서드에 누가 접근할 수 있는지 정하는 것.
- 정보 은닉: 외부에서 내부 데이터를 함부로 건드리지 못하도록 숨기는 것.
- 캡슐화: 데이터를 숨기고, getter나 setter 같은 정해진 방법으로 접근하게 하는 것. setter에서 잘못된 값도 막을 수 있다.
- `private`: 같은 클래스 안에서만 직접 접근 가능. 값을 못 바꾸게 하는 건 아니다.
- `final`: 한 번 값을 넣으면 다시 다른 값을 넣을 수 없다.
- 초기화: 처음 사용할 값을 정해주는 것. 0이나 `null`도 상황에 따라 정상적인 시작값일 수 있다.
- 정적 멤버: 객체를 만들지 않고 클래스 이름으로 사용할 수 있는 멤버.
- 매직 넘버: 코드에 갑자기 나오는, 무슨 의미인지 모르는 숫자. 기본 회복량 10을 `BASE_POINT`라고 이름 붙이면 이해하기 쉽다.
- 클램핑: 값이 범위를 벗어나면 경계에 맞춰주는 것. HP가 음수일 때 0으로 바꿔주는 게 예시다.
- 경계값 분석: 어디까지 허용되는지 경계 근처를 검사하는 것. 이름이 3글자 이상이어야 하면 2글자, 3글자, 4글자를 넣어본다.

클램핑은 **값을 처리하는 동작**이고, 경계값 분석은 **그 동작이 맞는지 검사할 입력을 고르는 방법**이다.

## 5. 코드 구조와 UML에서 배운 점

### 상수로 규칙의 의미 표현하기

기본 회복량 10에는 이름을 붙였다.

```java
private static final int BASE_POINT = 10;
```

이름 길이와 마력 범위도 상수로 표현하고, 오류 메시지에서도 같은 상수를 사용하도록 정리했다. 그래야 검사 기준을 바꿨을 때 안내 문구만 예전 값으로 남는 일을 줄일 수 있다.

반면 테스트의 `-1`, `0`, `1`은 경계값 자체를 보여주는 것이 중요하므로 무조건 상수로 바꾸지는 않았다.

### 클래스의 칸과 관계선

PlantUML에서는 다음 순서로 내용을 구분했다.

1. 클래스 이름
2. 상수
3. 인스턴스 필드
4. 공개 메서드
5. 내부 검증 메서드

`--`로 구분선을 넣어 역할별로 나눈 것이며, 칸이 나뉜다고 코드의 동작이 달라지지는 않는다.

관계선도 코드에 따라 달라진다.

```java
private Wand wand;          // 필드로 보관하므로 연관 관계
public void heal(Hero hero) // 인수로 받아 사용하므로 의존 관계
```

- `Wizard → Wand`: 실선 화살표
- `Wizard → Hero`: 점선 화살표
- `Person`: 현재 코드에서는 다른 게임 클래스와 직접적인 관계 없음

`recovPoint`와 `healedHp`는 메서드 안의 지역변수이므로 클래스의 필드 칸에 넣지 않았다.

### 기본 생성자

생성자를 하나도 작성하지 않은 클래스에는 Java가 인수 없는 기본 생성자를 제공한다.

```java
new Wand();
new Wizard();
```

반면 `Person`은 인수를 받는 생성자를 직접 작성했으므로, `new Person()`을 자동으로 사용할 수는 없다.

## 6. 오늘의 회고

처음에는 코드가 실행되면 된다고 생각했는데, 오늘은 **왜 이 접근 지정자를 쓰는지, 왜 이 값을 검사하는지, 테스트가 무엇을 보장하는지**까지 설명하는 것이 중요하다는 것을 느꼈다.

메서드를 단순화하는 것도 중요하지만, 무조건 짧게 만드는 것이 정답은 아니었다. 테스트 준비 메서드 안에 초기값을 숨기면 코드 길이는 줄어도 읽는 사람은 값을 찾으러 이동해야 했다.

앞으로는 코드를 작성한 뒤 다음을 확인하려고 한다.

- 이름만 보고 역할을 이해할 수 있는가?
- 잘못된 입력을 받았을 때 기존 상태를 지키는가?
- 테스트 이름만 보고 어떤 상황을 검사하는지 알 수 있는가?
- UML이 내가 생각한 관계가 아니라 실제 코드의 관계를 표현하는가?
