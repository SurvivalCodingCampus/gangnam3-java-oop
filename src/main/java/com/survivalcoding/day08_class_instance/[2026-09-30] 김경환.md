## 1. 오늘 내가 직접 손으로 치며 배운 점

### 비어 있는 메서드보다 추상 메서드가 정확하다

부모 클래스 `Character`에 `attack()`을 넣고 싶어도, 실제 공격 방법은 자식마다 다를 수 있다. 메서드의 몸체를 비워 두고 “자식에서 재정의하세요”라는 주석만 적으면 자식이 이를 잊거나 메서드 이름을 잘못 적어도 놓치기 쉽다. 부모 클래스 자체를 `new Character()`로 만들어 버릴 수도 있다.

```java
public abstract class Character {
    public void run() {
        System.out.println("도망쳤다");
    }

    public abstract void attack(Slime slime);
}
```

`run()`처럼 공통 동작은 몸체가 있는 메서드로 두고, 자식마다 달라지는 `attack()`은 몸체가 없는 `abstract` 메서드로 선언한다. 추상 메서드가 있는 클래스는 추상 클래스여야 한다. 추상 클래스는 직접 생성할 수 없고, 일반 자식 클래스는 물려받은 추상 메서드를 구현해야 한다. `@Override`를 붙이면 재정의하려는 메서드의 이름이나 매개변수를 잘못 적었을 때 컴파일 과정에서 확인하기 쉽다.

```java
public class Hero extends Character {
    @Override
    public void attack(Slime slime) {
        System.out.println("슬라임을 공격했다");
    }
}
```

추상 클래스라고 모든 메서드가 추상 메서드인 것은 아니다. 일반 메서드와 필드를 함께 가질 수 있다. 또 추상 메서드가 하나도 없어도 직접 만들면 안 되는 공통 개념을 추상 클래스로 표현할 수 있다.

### 여러 단계로 상속할 수도 있다

부모의 추상 메서드를 바로 다음 자식에서 모두 구현할 필요는 없다. 중간 자식도 추상 클래스라면 구현을 뒤 단계로 미룰 수 있다. 다만 **최종적으로 생성할 일반 클래스**는 남은 추상 메서드를 구현해야 한다.

```java
abstract class Monster {
    abstract void attack();
}

abstract class WalkingMonster extends Monster {
    // 아직 attack()을 구현하지 않아도 된다.
}

class Goblin extends WalkingMonster {
    @Override
    void attack() {
        System.out.println("고블린의 공격");
    }
}
```

### 인터페이스는 클래스가 제공할 동작을 약속한다

강의 자료에서는 `Attackable`을 “공격할 수 있음”이라는 역할로 설명했다. `Hero`가 이 인터페이스를 구현하면 `attack()`을 제공한다는 약속을 코드로 나타낼 수 있다.

```java
interface Attackable {
    void attack(Slime slime);
}

class Hero implements Attackable {
    @Override
    public void attack(Slime slime) {
        System.out.println("슬라임을 공격했다");
    }
}
```

인터페이스에 몸체 없이 선언한 `attack()`에는 `public abstract`가 암묵적으로 적용된다. 그래서 구현 클래스의 `attack()`은 `public`이어야 한다. 인터페이스에 선언한 필드는 각 객체의 상태를 담는 인스턴스 필드가 아니라 `public static final`인 상수다. 이번 장의 예제는 추상 메서드 중심으로 인터페이스를 배웠지만, 현재 Java에는 `default`, `static`, `private` 인터페이스 메서드도 있다. 따라서 “인터페이스의 모든 메서드는 추상 메서드”라는 문장은 입문 단계의 단순화로 이해했다.

## 2. 가장 헷갈렸던 순간과 해결 과정

### `extends`와 `implements`를 언제 쓰는가?

클래스가 다른 클래스의 자식이 될 때는 `extends`를 쓴다. 클래스가 인터페이스의 약속을 구현할 때는 `implements`를 쓴다. 둘을 함께 쓸 수도 있다.

```java
interface Healable {
    void heal(Hero hero);
}

class Wizard extends Hero implements Attackable, Healable {
    @Override
    public void heal(Hero hero) {
        System.out.println("용사를 치유했다");
    }
}
```

Java 클래스는 직접 부모 클래스를 하나만 둘 수 있지만, 인터페이스는 여러 개 구현할 수 있다. 인터페이스가 다른 인터페이스를 상속할 때는 다시 `extends`를 쓴다. 예를 들어 `Human extends Creature`라면 `Human`은 `Creature`의 메서드 약속을 물려받는다.

### is-a와 can-do로 관계를 생각하기

처음에는 “영웅은 공격할 수 있다”라는 말도 클래스 상속으로 표현하려고 생각했다. 이제는 두 질문을 먼저 해 본다.

- **is-a(∼의 한 종류인가?)**: `Book extends TangibleAsset`은 “책은 유형자산이다”라는 관계다. `TangibleAsset extends Asset`까지 따라가면 책은 자산이기도 하다. 이런 공통 분류와 상태는 클래스 상속으로 표현했다.
- **can-do(무엇을 할 수 있는가?)**: `Hero implements Attackable`은 “영웅은 공격할 수 있다”는 약속이다. 과제의 `TangibleAsset implements Thing`도 무게를 읽고 바꾸는 동작을 제공한다는 뜻이다.

is-a와 can-do는 설계를 정리할 때 쓰는 질문이지 Java가 강제하는 문법 규칙은 아니다. 인터페이스 이름도 반드시 형용사형이어야 하는 것은 아니다.

### `protected`는 상속할 때 반드시 써야 하나?

필드에 접근제어자를 쓰지 않으면 같은 패키지에서 접근할 수 있는 `package-private`이 된다. `protected`는 같은 패키지에서 접근할 수 있고 다른 패키지의 자식 클래스에서도 상속을 통해 접근할 수 있다. 그렇다고 부모의 필드를 반드시 `protected`로 선언해야 자식이 그 기능을 사용할 수 있는 것은 아니다. 부모가 필드를 `private`으로 두고 getter를 제공하는 방법도 있다.

이번 과제 풀이에서는 공통 필드와 부모 생성자에 `protected`를 사용했다. **접근제어자는 누가 직접 접근해야 하는지를 보고 정하는 것**이지, `extends`를 적었다는 이유만으로 정해지는 것은 아니었다.

## 3. 연습문제에 적용하면서 확인한 점

강의 뒤의 자산관리 문제는 앞에서 배운 두 관계를 한꺼번에 사용했다.

```text
Asset (추상 클래스)
├─ TangibleAsset (추상 클래스, Thing 구현)
│  ├─ Book
│  └─ Computer
└─ IntangibleAsset (추상 클래스)
   └─ Patent

Thing (인터페이스): getWeight(), setWeight()
```

1번에서는 `Book`과 `Computer`에 반복된 `name`, `price`, `color`를 공통 부모인 `TangibleAsset`으로 모았다. 2번에서는 유형자산과 무형자산의 공통 부모 `Asset`을 만들고, `Patent`가 무형자산의 예임을 나타냈다. 3번에서는 `Thing`을 무게 getter/setter가 있는 인터페이스로 만들었다. 4번에서는 `TangibleAsset`이 `Asset`을 상속하면서 `Thing`을 구현하고 `weight`를 실제로 저장하게 했다.

처음 작성한 `Thing`은 무게 필드가 있는 클래스였고, `Book`과 `Computer`에는 상속 관계 없이 같은 필드가 반복되어 있었다. 두 코드 모두 컴파일될 수 있어도 **문제가 요구한 관계를 표현하지는 못한다**는 것을 알았다.

자식 생성자는 `super(...)`로 부모 생성자를 호출해 공통 필드를 초기화한다. 과제를 수정하면서 기존 `Book`과 `Computer`의 4개 인자 생성자와 getter/setter를 없애지 않도록 다시 확인했다.

## 4. 나만의 언어로 정리한 핵심 용어

- **추상 클래스**: 공통 필드나 동작을 담고, 그 클래스 자체는 직접 생성하지 않도록 한 상속용 클래스.
- **추상 메서드**: 자식이 구체적인 내용을 정하도록 몸체 없이 선언한 메서드.
- **구현 클래스**: 물려받은 추상 메서드나 인터페이스의 약속을 실제 메서드로 채운 클래스.
- **`extends`**: 클래스의 상속 또는 인터페이스 사이의 상속을 적는 키워드.
- **`implements`**: 클래스가 인터페이스의 약속을 구현한다고 선언하는 키워드.
- **`@Override`**: 부모 또는 인터페이스의 메서드를 재정의한다는 표시.
- **다형성**: 서로 다른 구체적 객체를 공통 부모 타입이나 인터페이스 타입으로 다루는 것. `Book`과 `Computer`를 `Asset`으로 다룰 수 있다.
- **`super(...)`**: 자식 생성자에서 부모 생성자를 호출하는 표현.

## 5. 코드 구조와 UML에서 배운 점

클래스 상속과 인터페이스 구현은 코드에서도, 다이어그램에서도 다른 관계다.

```text
PlantUML 클래스 상속:       Asset <|-- TangibleAsset
PlantUML 인터페이스 구현: Thing <|.. TangibleAsset
```

따라서 `Computer`가 `Thing`을 직접 구현한다고 선을 그리지 않았다. `Computer`는 `TangibleAsset`의 자식이므로 부모가 구현한 무게 관련 동작을 사용한다. 다이어그램에서는 오늘 정한 표기대로 공개 멤버 앞의 `+`를 생략하고, 핵심 필드와 관계가 보이도록 그렸다.

강의 자료의 연습문제 1 이미지에는 `required this.name` 형태의 생성자가 나온다. 이것은 Java 생성자 문법이 아니다. Java 풀이에서는 부모 생성자를 `super(name, price, color)`처럼 호출한다. **그림의 의도는 공통 상태를 부모로 옮기는 것**이고, 코드는 Java 문법에 맞춰 작성해야 했다.

## 6. 오늘의 회고

처음에는 추상 클래스와 인터페이스를 둘 다 “직접 만들지 않고 다른 클래스가 가져다 쓰는 것” 정도로 생각했다. 이제는 추상 클래스가 **공통 상태와 동작을 묶는 상속의 틀**이고, 인터페이스는 **제공할 동작의 약속**이라는 차이를 설명할 수 있다.

예전에는 “인터페이스부터 적어 놓고 나중에 구현한다”는 말이 무슨 뜻인지 몰랐다. 오늘 과제에서 `Thing`에 `getWeight()`와 `setWeight()`를 먼저 선언하고, `TangibleAsset`에서 무게를 저장하고 두 메서드의 내용을 채워 보니 그 말이 이해됐다. 직접 연결해 보면서 인터페이스와 구현의 차이를 많이 배웠다.

또 주석으로 “반드시 재정의하세요”라고 적는 것보다 `abstract`와 `@Override`를 써서 컴파일 과정에서 확인하는 편이 명확하다는 것을 배웠다. 다음에는 코드를 쓰기 전에 부모·자식 관계와 인터페이스 역할을 먼저 그린 뒤, 기존 생성자와 메서드가 유지되는지도 함께 확인하려고 한다.
