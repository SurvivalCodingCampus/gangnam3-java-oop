# 푸드 레시피 앱 — 핵심 비즈니스 규칙

> 분석 대상: Food Recipe App (Community) Figma
> 모델과 Repository 정의는 `architecture.puml` 참고.
> 이 문서는 코드 없이 기능별 블랙박스 스펙만 정의한다.

---

## 0. 분류 기준

| 구분               | 기준                                                                                  |
|--------------------|---------------------------------------------------------------------------------------|
| Repository 직통    | 받은 데이터를 그대로 화면에 보여준다. 판정도 가공도 없다.                             |
| 비즈니스 규칙 함수 | 입력값 검증, 정책 판정, 데이터 가공, 2개 이상의 Repository 조합 중 하나라도 필요하다. |

| 실패의 종류 | 누가 돌려주나      | 예                         |
|-------------|--------------------|----------------------------|
| 데이터 실패 | Repository         | 네트워크 오류, 데이터 없음 |
| 규칙 실패   | 비즈니스 규칙 함수 | 빈 검색어, 비밀번호 불일치 |

## 1. Repository 직통으로 충분한 기능

### 1-1. 레시피 상세 조회

| 항목        | 내용                                                                            |
|-------------|---------------------------------------------------------------------------------|
| 화면        | Recipe (Ingrident / Procedure 탭)                                               |
| 목적        | 레시피 한 건의 정보, 재료, 조리 순서를 보여준다                                 |
| 필요한 부품 | `RecipeRepository.getRecipe`                                                    |
| 입력값      | `recipeId: Long`                                                                |
| 성공 데이터 | `Recipe`                                                                        |
| 규칙 에러   | 없음 (데이터 실패만 전달)                                                       |
| 직통인 이유 | 받은 `Recipe`를 그대로 그린다. `10 Items`, `10 Steps`는 리스트 크기로 표시한다. |

### 1-2. 리뷰 목록 조회

| 항목        | 내용                                          |
|-------------|-----------------------------------------------|
| 화면        | Reviews                                       |
| 목적        | 레시피에 달린 댓글 목록을 보여준다            |
| 필요한 부품 | `ReviewRepository.getReviews`                 |
| 입력값      | `recipeId: Long`                              |
| 성공 데이터 | `List<Review>`                                |
| 규칙 에러   | 없음 (데이터 실패만 전달)                     |
| 직통인 이유 | 판정도 가공도 없다. 댓글이 0개면 빈 리스트다. |

## 2. 비즈니스 규칙 함수가 필요한 기능

### 2-1. 레시피 검색 + 필터

| 항목        | 내용                                                                      |
|-------------|---------------------------------------------------------------------------|
| 화면        | Search → Filter → Search Result                                           |
| 목적        | 검색어와 필터 조건에 맞는 레시피 목록과 결과 수(`255 results`)를 보여준다 |
| 필요한 부품 | `RecipeRepository.searchByTitle`                                          |
| 입력값      | `query: String`, `time: String`, `rate: Int?`, `category: String?`        |
| 성공 데이터 | `recipes: List<Recipe>`, `totalCount: Int`                                |

**비즈니스 규칙**

| 구분 | 규칙                                                                                                                        |
|------|-----------------------------------------------------------------------------------------------------------------------------|
| 판정 | 검색어는 앞뒤 공백을 뺀 뒤 비어 있으면 안 된다                                                                              |
| 판정 | 검색어는 2글자 이상이어야 한다                                                                                              |
| 판정 | `rate`가 있으면 1~5여야 한다                                                                                                |
| 가공 | `rate`가 있으면 `rating`이 그 별점대인 레시피만 남긴다                                                                      |
| 가공 | `category`가 있으면 `category`가 같은 레시피만 남긴다. `All`은 거르지 않는다                                                |
| 가공 | `time`으로 정렬한다. Newest는 `createdAt` 최신순, Oldest는 오래된 순, Popularity는 `rating` 높은 순, All은 받은 순서 그대로 |
| 가공 | 거른 뒤의 개수를 `totalCount`로 돌려준다                                                                                    |

**규칙 에러 Enum — `SearchRecipeError`**

| 값                | 상황                         |
|-------------------|------------------------------|
| `EMPTY_QUERY`     | 검색어가 비었거나 공백뿐이다 |
| `QUERY_TOO_SHORT` | 검색어가 2글자 미만이다      |
| `INVALID_RATE`    | `rate`가 1~5 밖이다          |

> 결과가 0건인 것은 에러가 아니다. 성공이며 빈 리스트와 `totalCount = 0`을 돌려준다.

### 2-2. 회원가입

| 항목        | 내용                                                                                                     |
|-------------|----------------------------------------------------------------------------------------------------------|
| 화면        | Sign Up                                                                                                  |
| 목적        | 입력값을 검증한 뒤 계정을 만든다                                                                         |
| 필요한 부품 | `AuthRepository.signUp`                                                                                  |
| 입력값      | `name: String`, `email: String`, `password: String`, `confirmPassword: String`, `termsAccepted: Boolean` |
| 성공 데이터 | `User`                                                                                                   |

**비즈니스 규칙**

| 구분 | 규칙                                                                                                                                   |
|------|----------------------------------------------------------------------------------------------------------------------------------------|
| 판정 | 이름은 비어 있으면 안 된다                                                                                                             |
| 판정 | 이메일은 비어 있으면 안 된다                                                                                                           |
| 판정 | 비밀번호는 비어 있으면 안 된다                                                                                                         |
| 판정 | Password와 Confirm Password가 같아야 한다                                                                                              |
| 판정 | `Accept terms & Condition`에 체크해야 한다                                                                                             |
| 가공 | 모든 검증을 통과했을 때만 `signUp(name, email, password)`를 호출한다. `confirmPassword`와 `termsAccepted`는 Repository로 넘기지 않는다 |

**규칙 에러 Enum — `SignUpError`**

| 값                   | 상황                   |
|----------------------|------------------------|
| `EMPTY_NAME`         | 이름이 비어 있다       |
| `EMPTY_EMAIL`        | 이메일이 비어 있다     |
| `EMPTY_PASSWORD`     | 비밀번호가 비어 있다   |
| `PASSWORD_MISMATCH`  | 두 비밀번호가 다르다   |
| `TERMS_NOT_ACCEPTED` | 약관에 동의하지 않았다 |

### 2-3. 레시피 별점 남기기

| 항목        | 내용                                           |
|-------------|------------------------------------------------|
| 화면        | Recipe → `⋯` → Rate Recipe → Send              |
| 목적        | 레시피에 별 1~5개를 매긴다                     |
| 필요한 부품 | `RecipeRepository.rateRecipe`                  |
| 입력값      | `userId: Long`, `recipeId: Long`, `score: Int` |
| 성공 데이터 | `Unit`                                         |

**비즈니스 규칙**

| 구분 | 규칙                                                                              |
|------|-----------------------------------------------------------------------------------|
| 판정 | `score`는 1~5여야 한다. 화면에서 별 0개일 때 `Send`가 비활성인 것과 같은 규칙이다 |
| 가공 | 검증을 통과했을 때만 `rateRecipe(userId, recipeId, score)`를 호출한다             |

**규칙 에러 Enum — `RateRecipeError`**

| 값              | 상황                 |
|-----------------|----------------------|
| `INVALID_SCORE` | `score`가 1~5 밖이다 |

## 4. AI 설계 감사 결과

| 감사 항목               | 조치                                                                            |
|-------------------------|---------------------------------------------------------------------------------|
| 과잉 설계 걷어내기      | 상세 조회와 리뷰 목록은 규칙 함수로 감싸지 않고 Repository 직통으로 뒀다        |
| 비즈니스 규칙 누락 확인 | 세 기능 모두 데이터 실패와 별도로 규칙 에러 Enum을 정의했다                     |
| 단일 책임 원칙 점검     | 검증, 필터, 정렬은 규칙 함수가 맡는다. Repository에는 조회와 저장 메서드만 있다 |

## 5. 팀 합의가 필요한 가정

| 가정                 | 이유                                                             |
|----------------------|------------------------------------------------------------------|
| 검색어 최소 2글자    | Figma에 표시가 없다. 수업 자료의 예시 값을 따랐다                |
| Rate `4★`의 범위    | "4.0~4.9"인지 "4.0 이상"인지 화면만으로 알 수 없다               |
| Popularity 정렬 기준 | `rating` 기준으로 뒀다. `reviewCount`나 `savedCount`일 수도 있다 |
