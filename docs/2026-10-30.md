# 네트워크 통신

## 용어 정리

- `HTTP`: 웹에서 텍스트, 이미지, JSON 등 다양한 데이터를 주고받기 위한 통신 프로토콜
- `URI`: 인터넷에 존재하는 특정 자원(웹페이지, 이미지, 문서, 파일 등)을 다른 자원과 구별하여 식별할 수 있도록 하는 문자열
- `URL`: 네트워크 상에서 자원이 어디에 위치하는지(주소)를 표시
- `URN`: 위치와 상관없이 자원 자체에 고유한 이름을 부여
- `RESTful API`: 서버와 클라이언트가 메시지를 주고받을 때 가장 많이 사용하는 통신 규격 (암묵적인 룰)
- `네트워크 OSI-7 계층`: 국제표준화기구(ISO)가 네트워크 통신 과정을 7개의 독립된 계층으로 나누어 표준화한 개념적 프레임워크
- `TCP/IP`: 컴퓨터들이 인터넷을 통해 서로 데이터를 주고받을 수 있도록 만드는 통신 표준 규약(프로토콜)의 집합

## 클래스 작성 테스트 코드

```kotlin
class RemoteDataSourceTest {

    // 각 테스트의 given 단계에서 MockEngine이 어떻게 응답할지 정한다
    private var handler: MockRequestHandler = { respondJson(content = "{}") }

    private lateinit var mockEngine: MockEngine
    private lateinit var dataSource: RemoteDataSource

    private fun MockRequestHandleScope.respondJson(
        content: String,
        status: HttpStatusCode = HttpStatusCode.OK,
    ) = respond(content, status, headersOf(HttpHeaders.ContentType, "application/json"))

    @BeforeEach
    fun setUp() {
        mockEngine = MockEngine { request -> handler(request) }
        dataSource = RemoteDataSource(HttpClientFactory.create(mockEngine))
    }

    // 1) 성공 케이스
    @Test
    fun `getPosts는 게시글 목록을 가져온다`() = runTest {
        // given: 서버가 게시글 2개를 반환한다
        handler = {
            respondJson("""[{"userId":1,"id":1,"title":"제목1","body":"내용1"},{"userId":1,"id":2,"title":"제목2","body":"내용2"}]""")
        }

        // when: 게시글 목록을 조회한다
        val response = dataSource.getPosts()

        // then: GET /posts로 요청하고, 2개의 게시글을 받는다
        val request = mockEngine.requestHistory.last()
        assertEquals(HttpMethod.Get, request.method)
        assertEquals("https://jsonplaceholder.typicode.com/posts", request.url.toString())
        assertEquals(200, response.statusCode)
        assertEquals(2, response.body?.size)
    }

    @Test
    fun `getPost는 게시글 하나를 가져온다`() = runTest {
        // given: 서버가 id 1인 게시글을 반환한다
        handler = { respondJson("""{"userId":1,"id":1,"title":"제목","body":"내용"}""") }

        // when: id 1인 게시글을 조회한다
        val response = dataSource.getPost(id = 1)

        // then: GET /posts/1로 요청하고, 게시글을 받는다
        val request = mockEngine.requestHistory.last()
        assertEquals(HttpMethod.Get, request.method)
        assertEquals("https://jsonplaceholder.typicode.com/posts/1", request.url.toString())
        assertEquals(200, response.statusCode)
        assertEquals(Post(userId = 1, id = 1, title = "제목", body = "내용"), response.body)
    }

    @Test
    fun `createPost는 게시글을 생성한다`() = runTest {
        // given: 서버가 id 101로 생성된 게시글을 반환한다
        handler = {
            respondJson("""{"userId":1,"id":101,"title":"네트워크 학습","body":"어려움"}""", HttpStatusCode.Created)
        }

        // when: 게시글을 생성 요청한다
        val response = dataSource.createPost(Post(userId = 1, title = "네트워크 학습", body = "어려움"))

        // then: POST /posts로 요청하고, 서버가 정한 id를 받는다
        val request = mockEngine.requestHistory.last()
        assertEquals(HttpMethod.Post, request.method)
        assertEquals("https://jsonplaceholder.typicode.com/posts", request.url.toString())
        assertEquals(201, response.statusCode)
        assertEquals(101, response.body?.id)
    }

    @Test
    fun `updatePost는 게시글을 수정한다`() = runTest {
        // given: 서버가 수정된 게시글을 반환한다
        handler = { respondJson("""{"userId":1,"id":1,"title":"Network Study","body":"Difficult"}""") }

        // when: id 1인 게시글을 수정 요청한다
        val response = dataSource.updatePost(
            id = 1,
            post = Post(id = 1, userId = 1, title = "Network Study", body = "Difficult"),
        )

        // then: PUT /posts/1로 요청하고, 수정된 게시글을 받는다
        val request = mockEngine.requestHistory.last()
        assertEquals(HttpMethod.Put, request.method)
        assertEquals("https://jsonplaceholder.typicode.com/posts/1", request.url.toString())
        assertEquals(200, response.statusCode)
        assertEquals("Network Study", response.body?.title)
    }

    @Test
    fun `deletePost는 게시글을 삭제한다`() = runTest {
        // given: 서버가 200을 반환한다
        handler = { respondJson("{}") }

        // when: id 1인 게시글을 삭제 요청한다
        val response = dataSource.deletePost(id = 1)

        // then: DELETE /posts/1로 요청하고, 상태 코드 200을 받는다
        val request = mockEngine.requestHistory.last()
        assertEquals(HttpMethod.Delete, request.method)
        assertEquals("https://jsonplaceholder.typicode.com/posts/1", request.url.toString())
        assertEquals(200, response.statusCode)
    }

    // 2) 네트워크 에러 케이스
    @Test
    fun `getPost는 네트워크 에러가 나면 예외를 던진다`() = runTest {
        // given: 서버에 연결할 수 없다
        handler = { throw IOException("서버에 연결할 수 없습니다") }

        // when & then: 조회 요청 시 IOException이 발생한다
        assertThrows<IOException> {
            dataSource.getPost(id = 1)
        }
    }

    // 3) 존재하지 않는 ID 요청 케이스
    @Test
    fun `getPost는 존재하지 않는 id면 null을 반환한다`() = runTest {
        // given: 서버가 404를 반환한다
        handler = { respondJson("{}", HttpStatusCode.NotFound) }

        // when: 없는 id로 게시글을 조회한다
        val response = dataSource.getPost(id = 9999)

        // then: 상태 코드는 404이고, body는 null이다
        assertEquals(404, response.statusCode)
        assertNull(response.body)
    }

    @Test
    fun `deletePost는 존재하지 않는 id면 404를 반환한다`() = runTest {
        // given: 서버가 404를 반환한다
        handler = { respondJson("{}", HttpStatusCode.NotFound) }

        // when: 없는 id로 게시글을 삭제 요청한다
        val response = dataSource.deletePost(id = 9999)

        // then: 상태 코드 404를 받는다
        assertEquals(404, response.statusCode)
    }
}
```

## 정리

- `JSON 개념`
  - 서버-클라이언트 통신에서 표준처럼 사용되는 데이터 교환 형식이다.
  - 가볍고 사람이 읽기 쉽다.
  - `Map` 과 같은 `key-value` 구조
  - 직렬화하여 문자열로 나타내기 쉽다.
  - 대부분의 언어가 이를 파싱할 수 있기 때문에 상호 운용성은 걱정할 것이 없다.

- `HTTP(HyperText Transfer Protocol) 개념`
  - 원래는 문서 전송용으로 설계된 상태 비저장용 프로토콜
  - 브라우저가 `GET` 요청으로 웹 서버의 문서를 읽어오는 용도였다.
  - 지금은 서버와 클라이언트가 텍스트, 이미지, 동영상 등의 데이터를 주고 받을 때 사용하는 프로토콜로 확장되었다.
  - 웹 상에서 보는 이미지, 영상, 파일과 같은 바이너리 데이터도 `HTTP Multipart` 나 `Base64` 인코딩하여 사용한다.

- `HTTP와 함께 사용하는 다른 기술들`
  - `JSON` 등을 `HTTP` 와 함께 사용하는 `RESTful API`
  - `HTTP` 에 `전송 계층 보안(TLS: Transport Layer Security)` 을 더해 만든 `HTTPS`

- `무상태성`
  - `HTTP` 는 상태 비저장 프로토콜
  - `HTTP` 는 요청 메시지를 보내기 직전까지 대상 컴퓨터가 응답 가능한지 알 방법이 없다.
  - `Stateless` 프로토콜, 즉 상태가 없는 프로토콜이라고 한다.
  - `Stateful` 프로토콜로는 `TCP (Transmission Control Protocol)` 가 있다.

- `HTTP 요청과 응답`
  - 모든 `HTTP` 메시지는 요청과 응답이 일대일로 대응되어야 한다.
  - 클라이언트는 항상 자신이 보낸 요청에 대한 응답을 알 수 있어서 로직이 단순해지는 장점이 있다.
  - 클라이언트는 서버로 `HTTP` 요청을 보내기 직전까지 실제로 서버가 동작하는지 알 방법이 없는 단점이 있다.

- `실무에서의 HTTP 응답 없음`
  - 일정 시간 응답이 없을 경우 요청 실패로 간주한다.
  - 실제로 서버가 제대로 처리를 했어도 응답이 늦게 와서 타임아웃이 나는 경우도 있다.
  - Android 의 경우 `10초` 이내, iOS의 경우 `60초` 내 응답이 없으면 타임아웃으로 간주한다.

- `예측이 어려운 HTTP 응답 없음`
  - 서버가 다른 국가에 있는 경우
  - 클라우드 기반의 서버
  - `MockServer` 를 활용한 테스트 필요

- `웹페이지에 접속 시 일어나는 일`
  - 브라우저에서 `https://www.google.com` 을 입력
  - 브라우저가 `https://www.google.com` 으로 접속
  - 페이지 내용이 `HTML` 형식으로 송신
  - 브라우저가 `HTML` 을 파싱하여 화면에 출력

- `Socket을 사용한 저수준 액세스`
  - `TCP/UDP` 를 추상화한 개발자를 위한 API
  - 프로토콜이 아니며, `OSI 7계층` 에 포함되지 않는다.

- `TCP`
  - 신뢰성 있는 연결지향성 앱에서 사용한다. (이메일, 파일 전송, 웹브라우저)
  - `Stateful` 프로토콜
  - 연결되면 연결을 끊기 전까지 계속 메시지를 주고 받는 프로토콜
  - 한쪽에 문제가 생기면 다른쪽에서 감지 가능
  - 텍스트가 아닌 바이너리 데이터를 전송한다.
  - 패킷 크기가 `HTTP` 에 비해 작으며, 속도가 빠르다.
  - 각 요청이 `소켓` 1개를 공유한다. (`HTTP` 는 각 요청이 `소켓` 1개씩 사용한다.)
  - 따라서 요청을 식별할 식별자가 필요하다.
  - 응답을 알 수 있는 방법이 없기 때문에 타임아웃에 대해 직접 구현해야 한다.

- `TCP/IP`
  - `Socket` 을 사용하여 `TCP/IP` 통신을 할 수 있다.
  - 접속하기 위해서 `IP 주소` 와 `포트 번호` 가 필요하다.
  - 프로토콜(통신 시 사용되는 데이터 형식이나 순서 등)은 `RFC` 문서에 정해둔 것을 따른다.
  - 웹페이지 접속, 메일 전송, 게임 등은 모두 `TCP/IP` 를 통한 통신에 의해 이루어 진다.

- `UDP`
  - 신속한 데이터 전송이나 손실 가능성이 있는 상황에 주로 사용한다.
  - 비연결형 프로토콜
  - 데이터 전달 보장이 안되어 신뢰성이 낮다.
  - 흐름 제어가 없으며, 단순하다.
  - 멀티캐스팅 및 브로드캐스팅

- `요청 메서드`
  - 요청의 형태를 정의하는 키워드이다.
  - 원래 `GET` 만 있었으나 계속 확장되었다.
  - `GET` `POST` `DELETE` `PUT` `PATCH` 등이 있다.
  - 상황에 맞게 사용하는 것이 관례이다.
    - `GET`: 데이터 요청
    - `POST`: 데이터가 포함된 요청
    - `DELETE`: 삭제
    - `PUT`: 전부 업데이트
    - `PATCH`: 일부 업데이트

- `GET`
  - 일반적으로 웹 브라우저가 서버에 웹 페이지를 요청할 때 사용한다.
  - 읽기 요청이며, `body` 를 포함할 수 없다.
  - `?` 와 `&` 문자를 사용하는 `쿼리 파라미터` 를 추가할 수 있다.

- `POST`
  - 웹브라우저로 테스트 불가
  - 클라이언트에서 서버로 데이터가 포함된 요청을 보낼 때 사용한다.
  - 로그인, 주문 요청 등이 있다.
  - `쿼리 파라미터` 뿐만 아니라 `body` 로 데이터를 전송한다.

- `DELETE` `PUT` `PATCH`
  - 웹브라우저로 테스트 불가
  - `DELETE` 는 데이터를 삭제할 때 사용한다.
  - `PUT` 은 전체 데이터를 업데이트할 때 사용한다.
  - `PATCH` 는 일부 데이터를 업데이트할 때 사용한다.

- `HTTP 요청 헤더`
  - 요청 정보를 파악하는 데 도움이 되는 다른 여러 정보를 포함할 수 있다.
  - 주로 인증, 캐싱, 클라이언트 힌트, 조건, 연결 관리, 쿠키, CORS 등에 활용된다.
  - `JSON` 파일을 주고 받을 때 `Content-Type` 에 `application/json` 으로 명시한다.

- `상태 코드`
  - 모든 `HTTP` 응답에는 상태 코드와 상태 메시지가 있으며 다음과 같은 예시가 있다.
    - `200 OK`
    - `400 Bad Request`
    - `404 Not Found`
    - `500 Internal Server Error`

- `세션과 쿠키`
  - `HTTP` 는 상태라는 개념이 존재하지 않기 때문에 `세션` 과 `쿠키` 를 사용해 구분한다.
  - 주로 웹에서 `서버` 는 `세션` 그리고 `클라이언트` 는 `쿠키` 를 통해 상태를 저장한다.
  - 모바일에는 없는 개념이다.

- `RESTful API`
  - `REST` 는 분산 시스템을 위한 소프트웨어 아키텍처의 한 형태를 말한다.
  - `RESTful` 이란 `REST` 조건을 만족한다는 것을 의미한다.
  - `요청 주소(URL)` 과 `메서드(GET, POST 등)` `JSON` 규격을 이용하여 API를 정의한다.
  - 오늘날 가장 범용적으로 사용한다.

- `HTTP 통신을 위한 라이브러리`
  - Java의 HttpClient
  - OkHttp, Okio (기존에 Java에서 많이 사용)
  - Retrofit (데이터 소스 자동 작성)
  - ktor-client (Kotlin 공식)
