# 1. 배운 점

## DTO

> 계층 간 또는 네트워크를 통해 데이터를 주고받기 위해 사용하는 데이터 전달용 객체다. 데이터베이스 엔티티나 내부 도메인 모델을 외부에 직접 노출하지 않고, 전송에 필요한 데이터만 맞춤형으로 담아 전달하는 데 목적이 있다.

- DTO는 오직 데이터를 담아 이동시키는 역할만 수행한다.
- 계산, 데이터 검증, 데이터베이스 조회 등 상태나 비즈니스 로직을 포함하지 않고 데이터의 저장 및 조회 구조만 가진다
- DB 테이블과 직접 매핑되는 엔티티(Entity)나 내부 핵심 도메인을 API 응답이나 요청 데이터에 그대로 사용하면, 내부 구조 변경 시 외부 API 스펙까지 영향을 받는다.
- 네트워크를 통해 데이터를 주고받거나 JSON/XML 형태로 변환하기 용이한 구조를 갖는다.
- 엔티티 전체를 노출하지 않고, 특정 요청이나 화면에 필요한 필드만 선택하여 전달할 수 있다. 이를 통해 네트워크 트래픽을 최적화하고, 비밀번호나 개인정보 같은 민감한 데이터의 유출을 방지한다.
- 객체의 내부 필드는 주로 은닉화하며, 접근자와 수정자(Getter/Setter) 또는 불변 생성자 매핑을 통해 데이터에 접근한다.

## Mapper

> 서로 다른 데이터 구조나 계층 간의 객체를 상호 변환해 주는 컴포넌트 또는 패턴이다. 각 계층이 서로의 내부 구현에 직접 의존하지 않도록 격리하고, 데이터 형태나 필드 구성이 다를 때 필요한 변환 로직을 한곳에 모아 깔끔하게 관리하는 역할을 한다.

- 데이터베이스 테이블과 1:1로 매핑되는 엔티티(Entity)와 클라이언트 요청/응답을 처리하는 DTO는 목적과 구조가 다르다. 매퍼는 이 둘 사이의 다리 역할을 하며, 필요한 데이터만 추출하거나 가공하여 안전하게 변환한다.
- 변환 책임을 매퍼로 분리함으로써 비즈니스 로직은 순수하게 유지하고 코드의 가독성을 높인다.

## AI 프롬프트

1. 명확하고 극도로 구체적인 질문을 해야 원하는 결과를 얻을 수 있다.
- AI는 확률 모델 기반이라 질문이 모호하면 빈 공간을 임의로 채워 그럴듯한 거짓말을 하거나 뻔한 답변을 내놓는다.
- 조건과 맥락이 비어 있으면 답변을 수정하고 되묻는 과정에서 시간과 컨텍스트 창(Context Window)이 쓸데없이 소모된다.
- 지시가 구체적일수록 AI가 참조할 지식 체계의 범위가 좁아져 핵심을 정확히 찌르는 답변이 나온다.
2. 같은 유형의 예시만 반복하지 마라
  - 비슷한 예시만 접하면 특정 패턴이나 고정관념에 갇혀 더 넓은 관점, 다양한 맥락, 대안을 놓치게 됨.
- 새로운 통찰이나 데이터 없이 기존 내용이 반복되므로 시간, 노력, 자원이 낭비됨.
- 다양한 변수와 예외 상황을 마주하지 못하고 한 가지 방식에만 과적합(Overfitting)되어 실제 문제 해결 능력이 떨어짐.

### 꿀팁

> 프롬프트 끝에 '역질문'을 달아라

- "내 결정에 대해 비판적으로 반론을 제기하고, 내가 미처 생각하지 못한 엣지 케이스나 누락된 점을 지적해줘."
- 인간은 스스로의 논리적 허점을 발견하기 어려움. AI에게 의도적으로 반박과 누락된 점을 지적하게 만들어 잠재적 리스크나 예외 상황을 사전에 방지함.
- AI는 기본적으로 사용자의 의견에 동조하고 맞추려는(Confirmation Bias) 성향이 강함. 비판적 반론을 명시적으로 요구해야 객관적인 타당성을 점검할 수 있음.
- 정보를 일방적으로 받아오는 수준을 넘어, 내 결정의 타당성을 검증하고 구조적 결함을 짚어주는 날카로운 파트너로 활용하기 위함.
