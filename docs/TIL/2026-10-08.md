## 1. 배운 점

### 코틀린

- `==`: **값** 비교
- `===`: **주소** 비교
- 함수는 무조건 **런타임**에 호출 및 실행
- `Non-null` 타입이라고 해서 무조건 **`null`이 안들어오는건 아님**
  - **리플렉션 주입:** `setAccessible(true)`로 접근 제어 해제 후 메모리에 `null` 주입
  - **강제 형변환 (`as`):** `null`을 가진 `Any?` 값을 `as NonNullType`으로 강제 캐스팅 시 `null` 대입
  - **자바 연동 (Interop):** 자바의 플랫폼 타입(`Type!`) 반환값을 `Non-null` 변수로 수신 시 `null` 대입
  - **초기화 순서 (Init Order):** 부모 생성자/`init` 시점에 자식의 미초기화 `override` 프로퍼티 참조 시 `null` 읽음
  - **`Unsafe` / JNI:** 네이티브(C/C++) 코드나 `Unsafe` API로 메모리 오프셋[^1]에 `null` 직접 덮어쓰기

### Any(Kotlin), Object(Java)

> 코틀린의 `Any`는 자바의 `Object`에 상응하는 최상위 클래스이지만, **코틀린의 널 안전성(Null Safety) 체계와 언어적 깔끔함(3개 메서드)을 반영하여 재설계된 클래스**

| **비교 항목**                   | **Any(Kotlin)**                                                       | **Object(Java)**                                                                            |
| --------------------------- | --------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| **널 허용성 (Nullability)**     | **기본적으로 `null` 불가능 (`non-null`)**<br><br>`null`을 허용하려면 `Any?`로 선언해야 함 | **`null` 허용**<br><br>모든 `Object` 참조 변수는 `null`을 담을 수 있음                                     |
| **원시 타입 (Primitive Types)** | **`Int`, `Boolean` 등 모든 타입의 최상위**<br><br>원시 타입 개념을 포함하는 통합 최상위 타입     | **참조 타입(Reference Type)만의 최상위**<br><br>`int`, `boolean` 등은 `Object`에 직접 담기지 못하고 래퍼 클래스로 박싱됨 |
| **제공 메서드 수**                | **3개** (`equals`, `hashCode`, `toString`)                             | **11개** (`equals`, `hashCode`, `toString` + 쓰레드 동기화 메서드 등)                                  |
| **자바 바이트코드 변환**             | 런타임시 자바의 `java.lang.Object`로 컴파일됨                                     | `java.lang.Object` 자체                                                                       |

### 제네릭

> **타입 안정성(Type Safety)을 보장**하면서 **코드의 재사용성**을 높이기 위해 도입된 기능

- 컬렉션이나 클래스가 처리할 **데이터 타입을 외부에서 지정** 가능
- `타입 추론(Type Inference)`: 인스턴스 생성 시 타입을 명시하지 않아도 **컴파일러가 추론**
- `<T>`만 적으면 기본값으로 `<T: Any?>`로 널을 허용한다 허용하지 않는다면 `<T: Any>`를 쓰자
- `변성(Variance)`: 타입 파라미터 간의 **상하위 관계(서브타이핑)를 제어**
  - `공변성(out)`: **읽기 전용** (자바의 `? extends T`). 하위 타입 할당 허용
  - `반공변성(in)`: **쓰기 전용** (자바의 `? super T`). 상위 타입 할당 허용

- 장점:
  - **컴파일러가 타입을 검증**하므로 명시적 형변환(Casting)이 불필요함
  - 동일한 로직을 타입별로 **중복 작성할 필요 없이** 하나의 제네릭(`T`)으로 처리함

- 단점:
  - 원시 타입(Primitive Type) 사용 시 박싱, 언박싱 과정에서 메모리, CPU 비용이 발생함

- JVM 타입 소거 (Type Erasure):
  - **타입별 클래스를 각각 생성하지 않고** 단 **하나의 클래스만 공유**하여 메타스페이스 부담을 줄임
  - 이전 **자바코드(레거시) 호환성**을 위해 컴파일 완료 후 제네릭 **타입 정보를 제거**(`Object` 또는 `<T : Number>`의 경우 `Number`로 치환)함
  - **런타임 제약**: 런타임에는 **실체화된 타입 정보가 없어** `List<String>`과 `List<Int>`를 구별하거나 `instanceof` 검사가 불가능

| **비교 항목**    | **오브젝트 타입 (Object / Any)**                                | **제네릭 (Generics)**                                 |
| ------------ | --------------------------------------------------------- | -------------------------------------------------- |
| **개념**       | 모든 객체의 최상위 클래스를 활용해 다양한 타입을 받아옴                           | 타입을 선언 시점이 아닌 **사용 시점에 지정**할 수 있도록 추상화             |
| **타입 안정성**   | **낮음**<br><br>(컴파일러가 내부 실체 타입을 알지 못함)                     | **높음**<br><br>(컴파일 시점에 정해진 타입만 들어오도록 강제)           |
| **오류 발견 시점** | **런타임**<br><br>(잘못된 타입 입력 시 실행 중 `ClassCastException` 발생) | **컴파일 타임**<br><br>(잘못된 타입 사용 시 빌드 단계에서 즉시 에러 발생)   |
| **명시적 캐스팅**  | **필요함**<br><br>(`(String) obj` 형태로 값을 꺼낼 때마다 형변환 필요)      | **불필요함**<br><br>(컴파일러가 타입을 알고 있어 자동으로 처리)          |
| **코드 가독성**   | 캐스팅 코드가 반복되어 난잡해질 수 있음                                    | 타입 파라미터(`T`) 명시로 데이터 흐름과 타입 구분이 명확함                |
| **대표 활용 예시** | 타입에 관계없이 완전히 임의의 객체를 다뤄야 할 때                              | 컬렉션 프레임워크(`List<T>`, `Map<K, V>`), 공통 응답 Wrapper 등 |

### 열거형 클래스 (enum class)

> 일반적으로 문자열(`"MON"`, `"TUE"`)이나 숫자(`0`, `1`, `2`)로 상수를 다루면 **오타가 발생하거나 유효하지 않은 값**이 들어오는 위험이 있음 열거형은 이를 방지하고 **코드를 안전하게 관리하기 위해** 등장

- **서로 연관된 고정된 상수(Constant)들의 집합**을 정의하기 위해 사용하는 특별한 데이터 타입
- **가지고 있는 값이 명확하게 정해져 있고 변하지 않는 경우**에 주로 사용
- **정해진 값 외에는 변수에 할당할 수 없어**, 잘못된 값이 입력되는 실수를 컴파일 시점에 차단
- **단순한 이름 이상의 정보(값, 설명 등)를 내부에 프로퍼티**로 가질 수 있고, **전용 함수를 정의할 수도 있음**
- 각각의 enum 상수는 프로그램 전체에서 **싱글톤[^2]으로 관리**
- 각 상수가 갖는 부가 데이터나 관련 동작을 **한곳에 묶어서 관리**

- 장점:
  - 숫자 `1`이 무엇을 뜻하는지 추측할 필요 없이 `Status.APPROVED`처럼 **의미가 명확하게 드러남**
  - 오타나 엉뚱한 값이 들어갈 수 없어 **런타임 버그를 줄여줌**
- 단점:
  - **런타임에 새로운 상수를 추가하거나 변경할 수 없음** 데이터가 유연하게 늘어나는 경우에는 적합하지 않음

| **구분**     | **상수**             | **열거형 (enum class)**  |
| ---------- | ------------------ | --------------------- |
| **타입 안정성** | 없음 (아무 정수나 입력 가능)  | 높음 (정해진 enum 값만 가능)   |
| **가독성**    | 변수명을 직접 참조해야 함     | 클래스명과 상수명이 명확함        |
| **오타 방지**  | 문자열 사용 시 런타임 에러 가능 | 컴파일 시점에 에러 감지         |
| **부가 기능**  | 단순 값 보관            | 프로퍼티, 함수, 인터페이스 구현 가능 |

### Accessor, Mutator

- Accessor (접근자, ex) getter):
  - 객체 내부의 데이터를 **읽어올 때** 사용
- Mutator (설정자, ex) setter):
  - 객체 내부의 데이터를 **수정하거나 저장할 때** 사용

### 3. 트러블 슈팅

#### Kotlin + JUnit 5 `@Nested` 클래스 내 `@MethodSource` 데이터 탐색 실패 해결

##### 1. 문제 상황
- `@Nested inner class` 내부의 `@ParameterizedTest`에 `@MethodSource("provideData")`를 적용하였으나, 데이터 공급 **메서드를 찾지 못하는 예외 발생**
- 에러 메시지: `Could not find factory method [provideData] in class [PerMethodLifecycleTest$Test]`

###### 초기코드
```kotlin
@Nested  
inner class Test {  
    @ParameterizedTest  
    @MethodSource("provideData")  
    fun `test1`(input: String) {  
        // ...
    }
}  
  
companion object {
    fun provideData(): List<String> {  
        // ...
    }  
}
```

##### 2. 원인 분석 및 시행착오

1. **`@JvmStatic` 적용 후에도 동일 에러 발생**
  - 디컴파일을 통해 `companion object`가 바이트코드상 **별도의 static class(`$Companion`)로 분리됨을 확인**
  - `provideData()`에 **`@JvmStatic`을 부여**하여 외부 클래스 **자바 `static` 메서드를 생성**했음에도 동일한 에러 메시지 지속

2. **JUnit 5의 Scope 탐색 제약**
  - `@MethodSource("메서드명")`은 **현재 실행 중인 클래스 내부만 탐색**함
  - **외부 클래스는 자동 추적하지 않으며**, 외부 클래스 메서드는 **FQCN(전체 경로) 문자열 형태(`"패키지.OuterClass#method"`)로만 참조** 가능함
  - 기본 생명주기(`PER_METHOD`)에서는 **인스턴스 생성 전 데이터 수집**을 위해 `static`이 필수
  - 참고 링크: [Junit5 MethodSource](https://docs.junit.org/6.1.3/api/org.junit.jupiter.params/org/junit/jupiter/params/provider/MethodSource.html)

##### 3. 최종 해결 방안: `@TestInstance(PER_CLASS)` 적용

- 외부 `companion object`에 `@JvmStatic` 함수를 작성하는 방식은 테스트 케이스와 데이터가 분리되어, 테스트 함수가 늘어날수록 **가독성과 유지보수성이 크게 떨어지는 단점**이 있음
- 따라서 `@Nested inner class`에 `@TestInstance(Lifecycle.PER_CLASS)`를 부여하여 데이터 **공급 메서드를 테스트 클래스 내부에 작성**하여 깔끔하게 작성

```kotlin
@Nested
@TestInstance(TestInstance.Lifecycle.PER_CLASS) // 추가 코드
inner class Test {
  @ParameterizedTest
  @MethodSource("provideData")
  fun `test1`(input: String) {
    // ...
  }

  // 추가 코드
  fun provideData(): List<String> {
    // ...
  }
}  
```

[^1]: `메모리 오프셋`: 기준이 되는 시작 주소로부터 특정 데이터나 위치까지 떨어진 거리(상대적 위치)

[^2]: `싱글톤`:  **객체(인스턴스)가 오직 1개만 생성되도록 보장**하고 어디서든 그 객체에 접근할 수 있도록 전역 접근점을 제공
