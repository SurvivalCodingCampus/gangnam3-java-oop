## 1. 배운 점

### 코틀린

- `let`: 널이 아니면 블록 안의 코드를 실행
- 자바와 달리 **Checked Exception을 구분하지 않고 모두 Unchecked Exception**으로 다룬다
  - 예외를 처리(`try-catch`)하지 않고 그대로 두면 프로그램이 실행되는 동안 **발생한 예외가 상위 호출자 쪽으로 계속해서 전파**
  - 보일러플레이트(반복) 코드를 만든다고 판단하여 **언체크 예외 단일 체계**를 채택

### 에러

> **프로그램이 의도대로 동작하지 않거나 실행 자체를 방해하는 모든 치명적인 문제 상황**

- 개발자가 코드로 **수습할 수 없는 수준**의 문제이므로 일반적으로 프로그램이 종료

| **구분**    | **구문 에러 (Syntax Error)**                      | **런타임 에러 / 예외 (Runtime Error / Exception)**         | **로직 에러 (Logic Error)**           |
| --------- | --------------------------------------------- | --------------------------------------------------- | --------------------------------- |
| **원인**    | **코드의 오타나 문법적 형식 오류** (예: 세미콜론 누락, 괄호 짝 안 맞음) | 문법은 맞지만 실행 중에 **0으로 나누기, 파일 없음, 잘못된 메모리 접근 등**이 발생함 | 알고리즘이나 계산 방식에 **실수가 있음**          |
| **특징**    | **컴파일조차 되지 않아** 실행 화면을 보기도 전에 발견              | 실행 중에 프로그램이 **강제 종료**                               | 예상치 못한 **엉뚱한 결과값**이 나옴            |
| **해결 방법** | 컴파일러의 지적을 보고 수정                               | 에러 메시지와 발생 지점을 파악하여 **예외 처리 및 방어 코드 작성**            | 원인을 **스스로**(디버깅 등을 통해) 찾아서 해결해야 함 |

### 예외

> 프로그램이 **실행 중**에 **예상치 못한 상황**이 발생하여 **정상적인 흐름이 중단**되는 현상

- 개발자가 **코드로 예외 처리를 통해 복구하거나 대처할 수 있는** 대상

##### 주요 원인

- **사용자 및 데이터 요인:** 개발자가 예상하지 못한 잘못된 입력값 제공
- **프로그램 결함 요인:** 존재하지 않는 메모리에 접근하거나 허용된 범위를 넘어선 작업 수행
- **외부 환경 요인:**
  - 파일 시스템의 부재
  - 네트워크 연결 끊김
  - 서버 다운 등 프로그램 외부의 문제

##### 대표적인 예외 종류

- 메모리 부족
- 네트워크 통신 에러
- 파일없음
- 인덱스 범위 초과
- NPE

#### 예외 처리

> 프로그램 **실행 중** 발생할 수 있는 예외 상황에 **미리 대비**하여 프로그램이 강제 종료되지 않고 **정상적인 흐름을 유지하거나 안전하게 대처**할 수 있도록 코드를 작성하는 것

- `try` 블록:  예외가 발생할 가능성이 있는 코드를 작성
- `catch` 블록: 예외가 발생했을 때 **프로그램이 멈추는 대신 실행할 대처 코드**를 작성
- `finally` 블록: **예외 발생 여부와 상관없이 무조건 실행**해야 하는 마무리 코드를 작성

#### Throwable

> 자바에서 **에러와 예외**를 처리하는 **최상위 루트 클래스**

- **주요 하위 클래스**:
  - **`Error`**: 시스템에 비정상적인 **심각한 문제**가 발생했을 때 발생(`OutOfMemoryError`,  `StackOverflowError`)
  - **`Exception`**: 개발자가 구현한 **로직의 실수나 예외적인 상황**(사용자의 잘못된 입력, 존재하지 않는 파일 등)으로 인해 발생

##### 예외의 두 가지 종류

> 가장 중요한 구분 기준은 **컴파일 시점에 체크**를 하느냐(Checked), 안 하느냐(Unchecked) 차이

| **구분**        | **Error**                                | **Checked Exception**                                   | **Unchecked Exception**                                                    |
| ------------- | ---------------------------------------- | ------------------------------------------------------- | -------------------------------------------------------------------------- |
| **상위 클래스**    | `Throwable`                              | `Exception`                                             | `RuntimeException` (`Exception` 하위)                                        |
| **발생 시점**     | 컴파일/실행 시 (시스템 레벨)                        | 컴파일 시                                                   | 실행 시 (Runtime)                                                             |
| **예외 처리 강제성** | 강제 아님 (처리 불가)                            | **필수** (안 하면 컴파일 에러)                                    | 선택 (필요시 try-catch)                                                         |
| **주요 원인**     | 시스템의 비정상적인 심각한 문제 (메모리 부족, 하드웨어 결함 등)    | 외부 환경과의 상호작용 (네트워크 끊김, 파일 없음, 잘못된 DB 접근 등)              | 개발자의 부주의나 로직 오류 (Null 참조, 잘못된 인덱스 접근, 0으로 나누기 등)                           |
| **대표 예시**     | `OutOfMemoryError`, `StackOverflowError` | `IOException`, `SQLException`, `ClassNotFoundException` | `NullPointerException`, `IndexOutOfBoundsException`, `ArithmeticException` |
| **대응 방법**     | 프로그램 종료 후 원인 파악 및 시스템 개선                 | 예외 복구 로직 작성 (`try-catch` 또는 `throws`)                   | 로직 수정 및 방어 코드 작성                                                           |

##### 자원 해제 방법 `close()`

> 파일을 열거나 스트림을 사용할 때는 **시스템 자원[^2]을 점유**하게 됨 작업이 끝나면 **반드시 `close()`를 호출**해서 자원을 반환해야 **메모리 누수(Memory Leak)나 파일 잠금(Lock)** 같은 문제를 막을 수 있음

**try-finally(Java)**

- 직접 `finally` 블록에서 수동으로 자원을 닫아주어야 해서 코드가 길고 번거로움

```kotlin
val stream = Files.newInputStream(path)
try {
    // 작업
} finally {
    stream.close() // 깜빡하기 쉽고 코드가 길어짐
}
```

**try-with-resources(Java)**

- `Closeable` 또는 `AutoCloseable` 인터페이스를 구현한 객체만 넣을 수 있음
  - `Closeable`:
    - 오래전부터 있던 인터페이스로 **입출력(I/O) 스트림**(`InputStream`, `OutputStream`, `Reader`, `Writer` 등) 전용으로 만들어졌음
    - `close()` 메서드는 반드시 `IOException`을 던지도록 선언되어 있음
  - `AutoCloseable`:
    - `try-with-resources` 문법과 함께 등장한 **더 넓은 범위의 상위 인터페이스**
    - 파일이나 입출력이 아니더라도 데이터베이스 연결(`Connection`)이나 네트워크 소켓 등 다 **쓰고 나서 반납해야 하는 모든 종류의 자원을 포괄하기 위해** 만들어졌음
    - `close()` 메서드가 예외(`Exception` 또는 `Throwable`)를 던질 수 있도록 더 유연하게 설계

```kotlin
// try 뒤의 괄호 안에 자원을 선언
try (var reader = Files.newBufferedReader(Path.of("example.txt"))) {
    System.out.println(reader.readLine());
    // try 블록이 끝나면 close() 호출
} catch (IOException e) {
    e.printStackTrace();
}
```

**.use(Kotlin)**

- 자바의 `try-with-resources`를 코틀린 스타일의 람다와 확장 함수로 포장한 자원 해제 방식

```kotlin
Files.newInputStream(path).use { stream ->
    // 작업
    // 블록이 끝나면 알아서 close()가 호출
}
```

### 직렬화

> 객체나 데이터 구조를 **연속적인 데이터 흐름(Stream)(바이트배열이나 문자열)으로 변환하는 과정**

- 객체는 복잡한 구조를 가지고 있어서 **다른 컴퓨터로 네트워크를 통해 보내거나 하드디스크에 파일로 그대로 저장할 수 없음**

### 역직렬화

> 직렬화된 데이터(문자열이나 바이트)를 다시 **원래의 객체나 데이터 구조로 복원하는 과정**

- 네트워크를 통해 전달받은 데이터나 파일에 저장된 JSON 등을 프로그램이 다시 읽어들여 **코드에서 곧바로 사용할 수 있는 객체(인스턴스) 형태로 되돌리는 것**

### 스트림 종류

##### Java.io

- **바이트 기반** 스트림(`InputStream` / `OutputStream`)
  - 데이터를 **1바이트(byte) 단위**로 입출력
  - 텍스트뿐만 아니라 **이미지, 동영상, 압축파일, 실행파일 등 모든 종류의 바이너리 파일**을 다룰 때 사용
- **문자 기반** 스트림(`Reader` / `Writer`)
  - 자바는 한 문자를 **2바이트(유니코드)**로 처리하기 때문에 바이트 스트림으로 텍스트를 읽으면 한글이 깨질 수 있음 이를 해결하기 위해 **문자(Character) 단위**로 데이터를 처리하도록 만든 스트림
  - 오직 **텍스트 파일**(`.txt`, `.json`, `.html` 등)을 다룰 때 사용

- **버퍼기반** 스트림(`BufferedInputStream` / `BufferedOutputStream` / `BufferedReader` / `BufferedWriter`)
  - 입출력 장치(하드디스크, 네트워크 등)에 매번 직접 접근하는 대신 속도가 빠른 **메모리 버퍼**에 데이터를 모아두었다가 **한 번에 읽고 쓰도록** 만든 보조 스트림
  - 디스크 접근 횟수와 시스템 콜(System Call)을 줄여주어 **입출력 속도를 향상**
##### Java.nio

> NIO(New Input/Output)는 자바 4(JDK 1.4)부터 **기존 자바 IO의 성능 한계를 극복**하기 위해 도입된 **새로운 입출력 API**

- `채널(Channel)`:
  - 기존 IO의 **스트림이 단방향**이었던 것과 달리 **채널은 양방향(Read/Write 동시 가능)으로** 데이터가 흐름
  - 파일 채널(`FileChannel`), 네트워크 통신을 위한 소켓 채널(`SocketChannel`, `ServerSocketChannel`) 등이 있음

- `버퍼(Buffer)`:
  - NIO는 데이터를 처리할 때 **무조건 버퍼를 거쳐서** 움직임
  - `ByteBuffer`, `CharBuffer`, `IntBuffer` 등 **다양한 타입의 버퍼를 제공**하며, 스트림과 달리 **버퍼 내부에서 앞뒤로 자유롭게 이동**(`position`, `limit` 조절)하며 필요한 부분만 골라 읽고 쓸 수 있는 **유연성**을 제공

- `셀렉터 (Selector)` - 네트워크의 핵심
  - **넌블로킹(Non-Blocking)** 입출력을 가능하게 하는 핵심 요소
  - 하나의 **스레드**가 **여러 개의 채널(연결)을 모니터링(멀티플렉싱)**하고 있다가 **"데이터 읽기/쓰기 준비가 완료된" 채널만 쏙쏙 골라서 처리**할 수 있게 해줌
  - 덕분에 수천, 수만 개의 클라이언트가 접속하는 채팅 서버나 웹 서버를 **적은 수의 스레드로 고효율 관리할 수 있음**

| **구분**       | **기존 자바 IO (Streams)**                           | **자바 NIO (New IO)**                                        |
| ------------ | ------------------------------------------------ | ---------------------------------------------------------- |
| **기본 단위**    | **스트림 (Stream)** 기반<br><br>(단방향: 입력/출력 분리)       | **채널과 버퍼 (Channel & Buffer)** 기반<br><br>(양방향: 읽기/쓰기 동시 가능) |
| **버퍼 사용 여부** | 선택적<br><br>(필요하면 개발자가 `Buffered~`를 붙임)           | **필수적**<br><br>(데이터를 읽을 때 무조건 Buffer를 거침)                  |
| **블로킹 여부**   | **블로킹 (Blocking)**<br><br>(읽고 쓸 때 끝날 때까지 스레드 대기) | **블로킹 / 넌블로킹 (Non-Blocking) 모두 지원**                        |
| **주요 활용**    | 대용량 순차 파일 처리                                     | 네트워크 서버, 대규모 동시 접속 처리, 고성능 파일 관리                           |

##### 코틀린 입출력 함수
- `File.readText()`:
  - 파일을 열어 **버퍼**를 통해 읽지만 최종적으로 **전체 문자열 한 번에 메모리에 올림**
  - 내부적으로 문자셋(Charset, 기본값 UTF-8)을 처리하며 버퍼를 통해 처리
  - 파일 용량이 너무 크면 `OutOfMemoryError(메모리 부족)`가 발생할 수 있으므로 **대용량 파일에는 적합하지 않음**

- `File.writeText()`:
  - 문자열을 지정된 문자셋(Charset, 기본값 UTF-8)의 **바이트로 변환**한 뒤 파일에 씀
  - 내부적으로 문자셋(Charset, 기본값 UTF-8)을 처리하며 버퍼를 통해 처리
  - 파일이 없으면 새로 만들고 이미 존재하면 **기존 내용을 덮어쓴다(Overwrite)**
    이어 쓰기(Append)를 원할 때는 `append-` 계열 함수를 사용

##### Path 클래스

> 컴퓨터 파일 시스템 내의 **파일이나 디렉토리의 경로(위치)를 나타내는 객체

- `Path`를 사용하면 OS 맞게 경로 구분자를 넣어줘 안전한 경로 조작 가능
- **`Files` 클래스**와 함께 사용
  - 코틀린에선 **Java NIO** 기반의 **Path 관련** 확장함수[^1]가 구현되어 있어 `path.파일조작함수()`로 사용이 가능

### 데이터형식

> 데이터를 **효율적으로 저장, 처리**하고 **서로 다른 시스템이나 프로그램 간에 정보를 원활하게 주고받기 위해** 정해둔 일종의 **규칙과 구조**

| **구분**    | **CSV**            | **XML**                | **JSON**                   |
| --------- | ------------------ | ---------------------- | -------------------------- |
| **형태**    | 쉼표로 구분된 텍스트        | 태그(`<>`) 기반의 계층 구조     | 키-값 쌍의 객체 구조 (`{ }`)       |
| **장점**    | 용량이 작고 엑셀에서 열기 쉬움  | 구조가 명확하고 복잡한 데이터 표현 가능 | 가볍고 읽기 쉬우며 현대 웹 표준에서 널리 쓰임 |
| **단점**    | 복잡한 구조 표현 불가능      | 문법이 장황하고 용량이 큼         | 주석을 지원하지 않음                |
| **주요 용도** | 대용량 데이터 저장 및 엑셀 연동 | 레거시 시스템, 문서 설정 파일      | 웹/앱 API 통신, 데이터 교환         |
|           |                    |                        |                            |

- **런타임 리플렉션(Reflection) 없음**:
  - Gson이나 Jackson처럼 실행 중에 **리플렉션을 사용해 객체 구조를 분석하지 않음**
  - 대신 **컴파일 타임에 컴파일러 플러그인**이 **직렬화 코드를 미리 생성**하므로 실행 속도가 매우 빠르고 **메모리 오버헤드가 적음**

- **Kotlin 타입 시스템 완벽 지원**:
  - Kotlin의 `val`, `var`, 기본값(Default values), Nullable/Non-null 타입(`?`), 제네릭 등을 언어 **문법 수준에서 안전하게 지원**

- **멀티플랫폼(KMP) 지원**:
  - JVM(Android, 서버)뿐만 아니라 Kotlin/JS, Kotlin/Native(iOS 등) 환경에서도 **동일한 코드로 동작**

- **다양한 포맷 지원**:
  - 기본적으로 **JSON**(`kotlinx-serialization-json`)이 가장 널리 쓰이며 이외에도 Protocol Buffers, CBOR, HOCON 등을 지원
