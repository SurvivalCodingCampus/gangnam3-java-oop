## 1. 배운 점

### 디버깅

> 소프트웨어나 하드웨어 시스템에서 오류(버그)를 찾아내고 그 **원인을 분석하여 수정하는 모든 과정**

1. 디버깅이 필요한 이유
    - 프로그램이 **멈추거나(크래시) 엉뚱한 결과값**을 낼 때 **정상적으로 작동하도록** 바로잡음
    - **예상치 못한 예외 상황이나 보안 취약점을 미리 발견**하여 **프로그램의 안정성**을 높임
    - 코드가 어떻게 실행되고 데이터가 어떻게 흘러가는지 **흐름을 파악하는 데 도움이 됨**

2. 일반적인 디버깅 진행 순서
    1. 오류가 어떤 상황에서 발생하는지 **반복해서 확인**
    2. 에러 메시지(로그)를 읽거나 코드를 추적하여 문제가 발생한 **정확한 위치를 파악**
    3. **원인 부분을 고침**
    4. 수정한 뒤에도 프로그램이 **올바르게 동작하는지 다른 부작용(사이드 이펙트)은 없는지 테스트**

3. 자주 쓰이는 디버깅 방법
    - 코드 중간중간에 변수 값을 출력해 보며 원하는 대로 값이 들어오고 있는지 **눈으로 직접 확인**
    - IDE에 내장된 도구를 활용해 코드의 **특정 지점(중단점)에서 실행을 멈추고 한 줄씩 코드를 실행하며 변수의 변화를 실시간으로 관찰**
    - 서버나 프로그램이 기록해 둔 오류 **기록(Log)을 분석**하여 원인을 유추

### 메서드와 함수 차이

> 메서드와 함수 둘 다 어떤 **로직을 처리하는 코드의 묶음**이라는 점에서 본질은 같지만 **소속에 따라 부르는 이름이 다름**

1. 함수
    - **독립적으로 존재하는 코드의 집합**
    - 특정 클래스나 객체에 **종속되지 않고 단독으로 존재하며 호출가능**

2. 메서드
    - **객체나 클래스, 인터페이스 내부에 속해 있는 함수**
    - **객체의 상태(속성/필드)를 조작하거나 객체의 행위를 정의하는 데 사용**
    - **반드시 객체나 클래스**를 통해 호출

### 람다식과 함수

#### 1급 객체

> 다른 객체들에 **일반적으로 적용 가능한 연산을 모두 지원하는 객체**
> 함수도 1급 객체

1. 1급 객체의 조건
    - **변수나 데이터 구조(배열, 객체 등)에 담을 수 있어야 함**
        - 함수나 데이터를 **변수에 자유롭게 할당**할 수 있음
    -  함수의 **매개변수로 전달**할 수 있어야 함
        - 다른 함수를 호출할 때 **인자로 넘겨줄 수 있음**(콜백 함수)
    -  함수의 **반환값(리턴값)으로 사용**할 수 있어야 함
        - 함수가 **실행된 결과로 또 다른 함수나 객체를 반환**할 수 있음(클로저)

2. 1급 객체가 주는 장점
    - 로직을 **함수 단위로 쪼개고 조합하기 쉬워짐**
    - 함수를 데이터처럼 다룰 수 있게 되므로 맵(Map), 필터(Filter), 리듀스(Reduce) 같은 **선언형 프로그래밍 기법을 활용할 수 있음**

### 람다식

> 람다식(Lambda Expression)이란 이름이 따로 없는 **익명 함수(Anonymous Function)의 한 형태로 프로그래밍에서 함수를 간결하고 직관적으로 표현하기 위한 문법**

- 이름이 없고 **일회용 함수를 만들거나 다른 함수의 인자**로 곧바로 넘겨줄 때 주로 사용
- **불필요한 함수 선언(이름, `fun` 키워드, 반환 타입 등)을 생략**할 수 있어 가독성이 좋아짐
- 람다 덕분에 **함수를 변수에 넣거나 다른 함수의 매개변수**로 자유롭게 넘겨줄 수 있게 되었음
- 넓은 의미에서 **람다식은 익명 함수의 한 종류**
- 코틀린이나 자바 같은 언어에서는 컴파일될 때 **내부적으로 최적화**되어 동작하도록 설계

#### 람다/다형성

| **기준**     | **람다 (함수형 접근)**              | **객체지향 다형성 (클래스/인터페이스)**        |
| ---------- | ---------------------------- | ------------------------------- |
| **주요 목적**  | 행위(Algorithm)의 전달 및 파라미터화    | 데이터와 행위의 캡슐화 및 타입 계층 구조화        |
| **상태 관리**  | 무상태(Stateless)에 적합           | 상태 유지(Stateful) 및 복잡한 객체 관계에 적합 |
| **코드 양**   | 매우 적음 (Boilerplate 최소화)      | 상대적으로 많음                        |
| **적합한 패턴** | 전략 패턴(간단한 경우)[^1], 콜백 함수<br> | 복잡한 비즈니스 로직, 대규모 도메인 모델         |

### 람다식 표현 방법

- 람다식 or 람다 표현식
```kotlin
val sum: (Int, Int) -> Int = { a, b -> a + b }
```

1. 단일 매개변수 람다
    - 람다의 매개변수가 하나인 경우 **매개변수를 생략하고 it**를 사용할 수 있다
```kotlin
val square: (Int) -> Int = { it * it }
```

1. 후행 람다
    - 함수의 **마지막 인자가 람다일 경우 함수 호출 소괄호 밖에 람다**를 작성할 수 있다
```kotlin
// repeat(3, { println(it) })
repeat(3) {  
    println(it)  
}
```

1. 입출력 타입만 같다면 같은 함수로 볼 수 있다
    - `forEach`가 요구하는 타입은`(Int) -> Unit`
    - `printElements`가 요구하는 타입도 `(Int) -> Unit`

2. **`::` 함수 참조**
    - `printElements`는 원래 그냥 일반적인 `fun` 선언일 뿐이라 **곧바로 값처럼 쓸 수 없음**
    - 이 일반 함수를 **람다식(또는 함수 객체)처럼 다루겠다는 뜻**
```kotlin
fun main() {  
    val list = listOf(1, 2, 3)  
    list.forEach(::printElements)
}  
  
fun printElements(elements: Int) {  
    println(elements)  
}
```

### 클로저/캡쳐

1. **캡처(Capture)**
    - 람다식이나 익명 함수가 선언될 때 **주변 스코프에 있는 외부 변수를 내부로 끌어와 참조**하는 메커니즘

2.  **클로저(Closure)**
    - 외부 함수의 실행이 종료되어 **스택 프레임이 사라졌음에도 불구하고 람다가 캡처한 변수의 참조를 계속 유지하며 접근할 수 있는 상태**

클로저 예시
```kotlin
fun main() {  
    var result = 4  
    calc(6, 4) { x, y -> result += x + y } // result캡처, 클로저  
    println(result) // 값 유지로 14}  
  
fun calc(a: Int, b: Int, operation: (Int, Int) -> Unit) {  
    operation(a, b)  
}
```

- **Java:**
    - 람다 안에서 외부 **지역 변수를 읽을 수는 있지만 값을 변경하는 것은 불가능**
      (`effectively final` 제약)
    - **컴파일 시점에 값을 복사해서 가져오기 때문에 동기화 문제가 생길 수 있어 언어 차원에서 막음**

- **Kotlin:**
    - `val`은 읽기 전용으로 안전하게 쓰고 `var`는 람다 안에서 값 변경이 가능
    - 컴파일러가 뒤에서 **프리미티브 변수를 `Ref` 같은 래퍼 객체로 감싸서(Boxing) 힙(Heap) 메모리에 공유하도록 만들어줌**

#### 클로저 사용 장점

| **상황**      | **클로저 미사용 시**                | **클로저 사용 시**                    |
| ----------- | ---------------------------- | ------------------------------- |
| **상태 유지**   | 전역 변수를 쓰거나 클래스/객체를 새로 만들어야 함 | 함수 내부의 `var` 변수를 캡처하여 가볍게 상태 유지 |
| **비동기/이벤트** | 매번 인스턴스나 인터페이스 구현체를 전달해야 함   | 람다 형태로 문맥(Context)을 간단히 전달      |

### 함수형 인터페이스/SAM 인터페이스

> **Functional Interface(함수형 인터페이스)** 또는 SAM 인터페이스(Single Abstract Method Interface)는 객체지향 언어에서 **람다식을 원활하게 사용할 수 있도록 만들어주는 핵심 개념**

- **SAM**은 **Single Abstract Method**의 약자로 이름 그대로 **추상 메서드가 딱 하나만 존재하는 인터페이스**
- Java나 Kotlin 같은 **객체지향 언어에서는 모든 코드가 클래스나 객체 안에 있어야함** 하지만 **함수 자체를 인자로 넘기고 싶을 때(람다식) 순수 객체지향 언어는 이를 곧바로 받아들일 수 없음**
- 이때 **추상 메서드가 딱 하나뿐인 인터페이스라면 그 람다식을 이 인터페이스의 구현체로 쳐줄게!"라는 규칙**을 만든 것이 바로 SAM 인터페이스

### 무명클래스 → 람다식 → 후행 람다 → 각종 생략 과정

```kotlin
// SAM 인터페이스
fun interface OnClickListener {  
    fun onClick(message: String)  
}  

fun setButtonClickListener(listener: OnClickListener) {  
    listener.onClick("버튼이 클릭되었습니다!")  
}
```

1. 무명클래스
    - 객체를 생성하면서 **즉석에서 메서드를 오버라이드**
```kotlin
setButtonClickListener(object : OnClickListener {
	override fun onClick(message: String) {
		println(message)
	}
})
```

2. 람다식
    - 인터페이스가 SAM 인터페이스(추상 메서드가 1개)이므로 **컴파일러가 이를 알아서 인식**
```kotlin
setButtonClickListener(
	OnClickListener { message: String -> 
		println(message) 
	}
)
```

3. SAM 변환 및 파라미터 타입 생략
    - 코틀린 컴파일러는 `setButtonClickListener`가 `OnClickListener`를 원한다는 것을 **이미 알고 있음 따라서 인터페이스 이름도 생략할 수 있고 파라미터 타입(`String`)도 문맥상 유추할 수 있어 생략 가능**
```kotlin
setButtonClickListener({ message -> 
	println(message) 
})
```

4. 후행 람다 (Trailing Lambda) 적용
    - 코틀린의 규칙 중 하나로 **함수의 마지막 파라미터가 람다라면 소괄호 `()` 바깥으로 빼낼 수 있다**
```kotlin
setButtonClickListener() { 
	message -> println(message) 
}
```

5. 소괄호 생략
    - 함수의 파라미터가 **오직 람다 하나뿐**이라면 소괄호 자체를 통째로 생략
```kotlin
setButtonClickListener { message -> 
	println(message) 
}
```

6. 단일 파라미터 `it` 생략
    - 람다의 파라미터가 **딱 1개**뿐이라면 파라미터 **선언부(`message ->`)마저 생략**하고 자동으로 제공되는 **키워드 `it`로 대체**
```kotlin
setButtonClickListener { 
	println(it) // message 대신 it 사용 
}
```

7. 미사용 파라미터 생략
    - 사용하지 않는 파라미터는 관례적으로 **언더바(`_`)로 대체하여 쓰지 않겠다"**고 명시
    - 화살표를 쓰지않아도 가능
```kotlin
setButtonClickListener { _ -> 
	println("안녕") 
}

setButtonClickListener {
	println("안녕") 
}
```

### 인터페이스 생략

```kotlin
// 인터페이스 삭제
//fun interface OnClickListener {

//}

// 파라미터로 함수 타입(String) -> Unit)를 직접 받음
fun setButtonClickListener(action: (String) -> Unit) {
    // 함수를 직접 실행
    action("버튼이 클릭되었습니다!")

fun main() {
    // 바로 람다식을 작성
    setButtonClickListener { message ->
        println(message)
    }
}
```

### 콜백함수

> 어떤 작업이 끝났거나 **특정 이벤트가 발생했을 때 시스템(또는 다른 함수)이 나중에 다시 호출(Call back)해 주는 함수**

1. 비동기 처리 및 이벤트 핸들링
    - **네트워크 요청, 파일 읽기, 버튼 클릭 등 "언제 끝날지 모르는 작업"을 처리할 때 필수적** 작업이 끝나는 시점을 알 수 없으니 콜백을 등록해 두고 완료 시점에 실행

2. 코드의 유연성(로직의 분리)
    - **데이터를 가져오는 로직은 공통**으로 두고 **가져온 데이터를 어떻게 보여줄지(동작)는 콜백**으로 **외부에서 주입**받을 수 있어서 코드가 **모듈화되고 재사용성이 높아짐**

### 함수형 프로그래밍

> 프로그래밍 패러다임 중 하나로 수학적 **함수 계산을 모델로 삼고 상태(State) 변경과 가변 데이터(Mutable Data)를 피하는 프로그래밍 방식**

- 코틀린은 객체지향 프로그래밍과 **함수형 프로그래밍**을 모두 지원하는 **멀티 패러다임 언어**

1. 개념
    1. 순수 함수(Pure Functions)
        - 동일한 입력값을 넣었을 때 **항상 동일한 결과**를 반환
        - 함수의 실행이 **외부에 어떤 영향(Side Effect, 부수 효과)도 주지 않음**(예: 전역 변수 수정, 파일 I/O, 네트워크 요청 등 지양)

    2. 불변성(Immutability)
        - 데이터는 한 번 생성되면 **변경할 수 없음**
        - 상태를 변경해야 할 때는 기존 데이터를 수정하는 대신 기존 데이터를 바탕으로 **새로운 데이터 객체를 생성**하여 반환

    3. 일급 함수와 고차 함수 (First-Class & Higher-Order Functions)
        1. **일급 함수**
            - **함수를 변수에 저장하거나 다른 함수의 인자로 전달하고 결과값으로 반환할 수 있음**
        2. 고차 함수
            - **함수를 인자로 받거나 함수를 리턴**하는 함수

    4. 선언적 프로그래밍 (Declarative Programming)
        - 반복문과 조건문을 사용하여 제어 흐름을 일일이 지정하는 명령형 방식과 달리 **로직을 함수의 조합**으로 명시하여 가독성을 높임

2. 장점
    - 순수 함수와 **불변성을 유지하므로 버그가 발생할 확률이 낮고 디버깅이 쉬움**
    - **외부 상태에 의존하지 않기 때문에 단위 테스트(Unit Test)를 작성하기 쉬움**
    - 여러 스레드가 동시에 데이터를 접근해 수정하더라도 값이 변하지 않아(불변성) **멀티스레드 환경에서 안전**

3. 안티패턴
    - `map` 같은 함수 내부에서 `throw Exception`을 써서 로직을 중단시키는 것은 성능을 떨어뜨리고 가독성을 해침
    - 변환 목적의 `map` 내부에서 `return@map null` 등을 사용해 불필요한 널(Null) 리스트를 만드는 것은 피해야 함
    - 순수 함수여야 하는 고차 함수 내부에서 외부 상태나 전역 변수를 직접 수정하는 것은 데이터 예측을 어렵게 만듦
    - 새로운 컬렉션을 만들지 않으면서 단순히 순회와 부수 효과가 목적인데 `map`을 사용하는 것은 코드의 의도를 오해하게 만듦
    - 너무 길게 이어진 함수 체인은 디버깅을 어렵게 하고 가독성을 떨어뜨림

### 코틀린 filter 함수

> 컬렉션(list, set)에서 **특정 조건을 만족하는 요소들만 골라내어 새로운 컬렉션으로 반환**해 주는 함수

1. 특징
    - 원본 컬렉션을 변경하지 않고 조건을 만족하는 데이터로 구성된 **새로운 컬렉션을 생성 및 반환**
    - 각 요소를 인자로 받아 `Boolean`을 반환하는 **람다 함수(Predicate)를 매개변수로 받음**
    - 일반 컬렉션(Iterable)에서 `filter` 사용 시 **즉시 연산이 수행**되며 **중간 결과물로 새로운 리스트 객체가 생성**

2. 장점
    - `for`문과 `if`를 조합하면 **'어떻게(How)' 데이터를 순회하고 담을지 작성**해야 하지만 `filter`는 **'무엇(What)'을 골라낼지 직관적으로 표현하여 코드의 가독성이 좋음**
    - **원본 컬렉션을 직접 수정(Mutation)하지 않고** 조건에 맞는 데이터만 담은 **새로운 컬렉션을 반환**하므로 예기치 않은 **데이터 변조나 사이드 이펙트(Side Effect)를 방지**
    - `filter` 결과에 곧바로 `map`, `sorted` 등 다른 컬렉션 함수를 이어 붙여 **복잡한 데이터 가공 과정을 하나의 유연한 파이프라인으로 깔끔하게 구성**

#### Iterable/Sequence

| **비교 항목**                  | **Iterable (일반 컬렉션, 예: List, Set)**                                | **Sequence (시퀀스)**                                                         |
| -------------------------- | ------------------------------------------------------------------ | -------------------------------------------------------------------------- |
| **연산 방식 (Evaluation)**     | **즉시 연산 (Eager Evaluation)**<br><br>함수 호출 **즉시 연산 수행** 및 결과 반환     | **지연 연산 (Lazy Evaluation)**<br><br>최종 연산이 호출될 때까지 **연산 보류**                |
| **순회 및 처리 방식**             | **수평적 순회**<br><br>전체 데이터가 **단계를 거친 후 다음 단계**로 이동                   | **수직적 순회**<br><br>데이터 하나가 **모든 체이닝 단계를 통과 후 다음 데이터 처리**                    |
| **중간 객체 생성**               | **단계별 리스트 생성**<br><br>체이닝마다 **새로운 중간 컬렉션 객체 할당**                   | **중간 객체 미생성**<br><br>**연산 규칙을 담은 가벼운 껍데기(`Iterator`)만 유지**                 |
| **숏서킷 (Short-circuiting)** | 전체 데이터를 다 순회한 뒤 **일부를 잘라냄 (`take`, `find` 등 사용 시에도 전체 순회 가능성 있음)** | **조건을 만족하는 즉시 순회를 중단**하여 불필요한 연산 방지                                        |
| **최적의 사용 상황**              | **데이터가 적을 때** (수십~수백 건)<br>단일 연산 또는 전체 데이터를 한 번에 다루는 경우            | **대용량 데이터** (수만~수백만 건 이상)<br>**다중 체이닝 + 조기 종료(`take`, `first` 등)가 필요한 경우** |
| **단점 및 주의점**               | 대용량 + 다중 체이닝 시 **메모리 낭비 및 GC 부하 발생**                               | 데이터가 적을 때는 **시퀀스 관리 오버헤드로 인해 오히려 성능 저하**                                   |
