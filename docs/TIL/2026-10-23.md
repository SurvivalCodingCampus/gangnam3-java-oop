# 1. 배운 점

## 동시성

> 시분할을 통해 작업을 나누어 처리하는 것

- 여러 작업을 조금씩 나누어 처리함
- 단일 CPU 코어에서도 구현할 수 있음
- 작업이 동시에 실행되는 것처럼 보이는 개념
- 여러 작업을 효율적으로 관리하는 것
- 단일 CPU 코어에서 시분할 방식으로 여러 스레드를 번갈아 실행하여 구현할 수 있음
## 병렬성

> 여러 작업이 물리적으로 같은 순간에 실행되는 것

- 여러 CPU 코어 등을 사용해 작업을 동시에 실행
- 서로 다른 작업이 실제로 같은 순간에 처리
- 처리 속도와 연산 성능을 높이는 것
- 멀티코어 CPU나 GPU 등의 하드웨어 자원을 활용하여 여러 스레드 또는 프로세스를 동시에 실행함으로써 구현할 수 있음

| 구분        | 동시성                   | 병렬성                               |
| --------- | --------------------- | --------------------------------- |
| 목적        | 여러 작업을 효율적으로 진행       | 여러 작업을 동시에 처리하여 성능 향상             |
| 적합한 작업    | I/O Bound             | CPU Bound                         |
| 대표 사례     | API 요청, DB 조회, 파일 입출력 | 이미지 처리, 대규모 계산, 데이터 분석            |
| 실행 방식     | 하나의 스레드에서도 가능         | 여러 CPU 코어 활용                      |
| Kotlin 예시 | 단일 스레드의 여러 코루틴        | `Dispatchers.Default`에서 여러 코루틴 실행 |

### I/O 작업에서 동시성이 유리한 이유

> CPU가 연산하는 시간보다 외부 장치나 네트워크의 응답을 기다리는 시간이 길기 때문

- 하나의 작업이 I/O를 기다리는 동안 다른 작업을 진행하면 CPU 자원을 더 효율적으로 활용할 수 있기 때문
- I/O 작업은 운영체제(OS)와 하드웨어가 처리하므로 CPU가 I/O 완료를 기다리는 동안 다른 작업을 실행할 수 있음

### I/O 작업의 실행 과정
1. 애플리케이션이 시스템 콜 등을 통해 OS에 I/O를 요청
2. OS가 네트워크 장치와 협력해 요청을 처리
3. 네트워크 통신이 진행되는 동안 CPU는 다른 작업을 실행할 수 있음
4. 응답이 도착하면 OS가 데이터를 처리하고 대기 중인 스레드를 깨우거나 준비 완료 이벤트를 전달

### CPU 작업은 병렬성이 유리한 이유

> CPU 연산은 I/O 작업과 다르게 CPU 자체가 계속 계산해야 하는 작업

- 단일 코어에서 번갈아 계산한다고 전체 연산량이 줄어들지는 않음 오히려 문맥 교환 비용이 발생할 수 있음
- 반면 여러 CPU 코어를 활용하면 연산을 실제로 동시에 수행할 수 있으므로 처리 속도가 향상될 수 있음

## 동기

> 작업의 완료를 기다려 결과를 받은 뒤 다음 작업을 진행하는 방식

- 호출한 작업이 완료되어야 다음 코드를 진행
- 실행 흐름과 결과 처리 순서를 이해하기 쉬움
- 시간이 오래 걸리는 작업을 기다리면 전체 흐름이 지연될 수 있음

## 비동기

> 작업을 요청한 후 완료를 기다리지 않고 다른 작업을 진행할 수 있는 방식

- 작업이 완료되기 전에 다른 작업을 수행할 수 있음
- 결과는 자바의 콜백, Future, Promise, 코틀린의 Coroutine 등을 통해 처리할 수 있음
- 네트워크 통신, 파일 입출력처럼 대기 시간이 있는 작업에 유리
- 비동기 프로그래밍으로 동시성을 구현할 수 있고 그 작업들이 실제 병렬로 실행될 수도 하나의 스레드에서 번갈아 실행될 수도 있음

| 구분                | 제어권 및 실행 흐름             | 설명                      |
| ----------------- | ----------------------- | ----------------------- |
| 동기(Synchronous)   | 작업 완료에 맞춰 다음 단계 진행      | 작업 결과를 확인한 뒤 다음 단계 진행   |
| 비동기(Asynchronous) | 작업 완료와 무관하게 다른 작업 진행 가능 | 작업 완료를 나중에 통지받거나 결과를 회수 |
- 동기 vs 비동기: 작업의 완료와 결과를 언제, 어떻게 처리하는가에 초점
## Blocking, Non-Blocking

1. Blocking
- 호출자가 작업을 요청하면 호출된 함수가 제어권을 유지
- 작업이 완료되거나 진행 가능한 상태가 될 때까지 호출자는 다음 코드로 진행하지 못함

2. Non-Blocking
- 호출자가 작업을 요청하면 호출된 함수가 빠르게 제어권을 반환
- 작업이 완료되지 않았더라도 호출자는 다른 작업을 수행할 수 있음

| 구분           | 제어권                                | 설명                      |
| ------------ | ---------------------------------- | ----------------------- |
| Blocking     | 작업이 완료되거나 진행 가능해질 때까지 제어권을 반환하지 않음 | 호출 스레드가 대기 상태에 놓일 수 있음  |
| Non-Blocking | 작업 완료 여부와 관계없이 제어권을 즉시 반환          | 호출자가 다른 작업을 계속 수행할 수 있음 |

- Blocking vs Non-Blocking: 호출한 작업이 제어권을 언제 반환하는가에 초점
- 제어권(Control): 현재 실행 흐름에서 다음 코드를 진행할 수 있는 권한을 의미
- 동기와 Blocking은 자주 함께 사용되지만 같은 개념은 아님
- 비동기가 반드시 Non-Blocking인 것도 아님
## 코틀린 코루틴

> 코루틴(Coroutine)은 실행을 일시 중단(Suspend)하고 나중에 재개(Resume)할 수 있는 경량 실행 단위

- Kotlin에서는 코루틴을 사용하여 스레드를 차단하지 않고 비동기 작업을 처리할 수 있으며 동시성과 병렬성을 구현할 수 있음

1. 개념
- 일반적인 함수는 호출되면 실행을 시작하고 결과를 반환하면 종료됨 반면 코루틴은 실행 도중 일시 중단되었다가 나중에 이어서 실행할 수 있음
    - 코루틴의 일시 중단과 스레드의 차단은 서로 다르다

- Blocking: 스레드가 작업 완료를 기다리며 차단됨
- Suspending: 코루틴의 실행이 중단되고 스레드는 다른 작업에 사용될 수 있음
- Resuming: 중단된 코루틴이 나중에 실행을 재개함

2. 장점
- 적은 수의 스레드로 많은 동시 작업을 처리할 수 있음
- 콜백 중심 비동기 코드를 순차적인 코드 형태로 작성할 수 있음
- 취소, 예외 처리, 생명주기 관리를 구조화할 수 있음
- 네트워크 요청, DB 처리 등에 유용

3. 주의사항
- 코루틴이 모든 작업의 실행 속도를 높여주는 것은 아님
- `suspend` 함수라고 해서 반드시 논블로킹인 것은 아님
- 코루틴도 공유 데이터를 동시에 수정하면 경쟁 상태(Race Condition)가 발생할 수 있음
- 장시간 CPU 연산이나 블로킹 작업은 적절한 Dispatcher에서 실행해야 함

### 코루틴과 스레드의 차이

| 구분    | Thread           | Coroutine              |
| ----- | ---------------- | ---------------------- |
| 실행 단위 | OS가 스케줄링하는 실행 단위 | Kotlin 런타임이 관리하는 작업 단위 |
| 생성 비용 | 상대적으로 높음         | 상대적으로 낮음               |
| 메모리   | 스레드별 스택 필요       | 상대적으로 적은 메모리 사용        |
| 대기    | 블로킹 대기 가능        | 논블로킹 일시 중단 가능          |
| 실행    | CPU 코어에서 실행      | 스레드 위에서 실행             |
| 전환    | OS의 스레드 스케줄링     | 코루틴 디스패처와 중단·재개 메커니즘   |

- 코루틴은 스레드를 대체하는 기술이 아니라 스레드를 효율적으로 활용하기 위한 추상화
- 하나의 스레드에서 여러 코루틴을 번갈아 실행할 수도 있고 여러 스레드를 활용하여 코루틴을 병렬 실행할 수도 있음

### 코루틴의 주요 구성 요소

1. `suspend` - 일시 중단 함수
- 코루틴 내에서 실행 도중 일시 중단할 수 있는 함수를 선언할 때 사용
- `delay(1000)`은 코루틴을 약 1초간 일시 중단
- 기다리는 동안 스레드를 차단하지 않음
- 대기 시간이 끝나면 코루틴이 재개됨
- `suspend` 함수는 다른 `suspend` 함수 또는 코루틴 내부에서 호출할 수 있음

2. `CoroutineScope` -  코루틴 실행 범위
- 코루틴을 시작하고 수명을 관리하는 범위
- 코루틴은 단독으로 실행되는 것이 아니라 특정 `CoroutineScope`에 속해 실행된다
- 코루틴을 생성할 수 있는 환경을 제공하며 해당 범위에서 생성된 코루틴들의 실행, 완료, 취소를 관리하는 역할을 함
- 코루틴 스코프를 만드는 함수를 코투린 빌더라고 부름
- 구조화된 동시성: 부모 코루틴이 자식 코루틴의 생명주기를 관리하는 방식
    - 부모의 취소가 자식에게 전파되고 자식의 처리되지 않은 예외도 부모에게 영향을 준다

| 함수               | 설명                    | 스레드 차단 여부 |
| ---------------- | --------------------- | --------- |
| `runBlocking`    | 코루틴 실행 진입점            | O         |
| `coroutineScope` | 자식 코루틴 완료까지 대기        | X         |
| `launch`         | 코루틴 생성, `Job` 반환      | X         |
| `async`          | 코루틴 생성, `Deferred` 반환 | X         |
| `withContext`    | 지정한 컨텍스트에서 실행         | X         |
| `runTest`        | 테스트용 코루틴 실행 환경        | O         |

| 구분           | `runBlocking {}`     | `coroutineScope {}`  |
| ------------ | -------------------- | -------------------- |
| 함수 종류        | 일반 함수                | `suspend` 함수         |
| 현재 스레드 차단    | O (Blocking)         | X (Suspending)       |
| 자식 코루틴 완료 대기 | O                    | O                    |
| 호출 가능 위치     | 일반 함수, 코루틴 내부        | `suspend` 함수, 코루틴 내부 |
| 스코프 생성       | O                    | O                    |
| 반환 타입        | `T`                  | `T`                  |
| 주요 목적        | 일반 코드와 코루틴 연결        | 구조화된 동시성 구현          |
| 대표 사용처       | `main()` 함수, 동기식 진입점 | `suspend` 함수 내부      |
- `runTest`는 호출 스레드를 차단하지만 `delay()`로 인한 실제 대기 시간을 생략할 수 있는 테스트 함수

3. `launch`와 `async` - 코루틴 생성

> `launch`와 `async`는 기본적으로 부모 코루틴의 컨텍스트를 상속하며 별도의 스레드 생성을 보장하지 않음

- 두 함수 모두 코루틴을 시작하지만 반환값이 다름

| 구분    | `launch`     | `async`       |
| ----- | ------------ | ------------- |
| 반환 타입 | `Job`        | `Deferred<T>` |
| 결과값   | 별도로 반환하지 않음  | 결과값 반환        |
| 완료 대기 | `join()`     | `await()`     |
| 주요 목적 | 결과가 필요 없는 작업 | 결과가 필요한 작업    |


`async`는 새로운 코루틴을 시작하고 `withContext`는 지정한 컨텍스트에서 작업을 완료한 후 결과를 반환한다

| 구분         | `async(Dispatcher)` | `withContext(Dispatcher)` |
| ---------- | ------------------- | ------------------------- |
| 주요 목적      | 비동기 작업 시작 및 결과 수집   | 코루틴 컨텍스트 전환 및 결과 반환       |
| 새로운 코루틴 생성 | O                   | 별도 실행 코루틴 사용 가능           |
| 반환 타입      | `Deferred<T>`       | `T`                       |
| 결과 받기      | `await()`           | 직접 반환                     |
| 호출 시 완료 대기 | X (기본 설정)           | O (일시 중단)                 |
| 호출 이후 코드   | 완료를 기다리지 않고 진행      | 작업 완료 후 진행                |
| 동시 실행      | 여러 작업을 동시에 시작하기 편리  | 다른 코루틴과 동시 실행 가능          |
| 병렬 실행      | Dispatcher에 따라 가능   | Dispatcher에 따라 가능         |
| 사용 위치      | `CoroutineScope` 내부 | `suspend` 함수 또는 코루틴 내부    |
| 대표 사용 사례   | 여러 파일 동시 다운로드       | 단일 파일 다운로드, DB 조회         |

### 코루틴 디스패처

> 코루틴이 어떤 스레드 또는 스레드 풀에서 실행될지 결정하고 실행을 스케줄링하는 역할을 한다 코루틴은 스레드 위에서 실행되며 디스패처를 통해 실행 위치를 지정하거나 변경할 수 있다

- 디스패처를 생략했다고 무조건 `Dispatchers.Default`가 사용되는 것은 아니다 부모의 실행 환경을 상속한다

1. `Default`
- CPU 코어 수를 고려한 병렬 처리
- 공유 백그라운드 스레드 풀 사용
- CPU 연산 중심 작업에 최적화

2. `IO`
- 블로킹 I/O 작업에 적합
- 필요에 따라 작업 스레드 활용량 증가
- JVM 기본 병렬 처리 제한은 `max(64, CPU 코어 수)`
    - 이 수치는 기본적인 I/O 작업의 병렬 처리 제한이지 전체 스레드 풀이 절대 64개를 넘지 않는다는 의미는 아님
    - `Dispatchers.IO`와 `Dispatchers.Default`는 내부 스레드 자원을 공유할 수도 있다

3. `Main`
- UI 업데이트에 사용
- 긴 CPU 연산이나 블로킹 I/O는 피해야 함
- 일반 JVM 콘솔 프로젝트에서는 메인 디스패처가 제공되지 않을 수 있음

| Dispatcher               | 실행 환경            | 주요 용도                |
| ------------------------ | ---------------- | -------------------- |
| `Dispatchers.Default`    | 공유 백그라운드 스레드 풀   | CPU 연산               |
| `Dispatchers.IO`         | I/O 작업용 공유 스레드 풀 | 파일, DB, 블로킹 네트워크 I/O |
| `Dispatchers.Main`       | 메인(UI) 스레드       | UI 업데이트              |
| `Dispatchers.Unconfined` | 특정 스레드에 고정되지 않음  | 특수한 실행 제어            |

| 실행 환경                                       | 동시성 | 병렬성     | 설명                            |
| ------------------------------------------- | --- | ------- | ----------------------------- |
| `runBlocking`의 기본 Dispatcher                | O   | X       | 호출 스레드 하나에서 코루틴 실행            |
| `Dispatchers.Main`                          | O   | X       | 일반적으로 UI 스레드 하나에서 실행          |
| `Dispatchers.Default`                       | O   | O (조건부) | 멀티스레드 풀 사용, CPU 작업에 적합        |
| `Dispatchers.IO`                            | O   | O (조건부) | 공유 스레드 풀 사용, Blocking I/O에 적합 |
| `Dispatchers.Default.limitedParallelism(1)` | O   | X       | 해당 Dispatcher의 동시 실행 수를 1로 제한 |

| 구분          | `Dispatchers.Default`     | `Dispatchers.IO`                       |
| ----------- | ------------------------- | -------------------------------------- |
| 주요 목적       | CPU 연산                    | Blocking I/O                           |
| 스레드 수       | 대체로 CPU 코어 수 기준           | 필요에 따라 더 많은 스레드 활용                     |
| Blocking 작업 | 스레드가 차단되면 CPU 작업 처리 능력 저하 | 여러 대기 작업을 처리하도록 설계                     |
| 적합한 작업      | 계산, 이미지 가공                | Blocking 파일 읽기, JDBC, Blocking 네트워크 요청 |

| 구분       | Platform Thread | Virtual Thread    | Kotlin Coroutine |
| -------- | --------------- | ----------------- | ---------------- |
| 관리 주체    | OS/JVM          | JVM               | Kotlin 코루틴 라이브러리 |
| 경량성      | 상대적으로 낮음        | 높음                | 높음               |
| I/O 대기   | 플랫폼 스레드 차단      | 가상 스레드 중단 가능      | 코루틴 중단 가능        |
| 비동기 코드   | 별도 API 활용       | 동기식 코드 활용 가능      | `suspend` 활용     |
| 구조화된 동시성 | 별도 관리           | 관련 Java API 활용 가능 | 기본적인 설계 원칙       |
| 적합한 상황   | 일반적인 스레드 작업     | 대규모 블로킹 I/O       | 비동기 작업 및 생명주기 관리 |

### Virtual Thread VS Kotlin Coroutine

| 비교 대상                             | 테스트 결과                    |
| --------------------------------- | ------------------------- |
| Virtual Thread vs Platform Thread | I/O 작업에서 약 51% 성능 향상      |
| Virtual Thread vs Coroutine       | I/O 작업에서 약 37% 성능 향상      |
| CPU 연산                            | Platform Thread가 더 유리한 결과 |

소수를 찾는 CPU 연산 작업 100,000개를 실행해 두 기술의 성능을 비교

| 테스트 | Virtual Thread | Coroutine |
| --- | -------------- | --------- |
| 1회차 | 1,910ms        | 2,306ms   |
| 2회차 | 1,919ms        | 2,296ms   |
| 3회차 | 1,912ms        | 2,180ms   |

1. Kotlin Coroutine이 유리한 상황
- 명시적인 비동기 작업 관리가 중요하고 여러 작업의 취소, 완료, 예외 처리를 `CoroutineScope`와 `Job`으로 구조화하고 싶을 때

2. Java Virtual Thread가 유리한 상황
- 기존 Java 코드가 블로킹 I/O 중심이고 많은 코드를 비동기 API로 변경하지 않으면서 높은 동시 요청량을 처리하고 싶을 때

3. Virtual Thread의 주의사항
- Virtual Thread는 저렴하게 생성할 수 있으므로 일반 플랫폼 스레드처럼 재사용 풀을 만들 필요가 거의 없음
- CPU 연산 자체가 빨라지는 것은 아니며 스케줄링 오버헤드가 추가될 수 있음
- Pinning: 가상 스레드는 원래 작업을 기다리는 동안 실제 스레드를 반납할 수 있는데 특정 상황에서는 반납하지 못하고 계속 점유하는 현상
- 가상 스레드가 많으면 스레드별 데이터로 인한 메모리 부담이 커질 수 있음
- Java 24부터 `synchronized`로 인한 주요 Pinning 문제가 개선 네이티브 코드 등 일부 제한은 여전히 존재

두 기술 모두 무제한 동시 실행을 보장하지는 않음 DB 커넥션 풀, 외부 API 처리량, 메모리 등의 한계는 별도로 관리해야 함

## 이너 클래스

> 클래스 내부에 선언되며 `inner` 키워드를 사용하면 외부 클래스의 인스턴스와 멤버에 접근할 수 있는 클래스를 의미
1. `Nested Class`
- 코틀린에서 클래스 내부에 다른 클래스를 선언하면 기본적으로 Nested Class
- 외부 클래스의 인스턴스 없이 생성할 수 있음
- 외부 클래스의 인스턴스 멤버에 직접 접근할 수 없음
- Java의 `static nested class`와 유사

2. `inner class`
- `inner` 키워드를 사용하면 외부 클래스의 인스턴스에 연결되는 내부 클래스를 선언할 수 있음
- 외부 클래스의 인스턴스가 있어야 생성할 수 있음
- 외부 클래스의 `private` 멤버에도 접근할 수 있음
- 내부 클래스는 외부 클래스 인스턴스에 대한 참조를 유지
- 외부 클래스와 내부 클래스에 동일한 이름의 변수가 존재하는 경우 `this@Outer`를 사용하여 외부 클래스의 멤버에 접근할 수 있음
- 내부 클래스는 외부 객체에 대한 참조를 유지하므로 내부 객체가 외부 객체보다 오래 살아 있으면 외부 객체도 메모리에서 해제되지 않을 수 있음
- Android에서 `Activity`를 참조하는 내부 클래스가 장시간 유지된다면 메모리 누수가 발생할 수 있음

| 구분                      | Nested Class          | Inner Class            |
| ----------------------- | --------------------- | ---------------------- |
| 선언 방법                   | `class`               | `inner class`          |
| 외부 인스턴스 필요              | X                     | O                      |
| 외부 인스턴스 멤버 접근           | X                     | O                      |
| 외부 `private` 인스턴스 멤버 접근 | X                     | O                      |
| 외부 객체 참조 보유             | X                     | O                      |
| Java 비교                 | `static nested class` | Non-static inner class |
| 객체 생성                   | `Outer.Nested()`      | `outer.Inner()`        |

## 코틀린 object 키워드

1. 객체 선언
> 클래스 선언과 객체 생성을 동시에 수행하는 방식으로 싱글톤 패턴[^1]을 구현할 때 사용

- 객체가 하나만 생성되는 싱글톤 구조
- 별도의 인스턴스 생성 불필요
- 객체 선언은 최초 접근 시 초기화됨
- 생성자를 직접 선언할 수 없음
- 인터페이스 구현 및 클래스 상속 가능
- Java에서는 싱글톤을 직접 구현해야 하지만 Kotlin에서는 `object` 키워드 하나로 구현

2. Companion Object
> 클래스 내부에 선언하는 객체로, 클래스 이름을 통해 접근할 수 있는 멤버를 정의할 때 사용

- 클래스당 하나의 동반 객체를 선언할 수 있음
- 클래스 이름으로 멤버에 접근 가능
- 일반 인스턴스 생성 없이 사용 가능
- Java의 `static`과 비슷하지만 실제 객체임
- 인터페이스 구현 가능
- 인스턴스의 멤버에 직접 접근할 수 없음

3. 객체 표현식

> 이름 없는 익명 객체를 즉시 생성하는 방식

```kotlin
interface ClickListener {
    fun onClick()
}

fun main() {
    val listener = object : ClickListener {
        override fun onClick() {
            println("버튼 클릭")
        }
    }

    listener.onClick()
}
```

```kotlin
val person = object {
    val name = "홍길동"
    val age = 25

    fun introduce() {
        println("$name, $age")
    }
}

person.introduce()
```


- 객체를 선언하는 즉시 생성
- 별도의 클래스 이름이 필요 없음
- 인터페이스 구현 및 클래스 상속 가능
- 이벤트 리스너, 콜백 등에 활용
- `object` 선언과 달리 표현식이 평가될 때마다 새 객체가 생성됨

## 코틀린 테스트

`advanceTimeBy(duration)`:
- 코루틴 테스트에서 **가상 시간을 지정한 만큼 진행시키는 함수**
- `advanceTimeBy(1000)`은 가상 시간을 1000ms 진행시키지만 정확히 1000ms에 예약된 작업은 실행하지 않음

```kotlin
@Test
fun test() = runTest {
    launch {
        delay(1000)
        println("1초 경과")

        delay(2000)
        println("3초 경과")
    }

    advanceTimeBy(1000)
    println("현재 시간: $currentTime")
}

현재 시간: 1000
1초 경과
3초 경과
```

`runCurrent()`:
- 현재 가상 시간에 예약된 작업 실행

```kotlin
@Test
fun test() = runTest {
    launch {
        delay(1000)
        println("1초 경과")
    }

    advanceTimeBy(1000)
    println("A")

    runCurrent()
    println("B")
}

A
1초 경과
B
```

| 함수                    | 설명                                 |
| --------------------- | ---------------------------------- |
| `advanceTimeBy(1000)` | 가상 시간을 1000ms 진행하며 그 이전에 예약된 작업 실행 |
| `runCurrent()`        | 현재 가상 시간에 예약된 작업 실행                |
| `advanceUntilIdle()`  | 실행 가능한 예약 작업을 모두 처리할 때까지 가상 시간 진행  |
| `currentTime`         | 현재 가상 시간(ms) 확인                    |

## 표준 입출력 변경

> JVM에서는 `System` 클래스를 통해 표준 입력, 표준 출력, 표준 오류 스트림을 관리할 수 있음

| 표준 스트림       | 기본 역할         | 변경 메서드            |
| ------------ | ------------- | ----------------- |
| `System.in`  | 키보드 등에서 입력받음  | `System.setIn()`  |
| `System.out` | 콘솔에 일반 메시지 출력 | `System.setOut()` |
| `System.err` | 콘솔에 오류 메시지 출력 | `System.setErr()` |

- `readln()`은 키보드 입력 자체를 발생시키는 함수가 아니라 표준 입력 스트림에서 한 줄을 읽는 함수
- 스레드가 블로킹되어도 운영체제와 터미널의 입력 처리는 계속될 수 있다
- 일반적인 터미널에서는 입력 데이터가 운영체제의 입력 버퍼에 보관된다
- `System.in`은 운영체제가 제공하는 입력을 읽기 위한 표준 입력 스트림이다
- `readln()`은 해당 스트림에서 한 줄을 읽으며 데이터가 준비되지 않았다면 호출한 스레드를 블로킹한다
