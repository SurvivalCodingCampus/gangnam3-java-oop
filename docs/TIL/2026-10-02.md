### equals()와 hashcode()를 같이 재정의 해야하는 이유

#### 자바 명세의 Object.hashCode 공식 규약

$$\text{equals()가 true이면} \implies \text{hashCode()는 반드시 같다.}$$

- **동일한 객체는 항상 같은 hashCode**를 가진다
- **이유** : 만약 두 객체가 `equals()`상 같은데 `hashCode()`가 달라서 서로 다른 방에 들어간다면 `HashMap`이나 `HashSet`은 같은 객체를 찾지 못하고 중복 저장하는 오류가 발생

$$\text{hashCode()가 같다고 해서 } \kern-0.5em \not\implies \text{equals()가 true인 것은 아니다.}$$

- **같은 해시값이라고 항상 동일한 객체**는 아니다
- **이유** :
  - 비둘기집 원리[^1]로 인해 해시 충돌이 발생할 수 있음
  - 서로 다른 두 객체라도 해시 함수 계산 결과가 우연히 같을 수 있음
  - 따라서 hashCode()가 같아도 equals()를 통해 동등한지 비교한다
  - List가 equals()로 비교하는 이유도 굳이 hashCode()를 통해 equals() 두 번 연산을 할 필요가 없기 때문

### 프라임넘버를 31로 쓰는 이유

- **소수(Prime Number)를 곱하는 이유 (충돌 방지)**
  - **합성수(짝수, 10 등)** 비트 연산 시 하위 비트가 $0$으로 쏠려 정보가 손실되고
    해시 충돌 확률이 급증함
  - 약수가 $1$과 자기 자신뿐이라 비트 패턴이 고르게 흩어짐
  - 곱셈 누적 시 정보가 뭉치지 않아 **해시 충돌(Collision) 최적화**

- **하필 '31'을 쓰는 이유 (비트 연산 속도)**
  - 31보다 작으면 해시 분산력이 떨어지고 너무 크면 int 범위를 벗어나 자원 낭비(Overflow)가 심해지기 때문에 **해시 분산력 + 연산 속도**의 최적 접점
  - $31 \times i = (i \ll 5) - i$
  - 컴파일러가 곱셈보다 빠른 **비트 쉬프트(`<<`)와 뺄셈**으로 자동 최적화

### 익명 클래스

- 이름이 없는 일회성 클래스
- **클래스 선언과 객체 생성을 동시**에 진행하며 **특정 인터페이스나 클래스를 딱 한 번**만 **재정의(Override)하여 바로 사용하고 버릴 때** 활용
- 새로운 메소드도 만들어 사용가능, 새로 정의한 메서드는 외부에서 사용 불가
- **외부 지역 변수 참조 시 `final` 제약 (캡처 현상)** : **익명 클래스 내부**에서 자신이 속한 **메서드의 지역 변수를 참조**할 때는 해당 변수가 **`final`이거나 값이 바뀌지 않는 상수**의 상태여야 함
- 컴파일러가 클래스에 임의로 `$1`, `$2` 같은 순번을 붙여 바이트코드 파일(`.class`)을 생성

#### 캡쳐 현상이 발생하는 이유

- **생명주기(Lifespan)의 불일치** :
  - 지역 변수는 메서드가 실행을 마치고 종료되면 **스택(Stack) 메모리에서 즉시 파괴**
  - 반면 익명 클래스로 생성된 객체는 **힙(Heap) 메모리에 남아** 메서드가 끝난 후에도 살아있을 수 있어 지역 변수에 접근하면 치명적인 에러가 발생하기 때문

- **변수 캡처(Variable Capture)** :
  - 사라질 지역 변수를 나중에도 안전하게 쓰기 위해 익명 클래스는 변수 자체가 아닌 **변수의 값(Value)을 복사(Capture)해서 자신 내부에 가지고 있음**

- **동기화 문제 방지** :
  - 만약 **외부에서 변수 값을 계속 바꿀 수 있다면** "**복사본 값"과 "원래 변수 값"이 서로 달라져** 데이터 불일치(Inconsistency)나 멀티스레드 **동기화 오류**가 발생하므로 **자바 언어 차원에서 아예 값을 변경하지 못하도록 `final` 상태만 허용**하도록 강제

### 얕은 복사, 깊은 복사

- **얕은 복사**
  - **객체 자체는 새로 생성**되지만 **객체 내의 참조 타입 필드(다른 객체에 대한 참조)는 원본과 동일한 객체를 참조**

- **깊은 복사**
  - **객체 자체뿐만 아니라** 객체 내의 모든 **참조 타입 필드(중첩된 객체들)까지도 완전히 새로 생성**하여 복사

### 불변객체

- 생성된 이후에 그 내부의 **상태를 바꿀 수 없는 객체**
- **스레드 안전성(Thread-Safe)** : 여러 곳에서 동시에 접근해도 **값이 바뀌지 않아 안전**
- **사이드 이펙트 방지** : 예상치 못한 **객체 상태 변경으로 인한 오류를 막아줌**

  - 값이 변하면 Hashcode도 변하기 때문

### 동시성 문제와 Lock의 동작 메커니즘 (JVM)

#### 동시성 문제(Data Race[^3]) 발생 조건 (2가지)

* **Shared (공유):** JVM Heap 영역의 동일한 객체에 **여러 스레드가 접근**
* **Mutable (가변):** 해당 객체의 필드(상태)를 수정(Write)할 수 있음
#### Lock을 걸 때 생기는 3가지 문제점
- **커널 모드 전환 & 컨텍스트 스위칭 비용**
  * 락 획득 실패 시 **CPU 레지스터/PC 상태를 TCB[^7]에 백업하고 스레드를 교체**하는 오버헤드 발생
  * CPU **캐시\(L1/L2) 무효화(Cache Invalidation)**[^8]로 전체 연산 효율 급락
- **CPU 자원 소모 (스핀 락 대기 시)**
  * 차단 전 스핀 락 시도 시 **컨텍스트 스위칭은 없으나 CPU Clock Cycle**[^6]을 직접 소모
- **데드락 (Deadlock)**
  * 스레드들이 서로의 락을 **교차 대기**하며 **데드락**에 빠짐 (JVM 자동 해제 불가)

### Lock 획득 실패 시 JVM 내부 동작 3단계

1. **스핀 락(Spinning) 시도 (JVM 최적화)** :
  * 바로 재우지 않고 아주 짧은 시간 CPU를 쓰며 락 해제를 반복 확인 (CPU 자원 소모)
2. **OS 커널 모드 전환 & 스레드 차단 (Blocking)** :
  * 스핀 락 실패 시 스레드 상태를 `RUNNABLE` ➔ `BLOCKED`로 변경
  * 1:1 매핑된 OS 스레드를 재우기 위해 유저 모드 ➔ 커널[^12] 모드 전환(System Call[^10]) 발생
1. **컨텍스트 스위칭 (Context Switching)** :
  * CPU 레지스터, PC 등 스레드 상태(Context)를 TCB에 저장 후 다른 스레드로 교체

### 컨텍스트 스위칭 (OS)

- CPU/코어에서 실행 중이던 **프로세스/스레드가 다른 프로세스/스레드**로 교체되는 것
- 여러 **프로세스/스레드를 동시**에 실행시키기 위해 **OS커널에 의해 실행**

- **언제** :
  - 주어진 **time slice(quantum)**를 다 사용했거나
  - **IO** 작업을 해야하거나
  - **다른 리소스를 기다려야 하거나**
  - 등등

- **다른 프로세스(Process Context Switching), 같은 프로세스(Thread Context Switching)**에 따라 약간씩 다름

| **비교 항목**                              | **Process Context Switching**                                       | **Thread Context Switching**                             |
| -------------------------------------- | ------------------------------------------------------------------- | -------------------------------------------------------- |
| **대상**                                 | 서로 **다른 프로세스** 간의 전환                                                | **같은 프로세스 내** 서로 다른 스레드 간의 전환                            |

| **공통점 2: 레지스터**                        | **CPU 레지스터 상태 교체** (PC, SP, general register 저장/복원)                 | **CPU 레지스터 상태 교체** (PC, SP, general register 저장/복원)      |

### 가상메모리

- 물리적 메모리 용량의 한계를 극복하고 여러 프로그램을 안정적으로 실행할 수 있게 돕는 운영체제의 기술
- 램이랑 하드디스크를 추상화해서 인터페이스를 제공
- OS가 1차 메모리 + 2차 메모리를 매핑해줌
- 프로세스가 죽으면 메모리를 회수 함 OS손상 발생 X

- **Page** : 가상메모리 관리의 최소 단위 보통 4KB
  - **Page In** : 하드에서 램으로 이사
  - **Page Out** : 쓰지않는 프로세스는 Page Out함 빈 공간이 많이 생기면 함
    - 램에서 하드디스크로 이사
- **Frame** : 물리메모리 관리 최소 단위 보통 4KB

- **페이지 테이블 (전체 지도)** :
  - 가상 메모리의 어떤 페이지가 실제 RAM의 몇 번 프레임에 들어가 있는지, 아니면 디스크에 가 있는지 전체 목록을 관리

- **Page Fault (페이지 폴트)** : **프로세스가 참조하려는 주소가 가리키는 페이지가 현재 물리 메모리(RAM)에 없을 때 발생하는 현상**
  -  이 때 **디스크 I/O 작업은 CPU 처리 속도에 비해 매우 느리므로**, 페이지 폴트가 자주 발생할수록 CPU는 작업을 하지 못하고 대기 시간이 증가하여 **CPU 이용률이 저하**

  1. 페이지폴트 이후 OS에게 트랩[^13]을 전송 **OS는 먼저 페이지 폴트가 유효한 접근인지 점검** 만약 비정상적인 접근이라면 **프로세스를 강제 종료**할 수 있음

  2. OS는 물리 메모리에서 **빈 프레임이 있는지 확인**하고 다음의 과정이 일어남

    1. **빈 프레임이 있을 경우** : **디스크에서 필요한 페이지를 바로 메모리로 가져와 적재(Swap-in)** 이때 기존 페이지를 내보내는 작업(Swap-out)은 없음

    2. **빈 프레임이 없을 경우** : **페이지 교체 알고리즘(Page Replacement Algorithm)을 수행**하여 **기존의 한 페이지를 선택 선택된 페이지를 디스크로 보냄(Swap-out)** 빈 프레임을 확보한 뒤 필요한 페이지를 **디스크에서 메모리로 가져옴(Swap-in)**

  - 개발자(소프트웨어) 레벨의 페이지 폴트 방지 방법

  - **지역성(Locality) 원칙 고려하기**
    - **시간 지역성(Temporal Locality)** : **최근에 참조된 기억 장소는 가까운 미래에 다시 참조될 가능성이 높으므로 루프(Loop) 구조를 최적화**
    - **공간 지역성(Spatial Locality)** :  특정 기억 장소 근처에 있는 데이터가 연속적으로 참조될 가능성이 높으므로 배열(Array)에 접근할 때 행(Row) 우선 또는 열(Column) 우선 순서를 언어의 메모리 배치 방식에 맞춰 일관되게 사용

  - **메모리 사용량 최적화**
    - 불필요하게 **거대한 데이터 구조나 객체를 한 번에 로드하지 않고, 필요한 부분만 가져오는 지연 로딩**(Lazy Loading) 또는 **페이징 처리**를 활용

- **MMU (주소 변환 하드웨어)** :
  - CPU가 가상 주소를 던지면, 페이지 테이블을 뒤져서 순식간에 물리 주소로 바꿔주는 실무 담당 장치

- **TLB (주소 변환 캐시)** :
  - **MMU가 주소 변환**을 할 때 **매번 RAM에 있는 페이지 테이블까지 가면 너무 느림**
  - 자주 쓰는 `가상 페이지 번호 ↔ 물리 프레임 번호` 변환 정보를 **CPU 바로 옆 TLB**에 저장하여 **RAM 접근 횟수를 줄임**

- **장점**
  - **메모리 확장** : 프로그램이 사용하는 메모리보다 **더 많은 가상 주소 할당**이 가능
  - **메모리 보호** : **독립된 가상 메모리 주소 공간을 가져 다른 프로세스의 메모리에 접근 방지**
  - **효율적 메모리 사용** : **필요한 메모리 부분만 물리 메모리에 적재**하기 때문에, **전체 프로그램을 물리 메모리에 적재하지 않아도 실행 가능**

- **단점**
  - **페이지 부재(Page Fault) 비용** : **페이지 부재가 발생하면 디스크에서 데이터를 가져와야 해서 속도가 느려질 수 있음**
  - **복잡성** : **가상 메모리 시스템은 페이지 테이블을 관리**하고, **페이지 교체 알고리즘을 구현해야 하기 때문에 복잡성이 증가**
  - **디스크 의존성** : **하드디스크는 메모리보다 느려 너무 많이 사용하면 성능 저하 발생** 가능



#### MMU, TLB

- **MMU가 전체 주소 변환 과정을 총괄하며 그 과정에서 속도 가속을 위해 TLB라는 캐시를 활용**함

| 구분        | MMU (Memory Management Unit)       | TLB (Translation Lookaside Buffer)                    |
| --------- | ---------------------------------- | ----------------------------------------------------- |
| **성격**    | 주소 변환과 메모리 관리를 담당하는 **중앙 제어 하드웨어** | 변환 속도를 높이기 위한 **전용 캐시 메모리**                           |
| **위치**    | CPU 혹은 프로세서 내 메모리 관리 서브시스템         | MMU 내부 (CPU 칩셋 내 탑재)                                  |
| **동작 방식** | 주소 변환 요청이 오면 페이지 테이블을 탐색함          | TLB에 데이터가 있으면(Hit) 즉시 반환, 없으면(Miss) MMU가 페이지 테이블을 조회함 |

### 멀티스레드 환경에서 불변 객체를 쓰면 좋은점

- **읽기 전용(Read-Only) 상태 유지**
  - 데이터가 변하지 않으므로 100개의 스레드가 동시에 해당 객체의 값을 읽어가도 **데이터 충돌(Data Race)이 구조적으로 발생할 수 없음**
  - 따라서 스레드를 대기시키기 위한 **Lock을 걸 필요가 전혀 없음**

- **가시성(Visibility) 보장** (`final` 키워드의 메모리 배리어)
  - 자바에서 `final` 필드로 선언된 불변 객체는 생성자가 완료되는 순간 메모리 배리어(Memory Barrier)[^4]가 작동
  - 이로 인해 JIT 컴파일러의 명령어 재배치(Reordering)[^5]가 방지되며 **모든 스레드가 항상 완벽하게 초기화된 최신 객체 상태를 즉시 바라보게(가시성) 됨**

- **안전한 상태 변경** : 수정이 아닌 새로운 객체 생성
  - 값을 변경해야 할 때는 기존 객체의 필드를 수정하는 것이 아니라 **변경된 값을 가진 "새로운 불변 객체"를 만들어 반환**

[^1]: **비둘기집 원리** : **비둘기**(데이터)가 **비둘기집**(메모리 공간)보다 많으면 무조건 **2마리 이상 들어가는 집**(해시 충돌)이 생길 수밖에 없는 원리

[^3]: Data Race : 적어도 하나의 스레드가 **동기화(Lock) 없이** 공유 메모리에 **동시에 쓰기(Write)** 작업을 수행할 때 발생하는 메모리 수준의 오류

[^4]: Memory Barrier : 컴파일러나 CPU가 메모리 연산(읽기/쓰기)의 순서를 임의로 변경하지 못하도록 강제하는 명령어(또는 기능)

[^5]: **JIT 컴파일러의 명령어 재배치 :** CPU 실행 효율을 높이기 위해 **의존성 없는 코드의 실행 순서를 임의로 뒤바꾸는 최적화 기법**으로 **멀티스레드 환경**에서는 **초기화되지 않은 객체가 노출**되는 등의 **동시성 오류를 유발**할 수 있다

[^6]: **클럭 사이클(Clock Cycle)** :  CPU 내부 시계가 1초 동안 실행하는 가장 작은 신호 주기(진동 단위)로 CPU가 **하나의 기초 명령어나 연산을 수행하는 최소 단위 시간**

[^7]: **TCB (Thread Control Block, 스레드 제어 블록)** : 운영체제 커널 내부의 데이터 구조로 스레드의 ID, 상태(Runnable/Blocked 등), 레지스터 값, 프로그램 카운터(PC), 스택 포인터 등 **스레드의 독립적인 실행 문맥(Context)을 저장하고 관리하는 공간**

[^8]: **캐시 무효화 (Cache Invalidation)** : 멀티코어/분산 환경에서 원본 데이터 변경 시 캐시 간 데이터 불일치(Stale Data)를 방지하고 **데이터 일관성(Cache Coherence)**을 보장하기 위해 기존 캐시를 파기하거나 만료시키는 메커니즘

[^9]: **Tim sort** : **삽입 정렬(Insertion Sort)**과 **병합 정렬(Merge Sort)**의 장점을 결합하여 만든 **하이브리드(Hybrid) 안정 정렬 알고리즘**

[^10]: 시스템콜 : CPU의 권한 레벨(User Ring 3 ➔ Kernel Ring 0)을 변경하는 인터럽트/트랩 명령어. 자바 스레드가 락을 얻지 못해 `BLOCKED` 상태로 전환될 때 1:1 매핑된 OS 스레드를 스케줄러 목록에서 재우기 위해 OS 커널(예: Linux의 `futex`)을 직접 호출하는 과정을 말함

[^11]: **멀티태스킹 (Multitasking)** : 단일 또는 다중 CPU 코어 환경에서 OS 스케줄러가 **컨텍스트 스위칭(Context Switching)**을 통해 여러 프로세스/스레드의 실행 상태를 주기에 따라 교체함으로써 **하나의 CPU에서 여러 작업이 동시에 실행되는 것처럼 느끼게 하는(동시성, Concurrency) 자원 배분 메커니즘**

[^12]: 커널 : 운영 체제의 **핵심(Core)**으로 CPU, 메모리, 디스크, I/O 등 **하드웨어와 소프트웨어 사이의 중재자** 역할

[^13]: **트랩(Trap / Exception)** : CPU **내부**에서 현재 실행 중인 명령어에 의해 발생하는 **동기적(Synchronous) 이벤트** 동일한 코드를 동일한 상황에서 실행하면 항상 같은 지점에서 터진다 대표적으로 Page Fault, Segmentation Fault, 0으로 나누기, 유저 프로그램이 OS 기능을 요청하는 System Call 등이 있음
**인터럽트(Hardware Interrupt)** : CPU **외부** 하드웨어 장치에 의해 발생하는 **비동기적(Asynchronous) 이벤트** CPU의 현재 명령어 실행 흐름과 무관하게 언제든 발생할 수 있음, 대표적으로 키보드/마우스 입력, 타이머 만료, 디스크 I/O 완료 신호 등이 있음"

[^14]: ASID : TLB 캐시를 전체 무효화(TLB Flush)하지 않고 유지할 수 있도록 각 프로세스마다 부여하는 독자적인 ID

[^15]: 베이스 레지스터 : 메모리 주소를 지정할 때 **"기준이 되는 시작 주소(시작점)"를 저장하는 CPU 내부의 레지스터**
