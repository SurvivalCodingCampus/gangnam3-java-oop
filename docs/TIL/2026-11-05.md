## Result 패턴

> 예외(Exception) 대신 성공(Success)과 실패(Failure) 상태를 값으로 감싸서 반환하는 에러 처리 방식이다. 함수형 프로그래밍이나 Kotlin 등에서 예외를 던지는 대신 에러를 타입으로 안전하고 명시적으로 다루기 위해 쓰임

1. **명시적 에러 처리 (Explicit Error Handling)**
    - 함수의 반환 타입만 봐도 이 함수가 실패할 수 있는지 명확히 알 수 있다.
    - 예외처럼 콜스택을 타고 불쑥 던져지는 숨겨진 제어 흐름이 없어 코드의 흐름을 쉽게 예측할 수 있다.
    - 복잡한 `try-catch` 중첩을 제거해 가독성을 높여준다.

2.  **컴파일러 기반 타입 안전성**
    - Kotlin의 `sealed class`나 타 언어의 Result 타입을 활용하면, 성공 케이스와 실패 케이스를 모두 처리(`when` 분기 등)하도록 컴파일러가 강제한다.
    - 에러 처리를 누락하는 실수를 원천 방지한다.

3. **성능적 이점**
    - 전통적인 예외 방식은 발생 시점에 스택 트레이스(Stack Trace)를 채우는 무거운 비용이 발생하지만, Result 객체는 단순한 객체 반환이므로 비용이 적다. (비즈니스 로직 상 자주 발생하는 실패 분기에 유리)

| **구분**       | **코틀린 표준 Result<T>**             | **직접 만든 Result<T, E> (sealed class)**           |
| ------------ | -------------------------------- | ----------------------------------------------- |
| **에러 타입**    | `Throwable`로 고정됨                 | 도메인에 맞게 커스텀 타입(`E`) 지정 가능                       |
| **에러 분기 처리** | `Throwable` 내부를 `is` 체크나 캐스팅해야 함 | `sealed class` 덕분에 `when`절에서 모든 에러 케이스 강제 처리 가능 |
| **보일러플레이트**  | 언어에 내장되어 있어 즉시 사용 가능             | 별도의 Result 클래스 구현 필요                            |
| **성능 오버헤드**  | `value class` 기반이라 객체 생성 비용 없음   | 일반 클래스 생성으로 인한 미세한 오버헤드 발생                      |

| **구분**             | **전통적 try-catch (예외 처리)**                                             | **Result 패턴 (값 반환)**                                  |
| ------------------ | --------------------------------------------------------------------- | ----------------------------------------------------- |
| **제어 흐름**          | 예외 발생 시 콜스택을 타고 점프하는 **비지역적 제어 흐름 (Non-local control flow)**          | 성공/실패를 일반 값으로 반환하여 **정상적인 코드 흐름 유지**                  |
| **타입 안정성**         | 메서드 시그니처에 에러가 드러나지 않음 (Kotlin은 Unchecked Exception이라 컴파일러가 누락 방지 못 함) | 반환 타입(`Result<T, E>`)에 에러가 명시되어 **컴파일 타임에 처리 강제**     |
| **성능**             | 예외 객체 생성 시 **스택 트레이스(Stack Trace) 수집 비용** 발생                          | 단순 객체 생성으로 **오버헤드가 매우 적음**                            |
| **조합성 (Chaining)** | 중첩된 `try-catch` 구조로 인해 연산 체이닝이 어려움                                    | `map`, `flatMap`, `recover` 등 **고차 함수를 통한 선언적 조합 가능** |

### 짚어봐야 할 점 & 엣지 케이스 (비판적 반론)

1. **치명적인 시스템 예외(Fatal Exception)와의 혼동**
    - 네트워크 타임아웃이나 입력값 오류 같은 **비즈니스적 실패**에는 Result가 좋지만, `NullPointerException`, `OutOfMemoryError`, `StackOverflowError` 같은 **프로그래밍 버그나 치명적 시스템 장애**까지 Result로 감싸려고 하면 코드가 지나치게 복잡해지고 방어 로직이 지저분해진다. 치명적 장애는 여전히 예외로 던지는 것이 맞다.

2. **콜백 지옥 또는 보일러플레이트 증가**
    - Result를 중첩해서 사용하거나(`Result<Result<T>>`), 모든 함수마다 타입을 맞추려다 보면 오히려 `try-catch`보다 코드가 더 장황해질 수 있다. (코틀린에서는 `runCatching`이나 적절한 확장 함수로 완화해야 함)

3. **코틀린 코루틴과의 상호작용**
    - 코루틴의 취소 메커니즘(`CancellationException`)은 정상적인 제어 흐름의 일부인데, 무분별하게 `runCatching` 등으로 감싸버리면 코루틴 취소가 정상 작동하지 않고 무시되는 버그가 발생할 수 있다. (취소 예외는 잡지 않도록 예외 처리에 주의해야 함)

## 컨텍스트 엔지니어링

> AI 에이전트가 접근하는 지식, 제약 조건, 아키텍처 규칙, 작업 범위(Scope)를 미리 구조화해두는 것

1. 중요성
- LLM의 성능은 모델 자체의 능력만큼이나 '어떤 맥락을 주었느냐'에 따라 결정됨. 아무리 뛰어난 모델이라도 컨텍스트에 노이즈가 많거나 핵심 정보가 누락되면 환각(Hallucination)이 발생하기 때문에, 정확하고 압축된 맥락을 공급하는 엔지니어링 작업이 AI 애플리케이션의 품질을 좌우함.

2. 구성 요소
- **시스템 지시사항 (System Instructions):** 모델의 역할, 절대적인 제약 조건, 출력 포맷 정의.
- **동적 데이터 주입 (RAG & External Data):** 벡터 DB, 웹 검색 등을 통해 사용자의 질문과 관련된 정확한 외부 지식을 컨텍스트에 실시간으로 삽입.
- **이력 및 메모리 관리 (Memory & History):** 컨텍스트 윈도우 토큰 제한을 관리하기 위해 이전 대화를 압축, 요약하거나 장기 기억을 불러와 주입.
- **구조화된 스키마 (Structured Output):** JSON 등 특정 포맷으로 출력을 유도하기 위한 예시(Few-shot)나 규칙 제공.
