# 1. 배운 점

## value class

> 값 하나를 감싸서 별도 타입으로 구분하게 해주는 Kotlin 기능

- primary constructor에 `val` 프로퍼티 정확히 1개
- 상속 불가, 인터페이스 구현은 가능
- backing field 있는 추가 프로퍼티 불가 (계산 프로퍼티는 가능)
- `init` 블록으로 검증 가능
- nullable, 제네릭, 인터페이스 타입으로 쓰면 박싱될 수 있음
- data class와 달리 항상 객체를 만들지 않음
- 파라미터로 받는 함수는 JVM 시그니처에 해시가 붙어 자바에서 호출하기 불편함 (`@JvmName`으로 우회)

## URI(Uniform Resource Identifier)

> 자원을 식별하기 위한 문자열 체계의 총칭


## URL(Uniform Resource Locator)

> 자원이 **어디에 위치하는지** 그 경로와 프로토콜(http, https, ftp 등)을 포함해 나타내는 주소

## URN (Uniform Resource Name)

> 자원의 위치와 상관없이 고유한 이름(ID)만을 부여하는 방식

- 자원의 위치가 이동하거나 변경되어도 이름(URN)은 바뀌지 않음
- 주소처럼 바로 찾아가기 어려워(실행 가능성이 낮아) 웹에서는 URL에 비해 드물게 쓰임

## TCP(Transmission Control Protocol)

> 전송 계층(Transport Layer)에서 작동하며 송신자와 수신자 간의 **신뢰성 있고 안전한 데이터 전송을 보장**하는 연결 지향형 프로토콜

- **연결 지향 (Connection-oriented)**: 데이터 전송 전 `3-way handshake`로 세션을 맺고 전송 후 `4-way handshake`로 연결을 해제함
- 상태(Stateful)를 유지하는 프로토콜임
- **신뢰성 보장**: 패킷 손실, 중복, 순서 뒤바뀜 등을 감지하여 누락된 패킷의 재전송(ARQ)을 수행함
- **흐름 제어 (Flow Control)**: 수신 측의 버퍼 오버플로우를 막기 위해 송신 속도를 조절함
- **혼잡 제어 (Congestion Control)**: 네트워크 라우터의 과부하를 방지하기 위해 네트워크 상황에 따라 전송 데이터 양을 동적으로 제어함
- **바이트 스트림 기반**: 데이터를 경계 없는 연속된 바이트 스트림으로 취급함

### Byte Stream

> 데이터를 크고 작은 메시지 단위가 아닌 **경계가 없는 연속된 바이트(Byte)의 흐름**으로 간주하여 송수신하는 방식 TCP 같은 연결 지향형 프로토콜이 이 방식을 사용함

- **메시지 경계 부재 (No Message Boundaries)**: 데이터가 독립된 패킷 단위로 나뉘어 전달되지 않고, 수도관을 통해 물이 흐르듯 연속적인 바이트 데이터로 이어져 전달됨
- **유연한 분할과 병합 (Splitting & Merging)**: 송신 측에서 보낸 데이터의 크기와 상관없이 수신 측의 버퍼 상황이나 네트워크 상태에 따라 데이터가 임의의 크기로 쪼개지거나 합쳐져서 읽힐 수 있음
- **애플리케이션 계층의 파싱 필요**: 패킷의 경계가 없기 때문에 데이터를 읽는 프로그램(애플리케이션)이 직접 프로토콜 규격이나 구분자를 확인해 데이터의 끝과 시작을 판단해야 함
- **순서 및 무손실 보장**: 바이트의 흐름이 중간에 끊기거나 순서가 뒤바뀌지 않고 송신 측이 보낸 그대로의 순서와 내용이 수신 측에 안전하게 도달함

## UDP(User Datagram Protocol)

> 연결 설정 과정 없이 데이터를 빠르게 전송하는 데 초점을 맞춘 **비연결형(Connectionless) 전송 계층 프로토콜**

- **비연결형**: 사전 연결 설정(Handshake) 없이 곧바로 목적지로 데이터를 밀어냄
- **신뢰성 미보장 (Best-Effort)**: 패킷의 도달 여부, 순서, 유실 여부를 확인하지 않으며 재전송을 수행하지 않음
- **낮은 오버헤드**: 헤더 구조가 단순(8바이트 고정)하고 제어 로직이 적어 시스템 자원을 적게 소모함
- **속도 우선**: 확인 응답(ACK)을 기다리지 않으므로 지연 시간이 매우 짧음
- **데이터그램 기반**: 데이터를 독립된 패킷(Datagram) 단위로 처리하며 각 패킷의 경계가 유지됨

### Datagram

> 네트워크에서 데이터를 전송할 때 사용하는 독립적인 단위(Packet)를 뜻 주로 UDP 같은 비연결형 프로토콜에서 데이터를 주고받을 때 사용되는 용어

- **독립성**: 각 데이터그램은 저마다 출발지와 목적지 주소(IP, 포트)를 포함하고 있어서 다른 패킷과 경로가 달라도 혼자서 목적지까지 찾아갈 수 있음
- **비연결성**: 송신 측과 수신 측이 사전에 연결을 맺지 않고 데이터그램 단위로 그냥 던지는 방식
- **신뢰성 부재**: 중간에 패킷이 유실되거나 순서가 뒤바뀌어도 데이터그램 자체는 이를 스스로 복구하거나 재전송하지 않음
- **가벼운 구조**: TCP처럼 연결 상태를 유지하기 위한 복잡한 제어 정보가 없기 때문에 헤더가 단순하고 속도가 빠름

## 소켓

> 네트워크상에서 프로그램(프로세스)이 데이터를 주고받을 수 있도록 해주는 **소프트웨어적인 통신 단자(엔드포인트)**
- **IP와 Port의 조합**: 소켓은 `IP 주소`와 `포트 번호`로 구성됨 (예: `127.0.0.1:8080`) 네트워크상에서 어떤 기기의 어떤 애플리케이션과 통신할지 식별하는 역할
- **통신 추상화**: 운영체제(OS)가 제공하는 API로, 애플리케이션이 전송 계층(TCP/UDP)의 복잡한 네트워크 제어 과정을 몰라도 파일처럼 쉽게 데이터를 읽고 쓸 수 있게 만들어 줌
- **주요 유형**:
  - **스트림 소켓 (TCP)**: 연결 지향형, 신뢰성과 순서가 보장되는 바이트 스트림 통신
  - **데이터그램 소켓 (UDP)**: 비연결형, 속도가 빠른 독립적 데이터그램 통신

## HTTP(HyperText Transfer Protocol)

> 웹상에서 클라이언트(브라우저 등)와 서버 간에 리소스(HTML 문서, 이미지, 영상, JSON 등)를 주고받기 위해 사용하는 **애플리케이션 계층(Application Layer) 통신 프로토콜**
- 기본 HTTP 통신은 '1요청 = 1응답'이지만 연결을 유지하며 연속 전송하는 SSE(1:N)나 HTTP를 벗어난 자유로운 양방향 **웹소켓**으로 확장됨
- **클라이언트-서버 구조**: 요청을 보내는 클라이언트(Client)와 요청에 응답하는 서버(Server) 구조로 동작함
- **비연결성 (Connectionless)**: 클라이언트가 요청을 보내고 서버가 응답을 마치면 즉시 연결을 끊어 서버 자원을 효율적으로 관리함 (HTTP/1.1부터는 Keep-Alive로 어느 정도 유지 가능)
- **무상태 (Stateless)**: 서버가 클라이언트의 이전 상태나 요청 기억하지 못함 매 요청이 독립적이며 상태 유지가 필요한 경우 쿠키(Cookie), 세션(Session), 토큰(JWT) 등을 사용함
- **메시지 기반 (Plain Text / Binary)**: 사람이 읽을 수 있는 평문(HTTP/1.x) 또는 바이트 전송 최적화 방식(HTTP/2, HTTP/3)의 메시지(헤더 + 본문) 형태로 데이터를 교환함
- **TCP/UDP 기반**: 주로 TCP(포트 80) 위에서 동작하며 최신 버전인 HTTP/3는 UDP 기반의 QUIC 프로토콜을 사용함
- **클라이언트는 서버로 HTTP 요청을 보내기 직전까지 실제로 서버가 동작하는지 알 방법이 없다**
  - 이런 한계를 보완하려고 실제 서비스에서는 주기적으로 상태를 확인하는 헬스 체크(Health Check)나 **하트비트(Heartbeat)** 같은 별도의 메커니즘을 함께 사용
### HTTP 요청 메서드

> 클라이언트가 서버에게 요청의 목적(리소스 조회, 생성, 수정, 삭제 등)을 알리기 위해 사용하는 표준 명령어

- **GET**:
  - 리소스 **조회**
  - 서버의 데이터를 변경하지 않으며(안전성 Safe) 여러 번 호출해도 결과가 같음 데이터가 URL의 쿼리 스트링(`?key=value`)에 노출됨

- **POST**:
  - 리소스 **생성(등록)**
  - 서버의 상태나 데이터를 변경하며 새로운 리소스를 만듦 데이터는 HTTP 본문(Body)에 담겨 전송됨

- **PUT**:
  - 리소스 **전체 수정(대체)**
  - 해당 리소스가 있으면 완전히 덮어씌우고 없으면 새로 생성함

- **PATCH**:
  - 리소스 **일부 수정**
  - 리소스의 특정 필드만 골라서 변경할 때 사용함

- **DELETE**:
  - 리소스 **삭제**
  - 지정한 리소스를 제거함

### HTTP 상태 코드 (Status Codes)

> 클라이언트가 보낸 요청이 성공적으로 처리되었는지 아니면 문제가 발생했는지를 서버가 알려주는 3자리 숫자 코드

**범주별 주요 코드**:

- **1xx (Informational)**: 요청을 받았으며 처리 중 (임시 상태)

- **2xx(Successful)**: 요청이 성공적으로 처리됨
  - `200 OK`: 요청 성공
  - `201 Created`: 요청이 성공하여 새로운 리소스가 생성됨 (POST 등)

- **3xx(Redirection)**: 요청을 완료하기 위해 추가 조치(리다이렉트 등)가 필요함
  - `301 Moved Permanently`: 요청한 리소스의 URI가 영구적으로 이동됨
  - `304 Not Modified`: 리소스가 수정되지 않았으므로 캐시된 데이터를 사용함

- **4xx(Client Error)**: 클라이언트의 잘못된 요청이나 권한 문제로 처리할 수 없음
  - `400 Bad Request`: 잘못된 문법이나 파라미터로 인해 서버가 요청을 이해하지 못함
  - `401 Unauthorized`: 인증(Authentication)이 되지 않음 (로그인 필요)
  - `403 Forbidden`: 서버가 요청을 거부함 (권한 없음)
  - `404 Not Found`: 요청한 리소스를 찾을 수 없음

- **5xx(Server Error)**: 서버 측 문제로 요청을 처리하지 못함
  - `500 Internal Server Error`: 서버 내부 코드 에러나 예외 발생
  - `503 Service Unavailable`: 서버가 과부하 상태이거나 점검 중이어서 요청을 처리할 수 없음

### Restful API

> REST(Representational State Transfer) 아키텍처의 원칙과 규칙을 따르는 API 설계 방식 HTTP 프로토콜의 장점을 최대한 활용하여 네트워크 상에서 자원을 정의하고 주고받는 표준화된 방법

- **자원 중심 (Resource-Based)**: 모든 자원은 고유한 URI(식별자)를 가지며 주소는 동사가 아닌 **명사**로 표현함 (예: `/users`, `/posts/1`)
- **행위는 HTTP 메서드로 표현**: 자원에 대한 조작은 URL에 행위(동사)를 적지 않고 HTTP 메서드(`GET`, `POST`, `PUT`, `DELETE`)로 분리해서 정의함
- **무상태성 (Stateless)**: 서버는 클라이언트의 상태(세션 등)를 기억하지 않고 매 요청이 독립적임
- **캐시 가능성 (Cacheability)**: 기존 HTTP 웹 인프라의 캐시 기능을 그대로 사용하여 성능을 높일 수 있음
- **독립성 (Client-Server Separation)**: 클라이언트와 서버의 역할이 명확히 분리되어 서로의 개발 독립성을 보장함

### 쿠키 (Cookie)

> 클라이언트(브라우저) 측에 텍스트 형태로 저장되는 작은 데이터 파일


- **저장 위치**: 클라이언트(브라우저) 로컬 디스크
- **동작 방식**: 서버가 응답할 때 `Set-Cookie` 헤더로 쿠키를 보내주면 이후 클라이언트는 모든 HTTP 요청에 쿠키를 자동으로 포함해서 보냄
- **만료 기한**: 만료일을 설정할 수 있어 브라우저를 닫아도 유지될 수 있음
- **보안 취약**: 클라이언트에 노출되므로 탈취(XSS 등)되기 쉬워 민감한 정보(비밀번호 등)를 직접 담기엔 부적절함

### 세션 (Session)

> 클라이언트의 상태 정보를 **서버 측**에 저장하고 관리하는 방식

- **저장 위치**: 서버 메모리 또는 저장소 (DB, Redis 등)
- **동작 방식**: 사용자가 인증(로그인)을 거치면 서버가 고유한 `세션 ID`를 발급하고 클라이언트는 이 세션 ID를 쿠키(예: `JSESSIONID`)로 저장해 매 요청마다 보냄. 서버는 세션 ID를 통해 서버에 저장된 사용자 데이터를 꺼내 씀
- **보안성**: 실제 사용자 데이터가 서버에 안전하게 보관되므로 쿠키보다 안전함
- **만료 / 소멸**: 브라우저를 닫거나 서버에서 설정한 유효 시간이 지나면 소멸됨

### 응답 없음

> 클라이언트가 HTTP 요청을 보냈지만 서버로부터 제때 응답을 받지 못하고 대기 상태에 빠지는 현상

주요 대응방법
- **타임아웃 설정 (Timeout)**: 클라이언트나 게이트웨이에서 무한정 기다리지 않도록 제한 시간(`Connect Timeout`, `Read Timeout`)을 두어 일정 시간 지나면 강제로 에러 처리
- **서킷 브레이커 (Circuit Breaker)**: 특정 서비스에서 응답 없음이 반복되면 장애 전파를 막기 위해 일시적으로 요청을 차단하고 빠르게 실패(Fail-fast) 처리
- **멱등성(Idempotency) 고려한 재시도**: 응답이 없어 재시도(Retry)할 때 동일한 요청이 중복 실행되어도 데이터가 망가지지 않도록 설계
