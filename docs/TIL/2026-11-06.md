# 1. 배운 점

## 응집도

> 모듈 **내부**의 요소(함수, 클래스, 데이터 등)들이 얼마나 밀접한 관련이 있고, 단일 목적을 위해 협력하는지 나타내는 정도.

- 하나의 모듈이 단 하나의 명확한 책임(Single Responsibility)에 집중하고, 내부 기능들이 서로 긴밀하게 연관되어 작동할 때 응집도가 높다고 한다.
- 응집도가 높으면 코드의 가독성이 좋아지고 유지보수가 쉬우며 재사용성이 높아진다.

- 높은 응집도: 모듈이 하나의 특정 작업이나 기능에 집중
    - UserAuthentication 클래스 : 로그인, 로그아웃, 비밀번호 변경 기능
- 낮은 응집도 : 모듈이 여러 가지 서로 관련 없는 작업을 수행
    - Util 클래스 : 문자열 처리, 파일 읽기, 날짜 계산 기능

## 결합도

> 모듈 **간**에 서로 얼마나 의존하고 있는지 나타내는 지표.

- 한 모듈이 변경될 때 다른 모듈도 함께 수정해야 하는 정도를 의미한다.
- 결합도가 낮으면(Loose Coupling) 특정 모듈을 수정하거나 교체해도 다른 모듈에 미치는 영향(사이드 이펙트)이 최소화된다.

- 낮은 결합도 : 모듈이 서로 독립적으로 작동할 수 있을 때
    - UserAuthentication 클래스가 특정 클래스가 아니라 인터페이스를 통해 사용자 정보를 가져오는 경우
- 높은 결합도 : 모듈이 서로 강하게 연결되어 있을 때
    - UserAuthentication 클래스가 특정 클래스의 내부 구현에 직접 의존하는 경우

## 좋은 코드를 위해 의식하면 좋은 코드 작성 원칙

> 좋은 설계를 위해 높은 응집도, 낮은 결합도를 목표로 한다

1. DRY (Don't Repeat Yourself)
- 반복하지 마라.
- 같은 코드를 복사-붙여넣기(`WET`)하지 말고 함수로 분리해라

2. PIE (Program Intentionally and Expressively)
- 의도를 가지고 명확하게 표현하라.
- 코드가 무엇을 하는지 의도가 명확하게 드러나도록 작성해야 한다.

3. SDP (Stable Dependencies Principle) - 안정된 의존성 원칙
- **더 안정된 방향**으로 의존해야 함.
- 자주 바뀌는(불안정한) 모듈이 자주 안 바뀌는(안정한) 모듈에 의존하게 만들어야 함.
- 쉽게 변하는 코드가 핵심적이고 안정적인 코드를 의존하면 연쇄적으로 무너짐.

4. ADP (Acyclic Dependencies Principle) - 의존성 비순환 원칙
- 의존성 관계에 순환(Cycle)이 있어서는 안 됨.
- 순환 참조가 발생하면 컴포넌트 간의 경계가 무너지고 빌드나 테스트가 지옥이 됨.
- 의존 방향은 항상 단방향(Acyclic) 계층 구조를 유지해야 함.

### SOLID 원칙

1. SRP (Single Responsibility Principle) - 단일 책임 원칙
- 하나의 클래스는 단 하나의 변경 이유(책임)만 가져야 한다.
- 클래스가 너무 많은 역할을 맡으면 코드가 복잡해지고 수정할 때 다른 곳에 영향을 주기 쉬우므로, 책임을 철저하게 분리해야 한다.

2. OCP (Open-Closed Principle) - 개방 폐쇄 원칙
- 확장에는 열려 있어야 하고, 변경에는 닫혀 있어야 한다.
- 기존의 코드를 수정하지 않고도(Closed) 다형성을 이용해 새로운 기능을 덧붙일 수 있어야(Open) 한다.

3. LSP (Liskov Substitution Principle) - 리스코프 치환 원칙
- 서브 타입은 언제나 자신의 기반 타입(부모)으로 교체할 수 있어야 한다.
- 자식 클래스가 부모 클래스의 자리를 대체했을 때 프로그램이 정상 작동해야 한다. 부모의 규약이나 기대치를 깨뜨리면 안 된다.

4. ISP (Interface Segregation Principle) - 인터페이스 분리 원칙
- 자신이 사용하지 않는 메서드에 의존하지 말아야 한다.
- 덩치 큰 범용 인터페이스 하나보다, 작고 구체적인 인터페이스 여러 개로 쪼개서 클라이언트가 꼭 필요한 기능만 알게 해야 한다.

5. DIP (Dependency Inversion Principle) - 의존성 역전 원칙
- 추상화에 의존해야지, 구체화에 의존하면 안 된다.
- 자주 바뀌는 구체적인 클래스 대신, 변하지 않는 추상 클래스나 인터페이스(역할)에 의존해야 한다.

## 디자인 패턴

> 소프트웨어 개발 중에 자주 발생하는 반복적인 문제들을 해결하기 위해 검증된 **설계 재사용 가이드라인**이다.

- **코드 재사용성**: 검증된 구조를 사용하여 바퀴를 다시 발명하는 것을 방지.
- **유지보수성과 확장성**: 결합도를 낮추고 응집도를 높여 OCP, DIP 같은 원칙을 자연스럽게 적용 가능.
- **소통 효율성**: 개발자 간의 공통 언어(Vocabulary)로 기능하여 설계 의도를 빠르게 공유 가능.

1. 빌더 패턴 (Builder)
- 복잡한 객체를 단계별로 생성할 때 사용.
- 생성자에 인자가 너무 많을 때(생성자 오버로딩 지옥) 어떤 인자가 무엇을 의미하는지 파악하기 어렵고 실수하기 쉽다. 빌더 패턴은 메서드 체이닝을 통해 필요한 값만 명시적으로 안전하게 주입하며 객체를 생성할 수 있게 해준다.

2. 팩토리 메서드 패턴 (Factory Method)
- 객체 생성을 서브클래스에 위임하여, 클라이언트가 구체적인 클래스에 의존하지 않게 함.
- 객체를 생성하는 코드를 별도의 팩토리 메서드로 분리하여, 새로운 클래스가 추가되더라도 기존 코드를 수정하지 않고 확장할 수 있게 해준다(OCP 준수).

3. 싱글턴 패턴 (Singleton)
- 애플리케이션 전역에서 단 하나의 인스턴스만 생성되도록 보장하고, 어디서든 이 인스턴스에 접근할 수 있게 공유함.
- 인스턴스가 여러 개 생기면 자원이 낭비되거나 문제가 발생하는 객체에 적용한다. 다만 전역 상태를 공유하게 되어 결합도가 높아질 수 있으므로 주의해야 한다.

4. 데코레이터 패턴 (Decorator)
- 기존 객체의 코드를 수정하지 않고 런타임에 동적으로 새로운 기능을 덧붙임.
- 상속을 사용하면 기능 확장마다 클래스가 기하급수적으로 늘어나는 문제가 발생한다. 데코레이터는 객체를 감싸는(Wrap) 방식으로 원래 코드를 건드리지 않고 책임을 유연하게 추가한다.

5. 파사드 패턴 (Facade)
- 복잡한 서브시스템들의 집합에 대해 단순하고 일관된 하나의 통합 인터페이스를 제공함.
- 클라이언트가 복잡한 내부 구조를 일일이 알 필요 없이, 파사드 객체가 제공하는 간단한 메서드 하나만 호출하면 내부의 여러 모듈이 알아서 협력하여 작업을 처리하도록 숨겨준다.

6. 이터레이터 패턴 (Iterator)
- 컬렉션의 내부 구현 방식(배열, 리스트, 트리 등)을 노출하지 않고 원소들을 순차적으로 접근할 수 있게 해줌.
- 자료구조가 무엇이든 상관없이 동일한 인터페이스(`hasNext()`, `next()`)로 순회할 수 있어 클라이언트 코드가 자료구조 변경에 영향받지 않는다.

7. 옵저버 패턴 (Observer)
- 한 객체의 상태가 바뀔 때, 그 객체에 의존하는 다른 객체들에게 자동으로 변화가 통지되도록 함.
- 발행-구독(Publish-Subscribe) 모델의 기본이 되는 패턴이다. 이벤트가 발생했을 때 연관된 객체들을 직접 호출하는 대신, 옵저버로 등록해 두어 상태 변화를 알아서 수신하게 만든다.

8. 전략 패턴 (Strategy)
- 동일한 목적을 수행하는 여러 알고리즘(로직)을 각각의 클래스로 캡슐화하여, 런타임에 상황에 맞게 유연하게 바꿔 끼울 수 있게 함.
- `if-else`나 `switch`문으로 분기 처리하는 복잡한 코드를 깔끔하게 정리할 수 있음. 새로운 알고리즘을 추가할 때 기존 코드를 수정하지 않고(OCP 준수) 새로운 구현체 클래스만 만들면 되므로 확장성이 매우 뛰어남.

## 비즈니스 규칙 - 도메인 레이어

> UI 레이어와 데이터 레이어 사이에 위치하는 선택적(Optional) 레이어로, 앱의 핵심 **비즈니스 로직과 규칙**을 처리하는 순수 자바/코틀린 영역이다.

- **플랫폼 독립성**: 안드로이드 프레임워크나 UI 관련 라이브러리(Context 등)에 전혀 의존하지 않으므로 순수하게 비즈니스 로직만 테스트하기 매우 쉽다.
- **단일 책임 (SRP)**: 하나의 유스케이스(UseCase)가 하나의 단일 비즈니스 규칙만 담당하여 코드가 명확해진다.
- **재사용성**: 서로 다른 여러 UI/ViewModel에서 동일한 비즈니스 규칙이 필요할 때 중복 코드를 줄이고 공용으로 호출할 수 있다.
- **Model (도메인 모델)**: 외부 API나 DB 스키마에 종속되지 않은, 앱 내에서 사용하는 순수한 비즈니스 데이터 객체.
- **UseCase / Interactor (유스케이스)**: 앱이 수행하는 개별 비즈니스 작업(예: `LoginUseCase`, `CalculateTotalPriceUseCase`)을 정의한 클래스. 보통 하나의 핵심 메서드(또는 `invoke` 연산자)를 가짐.

### 데이터 실패 vs 규칙 실패

1. **기술/데이터 실패 (`Repository`)**
- 네트워크 끊김, 데이터베이스 조회 실패(`Not Found`), 서버 오류 등 외부 요인이나 시스템 결함으로 인해 데이터를 가져오는 행위 자체가 실패한 경우.

2. **비즈니스 규칙 실패 (`Domain / Business Logic`)**
- 통신이나 데이터 조회는 정상적으로 완료되었으나, 서비스의 핵심 정책이나 규칙(조건)에 위배되어 요청을 수행할 수 없는 경우 (예: 잔액 부족, 레벨 제한, 횟수 초과 등).
## 하향식 접근, 상향식 접근

1. 하향식 접근 (Top-Down Approach)
- 전체 시스템의 큰 그림(최상위 목표)에서 시작해 점점 더 작은 하위 모듈과 세부 기능으로 쪼개나가는 방식.
- 세부 구현 단계에서 예상치 못한 기술적 제약이 발견되면 전체 구조를 수정해야 할 수도 있음.
- 요구사항이 명확하고 대규모 시스템 설계에 유리함.

2. 상향식 접근 (Bottom-Up Approach)
- 가장 기초적이고 작은 단위의 부품(함수, 클래스, 모듈)부터 먼저 만들고, 이를 조립해서 점진적으로 상위 시스템을 완성해 나가는 방식.
- 전체적인 큰 그림을 놓치기 쉽고, 나중에 부품들을 조립할 때 통합 과정이 복잡해질 수 있음.
- 애자일(Agile) 개발, MVP(최소 기능 제품) 제작, 새로운 기술 스택을 탐색하며 빌드업하는 서비스 초기 단계에 적합함.

실제 서비스 개발에서는 두 방식을 혼용하는 경우가 많음. 전체적인 서비스 아키텍처와 핵심 비즈니스 로직은 **하향식**으로 큰 그림을 그리되, 신기술 도입이나 성능이 중요한 특정 핵심 모듈은 **상향식**(프로토타입 검증)으로 접근하는 방식이 주로 쓰임.

# 3. 트러블 슈팅

## 도메인 모델 설계 시 DTO와 혼동하고, 기능 도출 없이 Repository·UseCase로 넘어간 문제

### 1. 문제 상황
1. 모델 클래스를 설계했는데 도메인 모델이 아니라 **DTO 형태**(화면 필드 나열)가 됐다.
2. **기능(사용자 동작)을 먼저 정리해야 했는데**, 그 단계를 건너뛰고 바로 Repository와 UseCase 구성으로 넘어갔다.

### 2. 원인

1. **도메인 모델 대신 DTO를 설계했다.** 모델을 웹 게시판 경험의 엔티티(필드 묶음)로 이해해서, 화면 필드를 그대로 나열한 DTO 형태로 만들었다. 개념을 표현하는 도메인 모델과 구분하지 못했다.
2. **기능 도출 단계를 건너뛰었다.** `UI 분석 → 도메인/속성 → 기능 도출 → Repository 메서드` 순서를 따라야 했는데, 기능 목록 없이 바로 Repository와 UseCase 구성으로 넘어갔다.
3. **근거 없이 Repository 메서드를 만들었다.** 기능이라는 근거가 없으니 메서드가 "필요한 동작"이 아니라 "화면에 필요한 데이터 조합"(= UseCase)이 됐고, Repository와 UseCase의 책임이 섞였다.

### 3. 배운 점

- **모델의 정의**: 모델은 화면을 그리기 위한 클래스가 아니라, **앱이 다루는 대상(개념)을 표현하는 클래스**다. 화면이나 서버 API가 바뀌어도 유지되면 도메인 모델, 바뀌어야 하면 DTO나 UI 모델이다.
- **설계 순서**: **기능(요구) → Repository(데이터 접근) → UseCase(조합)** 순서로 내려가야 한다. 기능 목록은 Repository 메서드가 **왜 필요한지의 근거**가 되고, 중간 단계를 건너뛰면 계층의 책임이 섞인다.
- **화면 분석 방법**: "보이는 것"에서 **명사**(상품, 리뷰 등)를 뽑아 도메인 모델과 속성을 만들고, "누르거나 입력하는 것"에서 **동사**(조회, 검색, 찜, 작성 등)를 뽑아 기능 목록과 Repository 메서드로 만든다.
