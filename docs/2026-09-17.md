# 1. 배운 점

- **잘못 파일 삭제** : 인텔리제이 히스토리를 통해 복구 가능
* 단위테스트 : 모듈이 잘 작동하는지 테스트하는 가장 작은 단위의 테스트

### 테스트 장점

- 조기 장애 감지
- 신속한 피드백 가능(어느 지점에서 장애가 발생하는지 특정하기 쉬움)
- 리팩터링해도 정상 작동 확인 가능

#### 화이트박스

- 내부 구조와 동작 테스트
- 로직, 제어 및 데이터 흐름 검증에 사용

#### 블랙박스

- 내부 동작은 무시하고 기능을 테스트
- 입력 시 출력값이 정상으로 나오는지 테스트
- `테스트 기법(입력 예시)` : 입력이 1 ~ 100
  - `경계값 분석` : 0, 1, 2, 99, 100, 101을 뽑아 경계값을 테스트
  - `동등 분할` : 1 ~ 100 사이 대표값 1개만 테스트

### Java가 등장한 가장 큰 이유

- 해당 시기 기존 언어(**C/C++**)언어는 **특정CPU**나 **OS**에 맞춰
  **컴파일**을 해야 했는데 **스펙 변경**이 일어나면 해당 사항에 맞게 코딩을 해야 했음
  해당 문제를 해결하기 위해 플랫폼 독립적인 Java를 개발하게 됨

| **구분**     | **C/C++**                                                   | **Java**                                              |
| ---------- | ----------------------------------------------------------- | ----------------------------------------------------- |
| **특징**     | 하드웨어 제어, 좋은 성능                                              | 객체지향, 플랫폼 독립성(**JVM**)                                |
| **종속성**    | `종석적` : **OS**맞는 컴파일러를 통해 컴파일<br>-> Window, Linux 다른 컴파일 사용 | `독립적` : **JRE**가 설치되어 있으면 **JVM**을 통해<br>어떤 OS든 실행 가능 |
| **메모리 관리** | 개발자가 직접(**누수 위험**)                                          | 기본적으로 **GC**통해 자동으로 관리(**누수 위험 적음**)                  |
| **컴파일 방식** | 컴파일러                                                        | 하이브리드(컴파일러 + 인터프리터)                                   |

- `누수` : 필요하지 않는 메모리를 해제하지 않아 계속해서 메모리를 차지하는 현상
- `JVM` : **Java**를 돌릴 수 있는 **가상 컴퓨터**
- `JRE` : **Java 실행 환경** 제공(**JVM** + 라이브러리)
- `JDK` : **JRE** + 개발 킷
- `컴파일러` : **실행 전**(빌드 시) **컴파일**하는 방식
- `인터프리터` : **실행 시** 한 줄씩 **즉시 번역**해 실행
- 자주 쓰는 코드를 기계어로 변환해 인터프리터를 통하지 않고 바로 기계어로 실행
- `컴파일` : **사람**이 이해하기 쉬운 **소스 코드**를 **컴퓨터**가 **실행**할 수 있도록 변환하는 과정
- `바이트코드` : **VM**이 이해 가능한 코드
- `바이너리코드` : 컴퓨터가 이해 가능한 **이진코드**

- `참조(레퍼런스)타입` : 실제 값이 아닌 데이터가 저장된 **메모리 번지**를 저장
- `값(프리미티브)타입` : **실제 값**을 저장

### GC

* 자동으로 **동적 할당**한 메모리 중 **쓰이지 않는 메모리**를 찾아 **공간을 비워주는 관리 시스템**

#### GC 알고리즘

#### 참조 카운팅

- 객체에 자신을 가리키는 **참조의 개수를 보관**
- 누군가 객체를 참조하면 카운터 +1, 끊어지면 -1
- **카운터가 0**이 되는 **즉시 메모리 해제**

**장점**

- 카운트가 0이 되는 순간 바로 해제되므로 **예측 가능**
- 한 번에 일괄적으로 정리하지 않아 **길게 멈추지 않음**

**단점**

- 두 개 이상의 객체가 **서로를 참조**하면  외부에서 해당 객체에 접근이 불가해도
  **카운트가 0**이 되지 않아 **누수 발생**

#### 마크 앤 스윕(Java 채용)

- **마크** : 루트로 부터 **연결된 객체**를 찾아냄
- **스윕** : 연결이 **끊어진 객체**는 제거
- **압축** : **메모리 파편화**를 제거를 위해 **한쪽으로 모음** (필수는 아님 GC마다 다름)

- `파편화` : **빈 공간**이 생기면서 **큰 데이터**를 할당하기 어려운 상태

**장점**

- 순환 참조가 있어도 **루트 스페이스**로 부터 접근할 수 없다면 제거

**단점**

- **의도적으로 GC**를 실행시켜야 함(**타이밍이 존재**)
- **STW(StopTheWorld)** : 마크하는 동안 참조관계가 변하면 안 되므로 **실행을 멈춤**
- 메모리 크기가 클수록 **오버헤드**가 커짐

**루트 스페이스(JVM 기준)**

- Stack 영역의 **지역 변수**
- Metaspace(Method Area)의 **static 변수**
- Native Method Stack의 **JNI 참조**

* `JNI(JavaNativeInterface)` : **C/C++** 와 **Java** 사이에서 서로 호출할 수 있게 해주는 **인터페이스**


### 영 제네레이션

- **승격(Promotion)** : **특정 나이(기본값 15)**에 도달하면 **올드 제네레이션**으로 이동

**MinorGC**
- **영 제네레이션**에서 발생하는 GC
- **Eden**이 꽉 차면 GC가 발생하며 살아남은 객체는 **나이 증가**
#### Eden
- 객체가 **생성될 때** 할당되는 공간
- 영역이 **가득차게 되면** **Minor GC**발생
- 생존한 객체는 **Survivor영역**으로 이동
- GC가 일어나면 **완전히 비워진 상태**
#### Survivior
- Eden에서 **살아남은 객체**들이 존재
- **S0, S1** :
  - 둘 중 한 곳에만 데이터가 존재
  - GC 발생 시 S0, S1 사이에서 **이사**

### 올드 제네레이션

- 영에서 오랫동안 살아남은 객체들이 저장
- Major GC :
  - 올드 제네레이션에서 발생하는 GC
  - 영역이 영보다 크고 저장된 객체가 많아 시간이 오래 걸림

#### Full GC

- **힙 영역 전체**를 대상으로 하는 GC
- 메모리가 부족할 때
- 매우 느림

### Java 번역 과정

- `1단계` : .java -> .class(바이트코드)
- `2단계` : **클래스 로더**를 통해 **바이트코드**를 **Runtime Data Area**에 적재
- `3단계` : **Execution Engine**를 통해 **바이트코드**를 명령어 단위로 읽어
  **인터프리터 + JIT 컴파일러**로 혼용하여 실행한다

`JIT 컴파일러` :  **인터프리터**의 단점을 보완하기 위해 등장

### 클래스 로더

- 이름을 알고 있는 **특정 클래스**에 대한 **바이트코드**를 가져오는 역할

- `부트스트랩 클래스 로더` : 자바 **기본 API** 로딩
- `플랫폼 클래스 로더(기존 확장 클래스 로더)` : **확장** 클래스 로드
- `애플리케이션 클래스 로더` : **개발자**들이 짜는 클래스 로드
  - sun.misc.Launcher.AppClassLoader에 의해 로드

### Java 클래스 로딩

- 클래스 **로딩 및 링킹** 과정이 **런타임**에 이루어짐
- 실행 성능이 저하 될 수 있으나 **높은 확장성**과 **유연성**을 제공
  - **인터페이스**만 맞으면 런타임에 **구현 클래스**를 결정하지 않아도 된다
  - 실행할 프로그램 코드를 **네트워크로 수신**도 가능
- 해석단계는 **동적바인딩**혹은 **늦은 바인딩**을 지원할 목적으로 지연될 수 있다

- `링킹` : 필요한 클래스 **파일이나 라이브러리**를 **연결**해 **사용**할 수 있게 만드는 과정
- `바인딩` : 변수, 함수, 클래스 등 속성을 **실제 값이나 메모리 주소**에 **연결**하는 것
- `동적 바인딩` : 런타임에 호출할 함수나 메서드를 **결정**하는 기술

### 클래스 로딩 과정

#### 1단계 클래스 검증

- 파일 형식(.class) -> 클래스 메타데이터 -> 바이트코드(보안위협에 대한 검증) -> 심벌 참조

- `클래스 메타데이터` : 클래스 구조 정보, 메서드, 변수가 어떻게 생겼는지 설명해 주는 **설계도 정보**
- `심벌 참조` : 메모리 주소 대신 **문자열**으로 대상(클래스, 메서드 등)을 간접으로 가리키는 방식

#### 2단계 준비 및 해석

- 객체 인스턴스가 저장될 메모리 공간을 확보하고 0으로 초기화
- 생성자 호출 전 상태(필드 초깃값은 생성자 호출 시 변경)
  - 단 심볼릭 상수(static final) 필드는 값을 할당
- 해석은 **상수 풀**의 심벌 참조를 직접 참조로 대체하는 과정(바인딩)

- `상수 풀` : **리터럴 상수, 심볼릭 참조**를 모아둔 저장소(메모리 테이블)
- `리터럴 상수` : **이름이 없고** 값 자체로 존재하는 **고정된 데이터** **"str", 1, 3.14** 등

#### 3단계 Heap 영역에 객체 생성

- 객체 저장을 위한 메모리 공간 확보 후 0으로 초기화(객체 헤더(메타데이터) 제외)
- 객체 초기화를 위한 구성설정 실시(Java Object Layout)
  - 클래스 이름 및 메타 정보 확인 방법
  - 해시코드
  - GC 세대 나이
- 생성자 호출(init)

- `해시코드` : 객체를 식별하기 위한 고유한 번호
- `GC 세대 나이` : 나이 0으로

### JVM 런타임 데이터 영역

#### 힙영역(쓰레드 공유 영역)

- new로 생성된 모든 객체와 배열 메모리 할당
- GC에 의해 관리
- 정적 변수, 상수 풀 정보 저장

#### 논힙 메모리

- VM Heap 외부인 OS 메모리를 직접 사용하는 영역

#### 메타스페이스

- 메타데이터 및 메서드 관련 정보 저장
- 사용하지 않는 클래스에 대한 메타 데이터들은 회수 대상(GC)

#### 쓰레드 프라이빗 영역

- **스택** : 지역 변수, 매개변수, 리턴 값 등
- **PC 레지스터** : 실행 중인 JVM 명령어의 주소를 가리킴
- **네이티브 메서드 스택** : C/C++, 어셈블리 등 네이티브 코드 실행용 공간
