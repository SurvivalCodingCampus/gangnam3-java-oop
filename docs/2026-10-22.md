# Model Class, Repository 개념 / Test 이론

## 용어 정리

- `모델 클래스`: 앱에 보여일 데이터를 담는 순수한 객체. `도메인 모델` `Entity` `POJO` `VO` `data class` 와 관련
- `도메인`: 소프트웨어로 해결하고자 하는 현실 세계의 비즈니스/문제 영역
- `모델링`: 현실 세계의 복잡한 대상을 앱개발에 필요한 데이터와 규칙만 추려내어 단순화하는 작업
- `Repository`: `데이터 원천(DataSource)` 을 숨기고, 비즈니스 로직에 필요한 형태로 데이터를 제공하는 창구. 데이터가 어디서 오는지 신경쓰지 않도록 `캡슐화`
- `Test Double`: 테스트를 진행하기 어려운 경우에 테스트가 가능하도록 만들어주는 객체

## 클래스 작성 테스트 코드

```kotlin
class UserRepositoryImplTest {

    private lateinit var dataSource: UserDataSource
    private lateinit var userRepository: UserRepository

    @BeforeEach
    fun setUp() {
        dataSource = FakeUserDataSource()
        dataSource.saveUsers(
            listOf(
                createUser(id = 1, username = "Bret"),
                createUser(id = 2, username = "Antonette"),
                createUser(id = 3, username = "Samantha"),
            )
        )

        userRepository = UserRepositoryImpl(dataSource)
    }

    @Test
    fun `getUsers는 저장된 모든 유저를 반환한다`() {
        val users = userRepository.getUsers()

        assertEquals(3, users.size)
        assertEquals(listOf(1, 2, 3), users.map { it.id })
    }

    @Test
    fun `getUsersTop10ByUserName은 username 오름차순으로 정렬해 반환한다`() {
        val users = userRepository.getUsersTop10ByUserName()

        assertEquals(listOf("Antonette", "Bret", "Samantha"), users.map { it.username })
    }

    @Test
    fun `getUsersTop10ByUserName은 유저가 10명을 넘으면 10명만 반환한다`() {
        dataSource.saveUsers(
            (1..11).map { createUser(id = it, username = "user$it") }
        )

        val users = userRepository.getUsersTop10ByUserName()

        assertEquals(10, users.size)
    }

    private fun createUser(
        id: Int = 1,
        username: String = "username",
    ) = User(
        id = id,
        name = "name",
        username = username,
        email = "test@test.com",
        address = Address(
            street = "street",
            suite = "suite",
            city = "city",
            zipcode = "00000-0000",
            geo = Geo(lat = "0", lng = "0"),
        ),
        phone = "000-0000-0000",
        website = "test.com",
        company = Company(
            name = "company",
            catchPhrase = "catchPhrase",
            bs = "bs",
        ),
    )
}
```

## 정리

- `Model Class의 책임과 역할`
  - 앱의 비즈니스 로직과 화면에서 실제로 다루는 핵심 데이터를 표현하는 클래스.
  - 별도의 기능을 가지지 않는 순수한 클래스.
  - `DataSource` 로부터 읽어온 데이터를 앱에서 안전하고 편리하게 다룰 수 있도록 앱개발을 편리하게 한다.

- `Repository의 책임과 역할`
  - 비즈니스 로직을 위한 `단일 데이터 창구 (Single Source of Truth)`
  - 비즈니스 로직과 `데이터 소스` 사이를 중재
  - `데이터 소스` 의 세부 구현 은닉
  - 비즈니스 요구사항에 맞춘 데이터 가공
  - 여러 `데이터 소스` 의 조합 및 동기화

- `Repository 패턴의 이점`
  - `데이터 접근 추상화`
    - `데이터 소스` 구현 세부사항 은닉
    - 일관된 인터페이스 제공
  - `유지보수성 향상`
    - 관심사 분리
    - 코드 재사용성
  - `테스트 용이성`
    - `데이터 소스` `Mocking` 가능
    - 단위 테스트 작성 용이
  - `확장성`
    - 새로운 `데이터 소스` 추가 용이
    - 기존 코드 수정 최소화
    - 인터페이스 기반 설계

- `도메인 특화 기능을 Repository가 제공하는 경우의 장점`
  - 도메인 의도가 명확히 드러남
  - 재사용 가능한 로직
  - `데이터 소스` 구현과 분리된 비즈니스 요구사항 처리

- `Repository 와 DataSource 의 역할`
  - `Repository` 는 어떤 데이터를 전달할지에 집중 (필터링)
  - `Repository` 는 직접적인 데이터 조작이 아닌 필요한 데이터를 골라내는 일을 담당
  - 저장 매체를 직접 다루는 코드는 `DataSource` 에서 진행

- `테스트 대역`
  - `진짜 데이터소스`: 진짜 파일 조작
  - `테스트용 데이터소스`: 메모리만 사용하여 기존 동작을 모사한 객체

- `테스트 용이성`
  - 다형성을 활용하면 테스트할 때 원하는 객체를 활용 가능하다.
  - 테스트용 객체를 별도로 준비하여 테스트가 가능하다.

- `Mock 객체 활용`
  - `단위테스트` 는 때때로 `라이브 웹 서비스` 또는 `데이터베이스` 에서 데이터를 가져오는 클래스에 의존할 수 있다. 이는 다음과 같은 몇 가지 이유로 불편이 생긴다.
    - 테스트 실행 속도가 느려진다
    - 예기치 않은 결과를 반환하면 통과 테스트가 실패하기 시작할 수 있다.
    - 가능한 모든 성공 및 실패 시나리오를 테스트하는 것은 어렵다.
  - 따라서 `라이브 웹 서비스` 나 `데이터베이스` 에 의존하는 대신 이러한 종속성을 `Mocking` 할 수 있다.

  - `Mock` 은 `라이브 웹 서비스` 또는 `데이터베이스` 를 에뮬레이션하고 상황에 따라 특정 결과를 반환할 수 있다.

- `좋은 Unit Test의 6가지 조건 (FRIEND)`
  - Fast (빠르고)
  - Reliable (믿을 수 있고)
  - Independent (독립적인)
  - Ease of Maintenance (유지 관리가 쉽고)
  - Nearly compacted code (거의 압축적인 코드)
  - Dependencies should be less (의존성이 적어야 한다)
