# 인스턴스 기본 조작 복습

이 문서는 `Java 입문 응용 3장: 인스턴스의 기본 조작` 자료를 복습하기 위한 학습 자료입니다. 인스턴스를 문자열로 표현하고, 동등성을 정하고, 컬렉션에서 찾고 지우고, 원하는 기준으로 정렬하고, 안전하게 복사하는 방법을 익힙니다.

## 학습 목표

이 문서를 읽고 나면 다음을 설명하고 코드로 작성할 수 있습니다.

- Java의 모든 클래스가 `Object`의 기본 메서드를 상속한다는 점
- `toString()`으로 객체의 문자열 표현을 정하는 방법
- `==`와 `equals()`가 비교하는 대상의 차이
- `equals()`와 `hashCode()`를 함께 재정의해야 하는 이유
- `List`, `Set`, `Map`이 동등성을 사용하는 방식
- `Comparable`과 `Comparator`를 이용한 정렬
- 참조 대입, 얕은 복사, 깊은 복사의 차이
- `Cloneable`과 `clone()`의 역할 및 주의점

## 먼저 보는 전체 흐름

```text
객체를 출력한다       → toString()
두 객체가 같은지 정한다 → equals()
컬렉션에서 빠르게 찾는다 → hashCode()와 equals()
객체 목록을 정렬한다    → Comparable 또는 Comparator
객체를 복사한다        → 참조 대입, 얕은 복사, 깊은 복사
```

## 1. `Object` 클래스와 객체의 기본 메서드

### 1-1. 모든 클래스는 `Object`를 상속합니다

Java에서 직접 선언한 클래스는 다른 클래스를 상속하지 않아도 `Object`의 기본 기능을 사용할 수 있습니다.

```java
public class Hero {
    private String name;
}
```

위 클래스는 다음과 같이 선언한 것과 비슷한 상속 관계를 가집니다.

```java
public class Hero extends Object {
    private String name;
}
```

`Object` 타입 변수에는 참조 타입 인스턴스를 담을 수 있습니다.

```java
Object value = new Hero();
value = "문자열";
value = new java.util.ArrayList<>();
```

`int` 같은 기본형 값은 객체가 아니므로 `Object` 변수에 직접 넣을 수 없습니다. 다만 Java는 `Integer` 같은 래퍼 타입으로 자동 변환하는 오토박싱을 지원합니다.

### 1-2. 대표적인 `Object` 메서드

| 메서드 | 역할 |
| --- | --- |
| `toString()` | 객체를 설명하는 문자열을 반환합니다. |
| `equals(Object other)` | 두 객체가 동등한지 판단합니다. 기본 구현은 같은 인스턴스인지 비교합니다. |
| `hashCode()` | 해시 기반 컬렉션이 객체를 분류하고 검색할 때 사용하는 정수 값을 반환합니다. |

각 클래스는 필요한 동작에 맞게 메서드를 재정의할 수 있습니다.

### 1-3. `toString()`으로 객체를 읽기 쉽게 출력하기

`toString()`을 재정의하지 않은 객체를 출력하면 클래스 이름과 해시 코드처럼 사람이 바로 이해하기 어려운 문자열이 나올 수 있습니다.

```java
public class Hero {
    private String name;
    private int hp;

    public Hero(String name, int hp) {
        this.name = name;
        this.hp = hp;
    }

    @Override
    public String toString() {
        return "Hero{name='" + name + "', hp=" + hp + "}";
    }
}
```

이제 다음 코드는 객체의 주요 상태를 보여 줍니다.

```java
Hero hero = new Hero("아서스", 80);
System.out.println(hero);
// Hero{name='아서스', hp=80}
```

`System.out.println(hero)`는 내부적으로 `hero.toString()`의 결과를 출력합니다. `toString()`은 디버깅과 로그 확인에 유용하지만, 사용자에게 보여 줄 문장을 대신하는 용도로는 신중하게 사용합니다.

## 2. `equals()`와 객체의 동등성

### 2-1. `==`와 `equals()`는 무엇이 다른가요?

참조 타입 변수에는 객체 자체가 아니라 객체를 찾아갈 수 있는 참조가 들어 있습니다.

```java
Hero first = new Hero("아서스", 80);
Hero second = new Hero("아서스", 80);
Hero alias = first;

System.out.println(first == second); // false: 서로 다른 인스턴스
System.out.println(first == alias);  // true: 같은 인스턴스
```

`==`는 두 참조가 같은 인스턴스를 가리키는지 비교합니다. `Object`의 기본 `equals()`도 처음에는 같은 인스턴스인지 비교하므로, 별도로 재정의하지 않으면 `first.equals(second)`도 `false`입니다.

`equals()`를 재정의하면 클래스가 정의한 **값의 동등성**을 비교할 수 있습니다. 예를 들어 이름과 HP가 같으면 같은 영웅으로 볼 수 있습니다.

```java
import java.util.Objects;

public class Hero {
    private String name;
    private int hp;

    @Override
    public boolean equals(Object obj) {
        if (this == obj) {
            return true;
        }
        if (obj == null || getClass() != obj.getClass()) {
            return false;
        }

        Hero other = (Hero) obj;
        return hp == other.hp && Objects.equals(name, other.name);
    }
}
```

`getClass()`를 비교했기 때문에 정확히 같은 클래스의 객체만 비교합니다. 상속 관계까지 같은 동등성으로 다루려면 `instanceof`를 쓸 수 있지만, 부모 클래스와 자식 클래스의 `equals()`가 서로 모순된 결과를 내지 않도록 규칙을 함께 설계해야 합니다.

### 2-2. `equals()`가 지켜야 하는 규칙

동등성 비교는 호출 순서나 반복 횟수에 따라 결과가 흔들리면 안 됩니다.

| 규칙 | 뜻 |
| --- | --- |
| 자기 자신과 비교 | `a.equals(a)`는 `true`입니다. |
| 대칭성 | `a.equals(b)`가 `true`이면 `b.equals(a)`도 `true`입니다. |
| 추이성 | `a.equals(b)`와 `b.equals(c)`가 `true`이면 `a.equals(c)`도 `true`입니다. |
| 일관성 | 비교에 쓰는 값이 바뀌지 않는 동안 결과가 일정합니다. |
| null 비교 | `a.equals(null)`은 `false`입니다. |

`Objects.equals(a, b)`를 쓰면 두 값이 모두 `null`인 경우와 한쪽만 `null`인 경우를 안전하게 비교할 수 있습니다.

### 2-3. `List.remove()`와 `equals()`

객체를 인수로 전달하는 `List.remove(object)`는 목록에서 동등한 요소를 찾아 제거합니다. 기본 `equals()`가 인스턴스의 동일성만 비교하면, 필드 값이 같아도 다른 인스턴스는 제거되지 않습니다.

```java
List<Hero> heroes = new ArrayList<>();
Hero h1 = new Hero("슈퍼맨", 100);
Hero h2 = new Hero("슈퍼맨", 100);

heroes.add(h1);
System.out.println(heroes.size()); // 1

heroes.remove(h2);
System.out.println(heroes.size()); // equals()를 재정의하지 않았다면 1
```

이 `Hero`의 동등성을 이름과 HP로 정하고 `equals()`를 올바르게 재정의하면, `remove(h2)`는 `h1`과 동등한 요소를 찾아 제거합니다.

```java
heroes.remove(h2);
System.out.println(heroes.size()); // 0
```

인덱스를 넣는 `remove(0)`은 0번 위치의 요소를 제거합니다. 객체를 넣는 `remove(h2)`와 구분하세요.

## 3. `hashCode()`와 `Set`, `Map`

### 3-1. `equals()`와 `hashCode()`를 함께 재정의하기

`HashSet`과 `HashMap`은 객체를 찾을 때 먼저 `hashCode()`를 이용해 검색할 후보 영역을 찾고, 그 안에서 `equals()`로 동등한 객체인지 확인합니다. `hashCode()`만으로 같은 객체를 확정하지 않습니다.

다음 규칙은 반드시 지켜야 합니다.

1. `a.equals(b)`가 `true`이면 `a.hashCode()`와 `b.hashCode()`는 같아야 합니다.
2. 해시 코드가 같아도 두 객체가 동등하다고 단정할 수 없습니다. 서로 다른 객체가 같은 해시 코드를 가질 수 있습니다.
3. `equals()`가 비교하는 필드는 `hashCode()`에서도 함께 사용해야 합니다.

앞의 `Hero`에서 이름과 HP를 동등성 기준으로 사용했다면 다음처럼 해시 코드도 계산합니다.

```java
@Override
public int hashCode() {
    return Objects.hash(name, hp);
}
```

`Objects.hash(...)`는 전달한 값들을 사용해 해시 코드를 계산합니다. 필드 일부만 넣거나 `equals()`와 다른 필드를 넣으면 컬렉션에서 찾기 어려운 문제가 생길 수 있습니다.

### 3-2. `HashSet`은 중복을 어떻게 판단하나요?

`HashSet`은 중복 요소를 허용하지 않습니다. 객체의 `equals()`와 `hashCode()`가 값의 동등성을 표현한다면, 서로 다른 인스턴스라도 동등한 객체는 하나만 보관합니다.

```java
Set<Hero> heroes = new HashSet<>();
Hero h1 = new Hero("슈퍼맨", 100);
Hero h2 = new Hero("슈퍼맨", 100);

heroes.add(h1);
heroes.add(h2);
System.out.println(heroes.size()); // equals와 hashCode가 올바르면 1
```

`equals()`만 재정의하고 `hashCode()`를 그대로 두면, 두 객체가 같은 해시 영역에 들어간다는 보장이 없습니다. 반대로 `hashCode()`가 같아도 `equals()`가 `false`이면 서로 다른 요소일 수 있습니다.

### 3-3. `HashMap`의 키도 같은 규칙을 사용합니다

`HashMap`은 키로 저장한 객체를 다시 찾을 때 키의 해시 코드와 동등성을 사용합니다.

```java
Map<Hero, String> jobs = new HashMap<>();
Hero key = new Hero("아서스", 80);

jobs.put(key, "기사");
System.out.println(jobs.get(key)); // 기사
```

키로 사용한 객체의 `equals()`·`hashCode()` 기준 필드를 저장 후 변경하면, 나중에 `get()`이나 `remove()`로 찾지 못할 수 있습니다. 해시 기반 컬렉션에 들어 있는 동안에는 동등성 기준이 되는 필드를 바꾸지 않는 편이 안전합니다. 특히 변경 가능한 객체를 `Map`의 키로 쓸 때 주의합니다.

### 3-4. 자주 생기는 오해

| 오해 | 올바른 이해 |
| --- | --- |
| 해시 코드가 같으면 같은 객체다 | 같은 해시 코드는 검색 후보를 좁힐 뿐입니다. `equals()`가 최종 동등성을 판단합니다. |
| `List`도 `hashCode()`로 요소를 찾는다 | 일반적인 `List` 검색·삭제는 순서대로 요소를 확인하며 `equals()`를 사용합니다. |
| `equals()`만 재정의해도 된다 | `HashSet`·`HashMap`에서 값 동등성을 쓰려면 두 메서드를 함께 재정의해야 합니다. |
| `hashCode()`는 항상 서로 다른 값이어야 한다 | 서로 다른 객체가 같은 해시 코드를 가질 수 있습니다. |

## 4. 컬렉션 정렬: `Comparable`과 `Comparator`

### 4-1. 정렬 결과를 어떻게 표현하나요?

`compareTo()`나 `compare()`는 두 값을 비교한 결과로 음수, 0, 양수 중 하나를 반환합니다.

| 반환값 | 의미 |
| --- | --- |
| 음수 | 앞의 값이 뒤의 값보다 정렬 순서상 먼저 옵니다. |
| 0 | 두 값의 정렬 순서가 같습니다. |
| 양수 | 앞의 값이 뒤의 값보다 정렬 순서상 나중에 옵니다. |

반드시 `-1`, `0`, `1`만 반환해야 하는 것은 아닙니다. 음수·0·양수라는 의미가 중요합니다.

### 4-2. `Comparable`: 클래스의 기본 정렬 기준

객체가 기본 정렬 기준을 직접 제공하려면 `Comparable<T>`를 구현하고 `compareTo(T other)`를 작성합니다.

```java
public class Account implements Comparable<Account> {
    private int number;
    private String name;

    public Account(int number, String name) {
        this.number = number;
        this.name = name;
    }

    public int getNumber() {
        return number;
    }

    public String getName() {
        return name;
    }

    @Override
    public int compareTo(Account other) {
        return Integer.compare(this.number, other.number);
    }
}
```

이제 계좌 번호를 오름차순으로 정렬할 수 있습니다.

```java
List<Account> accounts = new ArrayList<>();
accounts.add(new Account(30, "다은"));
accounts.add(new Account(10, "민수"));
accounts.add(new Account(20, "서연"));

Collections.sort(accounts);
```

`Collections.sort(list)`는 목록 요소의 기본 정렬 기준을 사용합니다. 요소 타입은 `Comparable`을 구현해야 합니다.

### 4-3. 비교할 때 뺄셈을 피하기

정수를 비교할 때 다음처럼 뺄셈 결과를 반환하면 큰 값에서 정수 오버플로가 생길 수 있습니다.

```java
return this.number - other.number; // 큰 정수에서 안전하지 않을 수 있음
```

다음처럼 의도를 드러내는 비교 메서드를 사용합니다.

```java
return Integer.compare(this.number, other.number);
```

### 4-4. `Comparator`: 사용할 때 정렬 기준 지정하기

기본 정렬 기준을 바꾸고 싶거나, 클래스 코드를 수정하지 않고 특정 상황에만 다른 기준을 적용하고 싶다면 `Comparator`를 사용합니다.

```java
accounts.sort(Comparator.comparingInt(Account::getNumber).reversed());
```

위 코드는 계좌 번호를 내림차순으로 정렬합니다. 여러 기준을 이어 붙일 수도 있습니다.

```java
accounts.sort(
    Comparator.comparingInt(Account::getNumber)
        .thenComparing(Account::getName)
);
```

첫 기준이 같을 때 다음 기준으로 비교합니다. 클래스에 기본 정렬 기준을 넣는 `Comparable`과 정렬 호출 시 규칙을 전달하는 `Comparator`를 상황에 맞게 고릅니다.

## 5. 인스턴스 복사: 참조 대입, 얕은 복사, 깊은 복사

### 5-1. 참조 변수 대입은 객체 복사가 아닙니다

```java
Hero first = new Hero("홍길동", 100);
Hero second = first;
```

`second = first`는 새로운 `Hero`를 만들지 않습니다. 두 변수가 같은 인스턴스를 가리킵니다.

```text
first  ─┐
        ├──> Hero 인스턴스
second ─┘
```

따라서 `second`를 통해 HP를 바꾸면 `first`로 확인해도 바뀐 값이 보입니다.

### 5-2. 얕은 복사란?

얕은 복사는 바깥 객체는 새로 만들지만, 그 안의 참조 타입 필드가 가리키는 객체는 원본과 공유하는 복사입니다.

```text
원본 Hero ──> Sword
복사 Hero ──┘
```

`Hero` 자체는 둘이지만, 두 `Hero`의 `sword`가 같은 `Sword`를 가리킵니다. 한쪽에서 칼 이름이나 공격력을 바꾸면 다른 쪽에서도 그 변경이 보입니다.

현재 저장소의 `Hero.clone()`도 새 `Hero`를 만들면서 기존 `sword` 참조를 전달하므로, 칼이 있다면 얕은 복사입니다.

### 5-3. 깊은 복사란?

깊은 복사는 복사 대상 객체뿐 아니라 그 객체가 소유한 변경 가능한 내부 객체도 새로 만들어 복사합니다.

```text
원본 Hero ──> 원본 Sword
복사 Hero ──> 복사 Sword
```

이렇게 하면 한쪽의 `Sword`를 바꾸어도 다른 쪽에는 영향을 주지 않습니다. 참조 필드가 더 깊이 중첩되어 있다면 필요한 내부 객체를 재귀적으로 복사해야 합니다.

```java
public Hero clone() {
    Sword copiedSword = sword == null ? null : sword.copy();
    return new Hero(name, hp, copiedSword);
}
```

위 예시에서 `Sword.copy()`는 `Sword`를 새로 만들어 반환하도록 해당 클래스에 구현한 복사 메서드라고 가정합니다.

### 5-4. `Cloneable`과 `clone()`

`Cloneable`은 복제를 허용한다는 표시 역할을 하는 마커 인터페이스입니다. `Cloneable`이 `clone()` 메서드를 선언해 주는 것은 아닙니다. `Object.clone()`은 기본적으로 얕은 복사를 수행하며, 중첩된 객체까지 복제해 주지 않습니다.

`super.clone()`을 사용하는 전형적인 형태는 다음과 같습니다.

```java
@Override
public Hero clone() {
    try {
        Hero copy = (Hero) super.clone();
        copy.sword = sword == null ? null : sword.copy();
        return copy;
    } catch (CloneNotSupportedException e) {
        throw new AssertionError(e);
    }
}
```

이 예시가 깊은 복사가 되려면 `Sword.copy()`가 실제로 새로운 `Sword` 인스턴스를 만들어야 합니다. `copy.sword = sword`처럼 원래 참조를 그대로 대입하면 얕은 복사입니다.

`String`, `Integer`, `LocalDate`처럼 변경할 수 없는 객체는 참조를 공유해도 내부 상태가 바뀌지 않습니다. `Date`, 배열, 목록, 변경 가능한 사용자 정의 객체처럼 내용을 바꿀 수 있는 참조 필드는 복사 범위를 검토합니다.

실제 코드에서는 `clone()`의 동작이 복잡해지기 쉽습니다. 생성자나 이름이 분명한 복사 메서드(예: `copy()` 또는 `copyOf()`)가 더 이해하기 쉬운 경우도 많습니다.

## 6. 확인 문제

먼저 정답을 가리고 직접 생각해 보세요.

1. 필드 값이 같은 두 객체에 대해 `==`가 `false`이고 `equals()`가 `true`일 수 있나요?
2. `equals()`가 `true`인 두 객체의 `hashCode()`는 같아야 하나요?
3. 해시 코드가 같은 두 객체는 반드시 `equals()`도 `true`인가요?
4. `HashSet`에 객체를 넣은 뒤 그 객체의 `hashCode()` 기준 필드를 바꾸면 어떤 문제가 생길 수 있나요?
5. `Comparable`과 `Comparator`의 역할 차이는 무엇인가요?
6. `Hero second = first;`를 실행하면 새 `Hero` 인스턴스가 만들어지나요?
7. 얕은 복사한 두 `Hero`가 같은 `Sword`를 가리킨다면, 한쪽의 `Sword`를 바꿀 때 다른 쪽은 어떻게 되나요?
8. 깊은 복사에서 변경 가능한 내부 참조 객체를 별도로 복제하는 이유는 무엇인가요?

### 정답과 해설

1. 가능합니다. `==`는 같은 인스턴스인지 보고, 재정의한 `equals()`는 클래스가 정한 값의 동등성을 볼 수 있습니다.
2. 네. `equals()`가 `true`이면 해시 코드는 같아야 합니다.
3. 아닙니다. 서로 다른 객체가 같은 해시 코드를 가질 수 있으며, 이때 `equals()`로 다시 비교합니다.
4. 객체가 처음 저장된 해시 영역과 새 해시 코드가 가리키는 영역이 달라져 `contains()`, `get()`, `remove()`가 객체를 찾지 못할 수 있습니다.
5. `Comparable`은 클래스의 기본 정렬 규칙을 정하고, `Comparator`는 정렬을 수행하는 쪽에서 별도의 규칙을 전달합니다.
6. 아닙니다. 두 변수가 같은 인스턴스를 가리킵니다.
7. 공유된 `Sword` 인스턴스가 변경되므로 두 `Hero`를 통해 보이는 칼 상태가 함께 바뀝니다.
8. 참조만 복사하면 원본과 복사본이 같은 내부 객체를 공유하기 때문입니다. 내부 객체도 새로 만들어야 한쪽의 변경이 다른 쪽에 영향을 주지 않습니다.

## 7. 마지막 점검표

- 객체 내용을 읽기 좋게 출력하려고 `toString()`을 재정의했나요?
- 동등성의 기준 필드를 요구사항에서 확인했나요?
- `equals()`와 `hashCode()`에서 같은 기준 필드를 사용했나요?
- 해시 코드가 같다는 이유만으로 객체가 같다고 가정하지 않았나요?
- 정렬의 오름차순·내림차순 방향을 작은 예로 확인했나요?
- 얕은 복사와 깊은 복사에서 참조 타입 필드가 공유되는지 확인했나요?
- `Date`처럼 변경 가능한 내부 객체를 복사할 때 새 인스턴스를 만들었나요?

## 핵심 요약

```text
toString()   : 객체를 문자열로 표현한다.
equals()     : 클래스가 정한 동등성 규칙을 표현한다.
hashCode()   : HashSet·HashMap에서 검색 후보를 찾는 데 사용한다.
Comparable   : 클래스의 기본 정렬 기준을 제공한다.
Comparator   : 정렬할 때 별도의 기준을 전달한다.
얕은 복사    : 바깥 객체는 새로 만들지만 내부 참조 객체는 공유한다.
깊은 복사    : 필요한 내부 변경 가능 객체까지 새로 복사한다.
```

`equals()`와 `hashCode()`는 한 규칙으로 설계하고, 복사는 내부 참조 타입이 변경 가능한지 확인한 뒤 필요한 만큼 수행합니다.
