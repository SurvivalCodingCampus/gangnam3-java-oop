## 1. 배운 점

### 상속

- **기존 클래스(부모)**의 **속성(변수)과 기능(메서드)**을 **새로운 클래스(자식)**가 물려받아
  **그대로 사용하거나 확장**하는 기술
- **is-a**관계로만 상속
- **자식 클래스**일 수록 **구체화**
  - `구체화` : **추상적인 개념**을 실제 동작하는 코드나 **객체로 구현**하는 과정

- **부모 클래스**일 수록 **추상화, 일반화**
  - `추상화` : 복잡한 현실에서 **핵심적인 개념, 기능**을 **간추려** 내는 것
  - `일반화` : **공통된 성질**을 추출해 더 넓은 **상위 개념**을 만들어 내는 것

#### 장점

- **코드의 재사용성 증가**: 공통된 코드를 부모 클래스에 작성해 두고 재사용하므로 중복 코드를 작성할 필요가 없음
- **유지보수의 용이성**: 공통 기능에 수정이 필요할 때 부모 클래스 한 곳만 수정하면 상속받은 모든 자식 클래스에 반영
- **다형성(Polymorphism)의 기반**: **자식 객체**를 **부모 타입 변수**에 담아 다룰 수 있어 **유연한 설계** 가능(`Animal pet = new Dog();`)

#### 단점

- **강한 결합** : 상속은 **강력한 결합**을 만듦
  - **부모 클래스의 코드가 조금만 변경되어도
    모든 자식 클래스가 영향을 받거나 깨질 수 있음**
  - `결합(Coupling)` : **모듈(또는 클래스, 함수)들이 서로 얼마나 강하게 의존하고 있는지**를 나타내는 개념
    - `의존성` : 객체가 **작업을 수행**하기 위해 **다른 객체를 필요**로 하는 관계
- **불필요한 기능까지 물려받음(캡슐화 깨짐)** : 자식 클래스는 부모 클래스의 **모든 public/protected 메서드와 속성**을 강제로 물려 받음
- **복잡성 증가** : 상속의 **Depth가 깊어질수록 복잡도**가 **크게** 증가

### is-a vs has-a

| 구분            | IS-A 관계 (상속)                            | HAS-A 관계 (포함/조합)                    |
| :------------ | :-------------------------------------- | :---------------------------------- |
| **의미**        | "~는 ~다" (Kind-of)                       | "~은 ~를 소유/포함하고 있다" (Part-of)        |
| **개념적 관계**    | **하위 분류 관계** (자식 개념이 부모 개념에 포함됨)        | **구성 요소 관계** (객체가 다른 객체를 부품으로 가짐)   |
| **OOP 구현 기법** | **상속**                                  | **조합/포함 (Composition/Aggregation)** |
| **결합도**       | **높음** (부모 클래스 변경 시 자식 클래스에 영향)         | **낮음** (내부 부품 클래스가 바뀌어도 영향 최소화)     |
| **문장 예시**     | 학생은 사람이다                                | 자동차 엔진을 가진다                         |
| **주요 목적**     | **다형성(Polymorphism) 활용** 및 개념적 계층 구조 형성 | 코드 재사용, **유연한 구조** 설계 및 **결합도 감소**  |

### 조합 vs 포함

| 구분           | 조합 (Composition, 강한 결합)                   | 집합/포함 (Aggregation, 약한 결합)           |
| ------------ | ----------------------------------------- | ------------------------------------ |
| **개념적 관계**   | 전체와 부분 (Part-of)                          | 전체와 구성원 (Has-a)                      |
| **생명주기**     | **전체 객체**가 소멸하면 부분 객체도 **함께 소멸**(**종속적**) | 전체 객체가 소멸해도 구성원 **객체는 유지됨**(**독립적**) |
| **객체 생성 방식** | **클래스 내부**에서 직접 **생성 및 관리**               | **외부**에서 생성된 **객체를 주입(의존성 주입)**받음    |
| **현실 세계 비유** | 사람과 심장, 건물과 방                             | 학과와 학생, 팀과 선수                        |
- `의존성 주입` : 객체가 **필요로 하는 다른 객체(의존성)**를 직접 만들지 않고 **외부에서 만들어 넣어주는(주입)** 설계 방식

### AssertJ

- 자바 테스트 코드의 **가독성과 표현력**을 크게 높여주는 검증(Assertion) 라이브러리
- **메서드 체이닝**을 통해 가독성을 크게 높임
  - `메서드 체이닝` : **하나의 객체**에서 **여러 메서드를 연속해서 호출**하는 코드 작성 기법
    - **빌더 패턴**을 활용해 **메서드 체이닝** 구현가능
      - `빌더 패턴` : 복잡한 객체를 생성할 때 **어떤 값이 들어가는지 직관적으로 알 수 있게 하고 안전하게(불변 객체로) 만들기 위해** 사용하는 대표적인 **패턴**

### 빌더패턴

- **복잡한 객체를 단계별로 생성**할 수 있게 도와주며 주로 **생성자의 매개변수가 많을 때** 발생하는 **가독성 저하와 유지보수** 문제를 해결하기 위해 사용

| 구분           | 생성자 패턴 (Constructor)                 | Setter 패턴<br>(JavaBeans)                            | 빌더 패턴 <br>(Builder)             |
| ------------ | ------------------------------------ | --------------------------------------------------- | ------------------------------- |
| **가독성**      | **나쁨**<br>**매개변수**가 많이지면 보기 힘듦       | **좋음**<br>object.set(...) 을 통해 여려줄이 써야해 **여러줄**이 생김 | **좋음**<br>**메서드 체이닝**을 통해 직관적   |
| **불변성**      | **가능**                               | **불가**<br>객체 생성 후 Set을 하기 때문에 불가능                   | **가능**                          |
| **안전성**      | **높음**<br>필수 인자를 **누락**하면 **컴파일 에러** | **낮음**<br>객체 생성후 Set을 하기 때문에<br>**필수 값 누락 가능**      | 높음<br>빌더 생성자를 통해 **필수 값 강제**    |
| **선택적 매개변수** | **불편**<br>필요한 매개변수마다 **생성자 오버로딩**    | **편함**<br>**필요한 Setter**만 골라서 호출                    | **편함**<br>필요한 **메서드만 골라 체이닝**   |
| **성능**       | **빠름**<br>한 번에 설정해 빠름                | **보통**<br>여러 줄이 생겨 미세한 오버헤드 발생                      | **느림**<br>빌더 객체를 생성해 GC 일감이 늘어남 |

## 2. 가장 멘붕이었던 순간 & 트러블슈팅


- `문제상황` :
  - **생성자와 세터**를 같이 사용해 **코드 가독성**이 떨어짐
  - **생성자로 통일 시도** -> 매개변수를 다양하게 사용해
    **생성자 오버로딩**을 다 해줘야 하는 상황 발생
- `해결` : 빌더 패턴을 활용해 **가독성, 안전성**을 확보하는 쪽으로 선택
