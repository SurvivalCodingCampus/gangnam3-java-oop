# 비동기 프로그래밍

## 용어 정리

- `동기`: 한 작업이 끝날 때까지 기다렸다가 다음 작업을 시작한다.
- `비동기`: 기다리지 않고 다른 작업을 시작한다.
- `동시성`: 여러 작업을 번갈아가면서 처리하는 것
- `병렬성`: 여러 작업을 실제로 동시에 처리하는 것
- `코루틴`: `비동기` 프로그래밍을 간단하고 효율적으로 만들어주는 도구

## 클래스 작성 테스트 코드

```kotlin
@OptIn(ExperimentalCoroutinesApi::class)
class MainTest {

    // 반환값 테스트
    @Test
    fun `kuu는 꾸우를 반환한다`() = runTest {
        assertEquals("꾸우", kuu())
    }

    @Test
    fun `caw는 까악을 반환한다`() = runTest {
        assertEquals("까악", caw())
    }

    @Test
    fun `tweet은 짹짹을 반환한다`() = runTest {
        assertEquals("짹짹", tweet())
    }

    // 지연 시간 테스트
    @Test
    fun `kuu는 1초가 걸린다`() = runTest {
        kuu()

        assertEquals(1000, currentTime)
    }

    @Test
    fun `caw는 2초가 걸린다`() = runTest {
        caw()

        assertEquals(2000, currentTime)
    }

    @Test
    fun `tweet은 3초가 걸린다`() = runTest {
        tweet()

        assertEquals(3000, currentTime)
    }

    // 동시 실행 테스트
    @Test
    fun `launch로 실행하면 동시에 실행된다`() = runTest {
        val sounds = mutableListOf<String>()

        val job1 = launch { sounds.add(kuu()) }
        val job2 = launch { sounds.add(caw()) }
        val job3 = launch { sounds.add(tweet()) }

        job1.join()
        job2.join()
        job3.join()

        assertEquals(3000, currentTime)
        assertEquals(listOf("꾸우", "까악", "짹짹"), sounds)
    }

    // 실행 취소 테스트
    @Test
    fun `cancelAndJoin으로 무한 반복을 멈춘다`() = runTest {
        var count = 0

        val job = launch {
            while (true) {
                kuu()
                count++
            }
        }

        advanceTimeBy(3500.milliseconds)
        job.cancelAndJoin()

        val countAfterCancel = count
        advanceTimeBy(2.seconds)

        assertTrue(job.isCancelled)
        assertFalse(job.isActive)
        assertEquals(3, countAfterCancel)
        assertEquals(countAfterCancel, count)
    }
}
```

## 정리

- `비동기 프로그래밍`
  - 여러 작업이 `병렬` 로 실행될 수 있다.
  - 한 작업이 완료 여부와 관계없이 다음 작업을 시작할 수 있다.
  - 작업의 완료 순서를 예측할 수 없다.
  - I/O 작업이나 네트워크 요청과 같이 시간이 오래 걸리는 작업에 유용하다.
  - 성능 향상의 장점이 있으나, `복잡도 증가` `동기화 필요` `디버깅 어려움` 등의 단점도 존재한다.

- `동기 프로그래밍`
  - 코드가 순서대로 실행된다.
  - 작업이 완료될 때까지 프로그램이 중단될 수 없다.
  - 모든 작업은 이전 작업의 실행이 완료될 때까지 기다려야 한다.

- `동시성`
  - 여러 작업이 논리적으로 동시에 실행되는 것처럼 보이는 개념
  - 시분할 방식으로 여러 `스레드` 를 활용해 `동시성` 을 구현할 수 있다.

- `병렬성`
  - 여러 작업이 물리적으로 동시에 실행되는 개념
  - 멀티코어 환경에서 실제로 여러 `스레드` 가 `병렬` 로 실행될 수 있다.

- `단일 Thread 의 문제점`
  - 모든 인스턴스는 `main 스레드` 에서 생성되며 처리된다.
  - `Thread` 를 `Block` 하는 동안 프로그램이 멈춘다.

- `콜백 기준의 동기화 방식의 문제점`
  - 코드의 깊이가 깊어지고 관리하기 어려워진다.
  - 콜백 지옥이 발생한다.
  - 디버깅이 어려워진다.
  - 병렬처리가 어려워진다.

- `Coroutine`
  - Kotlin 표준 병행 프로그래밍 API
  - `코루틴` 은 오래 걸리는 작업을 수행하는 효율적인 방법 중 하나이다.
  - 콜백 기반 코드를 순차 코드로 변환할 수 있다.
  - 순차 코드는 읽기 쉽고 에러 처리가 편하다.
  - 일반적으로는 하나의 `코루틴` 이 특정한 `스레드` 에서 동작한다.
  - Kotlin `코루틴` 은 `suspend` 와 `resume` 을 통해 `스레드` 를 양보한다.
  - `비동기` 식이며 `스레드` 를 차단하지 않는다.
  - `일시 중단 함수` 를 사용하여 `비동기` 코드를 순차적으로 만든다.

- `Coroutine 사용 시 이점`
  - `경량`: `코루틴` 은 실행 중인 `스레드` 를 차단하지 않는 `정지(suspend)` 를 지원하여 메모리를 절약하면서 많은 동시 작업을 처리한다.
  - `메모리 누수 감소`: `스레드` 를 활용한 동기화는 휴먼 에러에 의한 메모리 누수나 데드락과 같은 위험이 존재하지만, `코루틴` 은 안전하다.
  - `스레드` 보다 가볍고 효율적이다.
  - 많은 안드로이드 API가 지원하고 있다.

- `Coroutine의 주요 컨셉`
  - 다른 언어의 `async` `await` 같은 키워드가 제공되지 않는다.
  - `정지(suspend) 함수` 를 활용한 안전하고 에러가 발생하지 않는 `비동기` 처리에 중점을 둔다.
  - `코루틴` 의 수명은 `runBlocking` `launch` 와 같은 `CoroutineScope` 내에서 결정되어, 메모리 누수나 손실을 방지한다.

- `Coroutine Builder`
  - 새로운 코루틴을 시작하는 함수를 `코루틴 빌더` 라고 한다.
  - `코루틴 빌더` 의 예시는 다음과 같다.
    - `runBlocking`
    - `withContext`
    - `CoroutineScope.launch`
    - `CoroutineScope.async`
  - `코루틴 빌더` 는 `코루틴` 이 생명주기를 제한하는 `CoroutineScope` 를 생성한다.
  - `코루틴 빌더` 의 블록 안은 `CoroutineScope` 이며, 이 블록 안에서 시작한 `코루틴` 은 그 스코프의 `자식` 이 된다.
  - `runBlocking` 안에서 `launch` 로 시작한 `코루틴` 은 `runBlocking` 의 `자식` 이다.
    - 부모는 모든 자식이 완료될 때까지 기다린다.
    - 부모가 취소되면 자식도 함께 취소된다.
    - 자식에서 예외가 발생하면 부모도 취소된다.
  - 자식 `코루틴` 은 부모 안에서 `동시에` 실행될 뿐, 부모와 독립적인 것은 아니다.
  - `GlobalScope.launch` 처럼 부모 스코프가 없는 곳에서 시작한 `코루틴` 은 부모와 연결되지 않아 독립적으로 동작한다. 수명을 직접 관리해야 하므로 권장되지 않는다.
  - 예: 연습 문제 2에서 `cancelAndJoin()` 을 호출하지 않으면, `runBlocking` 이 무한 반복하는 자식 `launch` 를 계속 기다리므로 프로그램이 끝나지 않는다.

- `launch`
  - 결과가 필요없는 `비동기` 작업
  - 반환값은 `Job`

- `async`
  - 결과가 필요한 `비동기` 작업
  - 반환값은 `Deferred<T>`

- `runBlocking`
  - `코루틴` 과 일반 코드 연결
  - 반환값은 `T`
  - 블로킹 방식으로 `코루틴` 실행
  - 완료될 때까지 호출자 `Thread` 를 차단한다. `Main Thread` 에서 호출하면 `Main Thread` 도 차단된다.

- `delay`
  - 일정 시간 `코루틴` 을 `일시 정지` 하는 `suspend` 함수다.
  - `코루틴` 이 정지되는 동안 실행 중인 `Thread` 는 차단되지 않는다.
  - `suspend` 함수는 `CoroutineScope` 블록 또는 다른 `suspend` 함수에서 호출 가능하다.

- `suspend`
  - `비동기` 함수를 표기하는 `코틀린` 문법이다.
  - 실행되면 완료될 때까지 일시 중지된다.
  - 그 사이 다른 함수나 `코루틴` 이 실행될 수 있다.

- `CoroutineScope`
  - 모든 `코루틴` 을 추적하여 `코루틴` 이 실행되어야 하는 시기를 관리하는 구성 요소
  - 모든 `비동기` 작업은 특정 스코프에서 실행되어야 한다.
  - `코루틴` 은 스코프에 의존적이다.
  - 적절한 스코프가 없으면 전역적인 스코프인 `GlobalScope` 를 사용할 수 있지만, 이는 권장되지 않는다.

- `Job`
  - `코루틴 빌더` 에 의해 작성된 `코루틴`
  - `launch` 는 `Job` 을 리턴한다.
  - `Job` 을 통해 실행 중인 `코루틴` 을 제어할 수 있다.
  - `join` 은 해당 `코루틴` 내의 처리가 끝나는 것을 기다린다.
  - `cancel` 을 통해 `코루틴` 취소가 가능하다.

- `Dispatcher`
  - `코루틴` 이 어떤 스케줄러에 의해 수행될 지를 지정할 수 있다.
  - `Default`
    - 백그라운드 스레드
    - 코어 수에 비례해서 스레드를 만든다.
    - 연산 용도 또는 CPU에 부하를 줄 만한 처리(List 정렬 등)에 사용한다.
  - `Main`
    - 메인 스레드에 연결되는 `디스패처`
  - `IO`
    - 백그라운드 스레드
    - Input/Output 조작용
    - 상대적으로 많은 스레드를 만드는 디스패처 (DB 통신 / Http 통신)
  - `Unconfied`
    - 특정 스레드를 한정하지 않는다. 공식 문서에서는 보통 사용하지 않는다고 명시되어 있다.

- `withContext`
  - 디스패처를 전환해주는 함수
  - 디스패처를 전환하여 `Worker 스레드` 와 `Main 스레드` 를 넘나들 수 있다.

- `Thread.sleep() vs delay()`
  - `Thread.sleep()` 은 `스레드` 를 차단(점유)하는 문제가 있다.
  - `delay()` 는 현재 실행되는 코드 블록을 일정 시간 쉬게하고 다른 코드 블록에 `스레드` 를 쓸 기회를 준다. 이를 `suspend(일시 중단)` 이라고 한다.
  - `Thread.sleep()` 은 `스레드` 를 소비하지만, `delay()` 는 양보한다.
