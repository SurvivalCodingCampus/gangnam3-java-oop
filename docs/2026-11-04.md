# DTO, Mapper

## 용어 정리

- `DTO`: 데이터 소스를 모델 클래스로 변환하는 과정에서 순수하게 클래스에 담기 위한 중간 전달 객체
- `Mapper`: `DTO` 를 모델 클래스로 변환

## 클래스 작성 테스트 코드

```kotlin
class PokeMapperTest {

    @Test
    fun `정상 데이터는 그대로 변환된다`() {
        // given
        val dto = PokeDto(
            id = 25,
            name = "pikachu",
            baseExperience = 112,
            height = 4,
            isDefault = true,
            order = 35,
            weight = 60
        )

        // when
        val poke = dto.toModel()

        // then
        assertEquals(
            Poke(
                id = 25,
                name = "pikachu",
                baseExperience = 112,
                height = 4,
                isDefault = true,
                order = 35,
                weight = 60
            ), poke
        )
    }

    @Test
    fun `모든 필드가 null이면 기본값으로 변환된다`() {
        val poke = PokeDto().toModel()

        assertEquals(
            Poke(
                id = 0,
                name = "Unknown",
                baseExperience = 0,
                height = 0,
                isDefault = false,
                order = 0,
                weight = 0
            ), poke
        )
    }

    @Test
    fun `name이 빈 문자열이면 Unknown이 된다`() {
        assertEquals("Unknown", PokeDto(name = "").toModel().name)
    }

    @Test
    fun `name이 공백이면 Unknown이 된다`() {
        assertEquals("Unknown", PokeDto(name = "   ").toModel().name)
    }

    @Test
    fun `height와 weight가 음수면 0이 된다`() {
        val poke = PokeDto(height = -5, weight = -10).toModel()

        assertEquals(0, poke.height)
        assertEquals(0, poke.weight)
    }

    @Test
    fun `height와 weight가 0이면 그대로 0이다`() {
        val poke = PokeDto(height = 0, weight = 0).toModel()

        assertEquals(0, poke.height)
        assertEquals(0, poke.weight)
    }
}
```

## 정리

- `실제 발생하는 문제들`
  - 서버 API 변경으로 인한 필드 누락/제거
  - 서버 장애 시 예상치 못한 응답 구조
  - 클라이언트/서버 버전 불일치

- `방어적 코드 작성`
  - 잘못된 데이터를 받으면 프로그램이 터진다.
  - 서버 잘못에 대한 클라이언트의 대비가 필요하다.
  - `DTO` 는 잘못된 데이터 소스를 받더라도 안 터지게 하려는 클라이언트의 방어 수단이다.

- `DTO 코드 예시`
  - 모든 필드가 `Nullable` 변수이다.
  - 직렬화, 역직렬화가 가능하도록 한다.

- `모델 클래스 역할 재정의`
  - 모든 필드는 `Non-Nullable` 상수이다.
  - `Equals` `HashCode` `ToString` 재정의
  - 앱에서 필요한 내용으로만 구성한다.

- `Mapper 작성 시 DTO 안에 작성하지 않고 확장함수를 선호하는 이유`
  - `DTO` 는 자동으로 만들고 수정하지 않는다. (다른 코드 개입 및 실수 방지)
  - 데이터 저장용 클래스(`DTO`) 와 변환 로직(`Mapper`) 을 분리한다.
  - `Mapper` 는 복잡한 로직이 포함될 수 있어서 문제가 있으면 해당 부분만 살핀다.

- `DTO를 모델로 변경했을 때의 장점`
  - `Boolean` 필드는 `is` 접두어 사용
  - `Nullable` 타입 제거로 안전성 향상
  - 도메인 모델은 순수 코틀린 타입 사용
  - `DTO` 는 데이터 소스 직렬화 및 역직렬화를 담당하고 모델 클래스는 `DTO` 에서 필요한 내용만 활용하는 도메인 객체로써 역할 분담이 가능하다.

- `DataSource 의 반환 타입으로 올바른 예시`
  - `DTO` 또는 `DTO` 를 담은 `Response` 반환

- `DTO 가 필요한 이유`
  - 모델 클래스는 `Non-Nullable` 값만 가지고 있도록 한다.
  - `Json` 데이터는 `null` 값을 포함할 수 있다. (문서에 명시되어 있지 않더라도)
  - `Map` 에서 모델 클래스로 변환 시 `null` 값 등의 예외를 사전에 걸러내기 용이하다.
  - 불완전한 코드가 포함될 것 같다면 `DTO` 를 도입한다.
  - `Json` 값에 예외가 없다면 반드시 `DTO` 를 도입할 필요는 없다.
